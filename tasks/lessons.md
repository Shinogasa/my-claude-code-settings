### 2026-08-02 | 学習ループ再設計時の診断ミス（未clone環境での断定）

**間違えた内容:**
`learning-journal.md` の実体を `find ~` で探して0件だったことから、「Protégé は一度も動かず蓄積ゼロ」と断定し、
それを設計書のファクト欄にも書いた。実際には移行元リポジトリに11エントリ・143行が蓄積されており、
当該リポジトリがそのマシンに未 clone だったための観測ミスだった。

**指摘・修正:**
ユーザーから「リポジトリはクローンしてきたので再確認」と指示を受けて再調査し、訂正した。
正しい診断は「約2.5ヶ月は週1ペースで稼働していたが1ヶ月前に停止した」であり、
「一度も動かなかった」とは原因の重み付けが異なる。

**教訓:**
**「ファイルが見つからない」は「存在しない」ではなく「この環境からは見えない」でしかない。**
symlink・外部リポジトリ・bind mount など間接参照が絡む構成では、参照元の不在と実体の不在を区別すること。
特に設計書のファクト欄に書く事実は、「何を確認して」「その確認方法で何が確認できないか」まで
セットで検証してから断定する。今回は `setup.sh` 内に移行元PRIVATEリポジトリへの
参照パスが明記されていたのだから、そのディレクトリの存在を確認した時点で
「未clone環境である可能性」に気付けたはずだった。

### 2026-07-24 | hooks導入時の危険コマンドガード実装

**間違えた内容:**
`guard-dangerous-bash.sh`で危険コマンドを正規表現の単純な部分文字列マッチで検知する実装にした結果、`git commit -m "$(cat <<'EOF' ... EOF)"`のヒアドキュメント内にある**説明文としての**「git reset --hard」という文字列に反応し、自分自身のコミット操作をブロックした。

**指摘・修正:**
「実行されるコマンド」と「コマンド文字列中に埋め込まれたテキスト(ヒアドキュメント本体、引用符付き文字列リテラル)」を区別せず判定していたのが原因。`shlex`でトークン化し、各サブコマンドの先頭トークン(コマンド名)と引数トークンを見るトークンベースの判定に書き直して解消した。

**教訓:**
コマンド文字列を安全側に倒して確定的にブロックするhookを書くときは、単純な文字列マッチ(`grep -qE`等)ではなく、シェルの構文(トークン化・ヒアドキュメント・引用符)を尊重した解析が必須。特にヒアドキュメントを使うgit commitは「危険な単語を含む説明文」を書く機会が多く、素朴な実装だと真っ先に事故る。

### 2026-08-05 | Codex への superpowers 導入時、hook 機構の有無を誤判定

**間違えた内容:**
Codex のプラグインが hook を持てるかを調べる際、`plugin.json` のキーだけを走査し
（bundled プラグイン6個分）、`hooks` 相当のキーが無いことから
「Codex にはプラグイン hook 機構が無い」と設計書に断定した。

実際には機構は存在し、`plugin.json` のキーではなく**プラグイン直下の `hooks.json`**
という別ファイルで定義する形式だった（`figma` / `replayio` が使用中）。
正しくは「superpowers の Codex 配布物が hook を同梱していない」。

**指摘・修正:**
実装後の検証で `find -iname "*hook*"` を回して自分で気づき、設計書・README・CLAUDE.md を
訂正した。設計の結論（発火の配線が必要）自体は変わらなかったため実装への影響は無かったが、
理由が過度に一般化されており、将来の判断材料としては誤りだった。

その後ユーザーから「ドキュメント読む」との指摘を受けて確認したところ、
`openai/plugins` の README 3段落目に、必須の `plugin.json` と並ぶ optional な構成要素として
`hooks.json` が明記されていた。**調査の過程でこのリポジトリのファイル一覧は取得しており、
README の存在を見ていながら開かずにファイル走査へ進んでいた。**

**教訓:**
**これは 2026-07-19 の「ファイルが見つからない ≠ 存在しない」の再発である。**
前回は環境起因（未clone）、今回は探索空間の前提誤り（定義場所の思い込み）と
現れ方は違うが、構造は同一。`ls` / `grep` / キー走査は
「**自分の探し方の範囲内に無い**」ことしか証明せず、「存在しない」の証明にはならない。

不在を主張するときは、探索空間そのものが正しいという別の根拠を添えること。
その根拠として最も安いのが一次ドキュメントであり、走査より**先に**読む。
`rules/ecc-development-workflow.md` の Research & Reuse が
「GitHub code search first, **library docs second**」を mandatory と定めているのは
まさにこの順序のことで、守っていれば発生しなかった。

走査を丁寧にやるほど「調べ尽くした」感覚だけが強まり、前提の誤りが隠れる。
**丁寧さは正しさの証明にならない。**

### 2026-08-05 | 調査・分析で繰り返した誤りから確立した検査の型

同日の調査（プラグイン停止判定 → 有用性測定 → バグ発見 → upstream 報告）で、
**同じ型の誤りを3回**踏んだ。個別の訂正は上のエントリに書いたので、
ここには再発防止として使える検査の形だけを残す。

**踏んだ3回:**

| 回 | 観測 | 誤った読み替え |
|---|---|---|
| 1 | manifest にキーが無い | 機構が存在しない |
| 2 | ログ上の検出0件 | 検出能力が無い（対象が綺麗だった可能性を排除できていない） |
| 3 | `grep '^VAR='` がマッチする | 値が設定されている（空文字列と区別できない） |

いずれも**観測手段の分解能を超えた結論**を出している。
3回目の道具は特に悪く、**測りたかったのが「空文字列か否か」なのに、
それを判別できない道具を選んでいた**。しかも出力は綺麗に出た。
動く出力が誤った確信を生む。

**作業前に通す問い（順に効く）:**

1. **不在を書く前** — この「無い」が間違いなら、どこを見ていなかったことになるか
2. **測定を組む前** — 仮説が偽のとき、この道具はどんな出力を出すか
   （真のときと同じ出力しか出せないなら、それは測定ではない）
3. **テストを書いた後** — これは実装の写像になっていないか
   （実装を読んでからケースを書くと実装を追認するテストになる。
   同日、同一ツールを2通りのテストで測ったら検出率が 94% と 0% に割れた）
4. **検査系を実装するとき** — 「検査できなかった」はどの状態に落ちるか
   （①検査OK ②検査NG ③検査不能 の3状態。③を①に畳むと危険側に倒れる）
5. **修正をレビューするとき** — この修正は、問題と同じ抽象度にあるか
   （「リストに1件足す」形の修正は再発を内包しやすい）

**ユーザー指摘の性質（今回効いた4つ）:**

| 指摘 | 型 |
|---|---|
| 「本当にこれはバグなのだろうか」 | 結論の停止 |
| 「一部のバージョンしか指定していないのは違和感がある」 | 前提への疑い |
| 「OSS なら誰か報告してるのでは」 | 探索空間の拡張 |
| 「下書きなくね？」 | 成果物の実在確認 |

4つとも**作業を進める指摘ではなく、進行を止めて枠組みを問い直す指摘**だった。
そしてこれらは全て、上記3回の誤り（探し方の範囲を事実の範囲と取り違える）への
外部補正になっている。**同じ枠組みの中で丁寧に探しても、枠組み自体の誤りは出てこない。**

だから作業中に「丁寧に調べている」感覚が強いときほど、
**枠組みを疑う問い（上記1〜2）を自分から通す**必要がある。

**成果物の扱いで1点:** 「下書きは scratchpad にある」と述べながら中身を一度も
提示していなかった。ファイルは実在したので嘘ではないが、相手から見れば
成果物は存在しないのと同じ。**成果物を作ったと報告するときは、内容を提示する。**

### 2026-08-13 | 設定監査で繰り返した「後から気づく」パターン

同一タスク中に、性質の同じ誤りを2回起こした。どちらも
**先に読む／確認すべきものを、作業を進めてから読んだ**ことが原因。

**1. コマンドの成否を出力から確認しなかった**

`git switch main && git pull --ff-only` を実行し、出力に `Aborting` が
含まれていたのに次の作業へ進んだ。実際には未追跡ファイルとの衝突で
pull が中断しており、**25コミット遅れたベースから新ブランチを切っていた**。
気づいたのは、参照したはずのファイルが存在しないという別の違和感からで、
そこまでに複数回のツール呼び出しを無駄にした。

複数コマンドを `&&` や `;` で連結して `tail` に通すと、
**中間のコマンドの失敗が最後の数行に現れず消える。**
状態を変えるコマンドは、実行直後にその状態を検証する
（`git merge-base --is-ancestor` 等、真偽が返るもので確かめる）。

**2. 既存の課題リストを着手前に読まなかった**

フックの `timeout` が桁違いであることを「新発見」として報告し、修正した。
実際には `backlog.md` に登録済みで、しかも
**「単純に短くすると防御が黙って外れる方向に倒れうる。先に fail-open か
fail-close かを確認せよ」という警告と着手条件が明記されていた。**
その条件を満たさないまま値を変えており、後から差し戻した。

`backlog.md` を開いたのは、作業の終盤に「項目を追加する」目的でだった。
**着手前に読めば警告として働くものが、終盤に読むと事後確認にしかならない。**

**共通の対策:** タスクの調査フェーズで既存の課題リストを読む。
「追記するために開く」のではなく、**「同じことが既に調べられていないか」を
最初に確かめる**。設定リポジトリでは特に、過去の自分が既に踏んだ地雷が
文書化されている可能性が高い。
