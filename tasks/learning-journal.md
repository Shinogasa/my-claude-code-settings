## [2026-04-21] | API パラメータの型設計 — nullable か デフォルト値付きか

**問いかけ:** 「なぜ `Boolean? = null` ではなく `Boolean = false` を選んだのか？」トレードオフを含めてどう説明する？

**自分の説明:**
バックエンドだと null の場合に既存の動作を保証するような実装になっているが、false にしたほうが明確に設定がわかる。トレードオフはいちいち書く必要があるところ。

**補足:**
「バックエンドのデフォルト値に暗黙依存しない」が核心。nullable だとバックエンド側がデフォルトを変更した場合に、呼び出し側の挙動が意図せず変わるリスクがある。default false により既存呼び出し元の書き換えは不要で、true を渡す箇所だけ明示する設計なのでコストも低い。

## [2026-04-22] | Kotlin `object` の `by lazy` 化（設定オブジェクトのトークン）

**問いかけ:** 今回 `val token: String = ...throw` ではなく `val token: String by lazy { ...throw }` を選んだ。「なぜ `by lazy` にしたの？」と聞かれたら、Kotlin `object` の初期化の仕組みを踏まえてどう説明する？

**自分の説明:**
オブジェクトは初回アクセス時に初期化が走る。今回利用しない変数があって環境変数に設定していなかった場合、現状だと exception が throw される。不要な環境変数をわざわざ設定する手間をなくしたいので、利用されるときに評価される lazy を利用した。

**補足:**
「初期化のタイミングを object ロード時から実使用時まで遅延させることで、関心の分離を実現した」とも言える。セットアップ用のスクリプトはトークンの関心事の外にいるのに、同じ設定オブジェクトに同居しているだけで巻き添えを食らっていた、という構造的な問題。JVM の `<clinit>` が全 val を一括評価する仕組みがその根本原因。

## [2026-04-23] | モックテストの「意味の有無」を見分ける観点

**問いかけ:** モックベースで「件数だけ違う」テストが意味がある / 意味がないを分ける境界はどこにある？後輩から「テストケース分けたのにレビューで消されたのなんで？」と聞かれたら、「こういう観点で見分けられるよ」とどう説明する？

**自分の説明:**
返ってくる件数の違いを出すロジックが実際に動作している場合は意味がある、モックならば意味がないと考える。追加したテストが本当に意味のあるテストかどうかという観点で消すかどうかの判断。

**補足:**
核心は「**入力と出力の間で区別する処理が実際に一行でも走るか**」。当該ケースでは3点すべてが「動かないロジック」だった:
- モデル側に種別を示すフラグが無い（データを区別する手段が無い）
- 組み立て層に種別ごとの分岐が無い（挙動差分を生む処理が無い）
- モック境界が上位層のため、バージョンガード実装も観測できない

結果、context を分けても「モックで件数が違うリストを返す → そのまま通過する」だけで、プロダクションコードは何もしない。テストが観測しているのはテストデータ自身の差分のみ。「ロジックが走るか」という観点は、テストの命名やカバレッジ数字より信頼できる判断基準になる。

## [2026-05-25] | 共有スクリプトを patch せずラッパー方式に切り替えた判断

**問いかけ:** 今回「共有スクリプトを自動 patch + pre-commit hook で誤コミットを防ぐ」案ではなく「個人用ラッパースクリプトを別途用意する」案を選んだ。「なぜラッパーにしたの？」と聞かれたら、トレードオフを含めてどう説明する？

**自分の説明:**
共通ファイルである実行スクリプトを更新したくなかったため。

**補足:**
本質を捉えている。さらに構造で見ると:
- patch 案 = 「誤コミットしうる状態」を作って **仕組みで防ぐ** 設計（pre-commit hook が安全装置）
- ラッパー案 = 「誤コミットしうる状態」自体を **作らない** 設計（共有ファイルが無改変）

「安全装置で守る」より「危険な状態を生まない」方が常に強い。後者は安全装置が壊れた・外された場合のフォールバックも不要だから、運用上のリスクが構造的にゼロになる。

トレードオフは実行コマンドの手癖が変わること。これは README + alias で誘導可能で、構造的安全と引き換えに払って妥当。この「仕組みで防ぐ vs そもそも起きない設計」の対比は、認可・バリデーション・型設計など他の場面でも応用が効く判断軸。

## [2026-06-01] | 分散DBの基礎: アクティブ-アクティブ / シャーディング / リードレプリカ

**問いかけ:** 「冗長性（障害への強さ）」の観点で、リードレプリカとシャーディングはどちらが有利か。それを "各台が持つデータの違い" からどう説明する？

**自分の説明:**
冗長性に関してはリードレプリカ。すべての DB で同じデータがあるので、どれかぶっ壊れても担保できる。

**補足:**
正確。核心は「**各台が持つデータの中身**」で全部説明がつくという点。
- リードレプリカ = 全台が**同じ完全なデータのコピー** → 1台死んでも他が肩代わり可（冗長性◎）。ただし書き込みは分散できない（どこに書いても全台反映が必要だから）
- シャーディング = 各台が**違うデータの一部**だけ持つ → 書き込みを並列化できる（書込スケール◎・容量突破）。が、1シャード死ぬとその範囲が止まる（冗長性△）

この一連で繋がった全体像:
- **アクティブ-アクティブ** = 全ノードが書ける構成。「昇格（フェイルオーバー）」という概念自体を消し、切替ダウンタイム・切替時データロストをゼロにする
- **シャーディング**（書込スケール）＋**リードレプリカ**（読取スケール＆冗長性）の**併用**が大規模 RDB の王道。「各シャードにレプリカをぶら下げる」ことで互いの弱点を補完する
- マネージド分散 SQL（Aurora DSQL 等）の本質は新技術の発明ではなく "統合と隠蔽"。シャーディング＋レプリカ＋アクティブ-アクティブを全部内包し、開発者には単一論理 DB に見せる。だから「実質無制限のスケール」「極めて高い可用性」「フェイルオーバー不要」が成立する

判断軸として持っておくべき対比:
- 読取が重い → リードレプリカ
- 書込が重い / 容量が限界 → シャーディング
- 冗長性が欲しい → レプリカ（同一データのコピーがあるから）

## [2026-07-01] | コンテナ内 SSH known_hosts の恒久登録先

**問いかけ:** 「なぜ `~/.ssh` ではなく `/etc/ssh/ssh_known_hosts` に置いたの？」を、"参照ファイルが2系統に割れていた" という原因と結びつけてどう説明する？

**自分の説明:**
そこに置くことにより、どの環境でも ssh が常にそのディレクトリも合わせて読んでくれる。そのため環境依存が出ない。

**補足:**
本質を捉えている。`~/.ssh/known_hosts`（ユーザー依存）や別途用意したランタイム用ディレクトリ配下の `known_hosts`（経路依存）は「誰が・どの経路で」に左右される環境依存の参照先。`/etc/ssh/ssh_known_hosts` はシステム全体の共通参照先で、ssh がどの経路でも必ず併せて読む。つまり「2系統の食い違い」を*解決*したのではなく、問題が発生しうる土俵の外に出た。当初の「コンテナ内でも使えるように明示的にした」という理解は方向A（経路を1つに統一する発想）で、実際に採った方向B（指定に依存しなくする）とは別物 — この違いに自分で違和感を持てたのが good。

## [2026-08-02] | 学習ループ再設計 — この設計が最初に壊れる箇所 [MISS]

**判断点:**
停止を `AskUserQuestion` 呼び出しに置き換えたが、「そのツールを呼ぶ判断」自体は AI の意志に残る。
この設計で最初に壊れるのはどこか。

**予測:**
AI 側の仕組み（ツールやシステムプロンプト）が変わったら壊れる。

**実際:**
最初に壊れるのは**発火点の選定**。ツールは呼ばれるが、開示の**後に**呼ばれるようになる。

**差分:**
ツール依存の指摘自体は正しい。ただしその故障は**うるさい** — ツールが消えれば呼び出しがエラーになり、
挙動が変われば即座に見える。気付ける故障は危険度が低い。

見落としていたのは**静かに壊れる方**。AI は問いを立てる前に既に答えを持っていることが多く、
「ここが判断点だ」と気付く頃には説明を書き始めている。その状態でツールを呼ぶと、
ツール呼び出し・停止・journal 追記のすべてが成立するのに、
ユーザーは既に推論を読んでいるため事前予測の効果だけが抜け落ちる。
しかも「3タスクでエントリ3件」という検証指標は通ってしまう。順序違反は回数に現れないため。

同じセッションで同型の失敗を3件観測した:
- 旧 Protégé — 記録先不在で書き込みが消え、1ヶ月誰も気付かなかった
- コンテナの read_only bind mount — 追記失敗がエージェント内部で握り潰される
- 今回の順序違反 — 検証指標だけ通って中身が空になる

一般化: **騒がしい故障は放置してよく、静かな故障だけが本当に危ない。**
そして静かな故障は、検証指標が「回数」や「存在」を見ている限り必ずすり抜ける。
検証は順序や因果を見る設計にしないと機能しない。

## [2026-08-02] | PR衝突の解消方針と、残存リスクの「静かさ」判定 [MISS]

4択 = ①学習ログがPUBLIC追跡になる ②旧symlinkが残り続ける ③起動ラッパーがPATH未通しで動かない ④学習モードの発火下限が機構的に強制されていない。

②③はどちらも**騒がしい**側にある。

- ③は `command not found` で即死する。さらにこの起動ラッパーは、逆向きの設計（既定側から認証設定を抜く）
  だと「シェル統合が読まれなかったとき黙って別アカウントで動く」ため、**わざと騒がしい方**を選んだ設計だった。
  故障の可視性が設計目標そのものなので、これを最大リスクに置くと設計意図と矛盾する。
- ②は git が untracked 衝突で停止するか symlink を実ファイルで置換するかのどちらかで、移行元の実体は無傷。
  画面に何かが出て、復旧手段もある。
- ④は確かに静か。ただし後から機構を足せば回収できる。

見落としていたのは**もう1本の軸＝可逆性**。①だけが「起きた後に戻せない」。
PUBLIC リポジトリの git 履歴は、コミットを消しても fork・mirror・アーカイブ・既存クローンに残るため、
一度書けば取り消せない。しかも `.gitignore` から外れた瞬間、防御は rules に書かれた散文だけになり、
構造としては④と同じ「規約のみ・機構的強制なし」に落ちている。

一般化の更新: **「静か」だけでは足りない。静か × 不可逆が最悪の象限。**
静か×可逆は後から検知機構を足して回収できるが、静か×不可逆は初回で終わる。
リスクを並べるときは、可視性と可逆性の2軸で象限に置いてから優先順位を決める。

対策の方向: 抽象化ルールを散文から機構へ落とす（journal 差分を対象にした禁止パターン検査を
pre-commit / hooks 側に置く）。規約のままでは、疲れている日の1回で不可逆側に踏み込む。

### 何に注目すれば気づけたか

材料は最初の `git diff --stat` に出ていた。

```
.gitignore                    |   4 -
tasks/learning-journal.md     | 231 ++++++++
```

この2行が**セットで**出ているのが合図。「除外設定が減った」と「これまで追跡されていなかった
ファイルが大量に追加された」が同じ diff に同居している＝**追跡ポリシーの変更**が起きている。
片方だけなら誤検知もありうるが、両方揃えば断定してよい。

注目すべきは行数の非対称性。ポリシーの変更はたった4行で、600行超の計画書に埋もれる。
**diff の危険度は行数に比例しない。**

### 汎用化できる観察手順

1. **ポリシーファイルを最初に読む** — `.gitignore` / `.dockerignore` / 権限設定 / CORS /
   認証ミドルウェア / IAM ポリシー / `.env.example`。これらは「何を許すか」を定義する層で、
   小さい diff で境界を動かす。機能コードとは別パスでレビューする。
2. **各変更に undo コマンドを書けるか自問する** — 書けなければ one-way door。
   今回は3つ書けて（旧リンクは消して再実行、PATH は1行追加、発火下限は後から hook）、
   1つだけ書けなかった。**書けない項目が1つ見つかった時点で最優先が機械的に決まる**ので、
   判断力を使わずに答えが出る。疲れていても機能する形式なのが利点。
3. **防御の層の数を数える** — 変更前は3層（除外設定・別リポジトリへの隔離・抽象化規約）、
   変更後は1層（規約のみ）。多層防御が1層になった瞬間は、その1層がどれだけ丁寧に
   書かれていても危険度が跳ね上がる。しかも残った1層が「遵守に依存するもの」なら、
   それは防御ではなく**期待値**でしかない。
4. **書き込み主体を見る** — このログは AI が自動追記し、内容は業務セッション由来。
   「自動書き込み × 公開 × 業務由来」は継続的な漏洩チャネルであって、一度のレビューでは守れない。
   人間のレビューを経ずに公開先へ流れるパスがないかを探す。

### 肝になる知識: 公開 git 履歴が「消せない」実メカニズム

雰囲気ではなく具体的な経路がある。ここを知っていると①だけが別カテゴリだと即断できる。

| 経路 | なぜ消えないか |
|---|---|
| SHA 直参照 | ブランチを消してもオブジェクトは GC まで残り、SHA を知っていれば到達できる |
| PR の ref | ホスティング側が `refs/pull/N/head` を恒久保持する。**force push しても PR 由来の古いコミットは残る** |
| fork ネットワーク | fork 間でオブジェクトが共有保管され、元から消えても fork 経由で到達可能 |
| 既存クローン / ミラー | 手元・CI・社内ミラーに複製済み。中央からは制御できない |
| コード検索インデックス / scraper | push 直後に拾われ、削除は反映されない |

だから業界標準の扱いは「公開リポジトリに push した認証情報は、**履歴から除去するのではなく無効化する**」。
除去が信用できないことが前提になっている。

### メタ: 知識不足ではなく転移の失敗

「静かな故障だけが危ない」は前回のエントリで自分が書いた。**知識は既にあり、想起できなかった。**
実務ではこちらの失敗の方が圧倒的に多い。「知っている」と「その場で思い出せる」の間には溝があり、
負荷がかかるほど広がる。

対策は精神論ではなく外部化。上の手順2・3をチェックリストにしてレビュー時に必ず通す。
——今回の教訓そのものと同じ構造で、**規約（覚えておく）ではなく機構（必ず通る手順）にしないと守れない。**

## [2026-08-03] | 宣言ファイルと実環境の整合性チェックが落ちる原因の切り分け [MISS]
`#dotfiles` `#検証設計` `#サプライチェーン`

**判断点:** パッケージ宣言ファイルと実環境の整合性チェックコマンドが失敗する。どう解消するか。

**予測:** バージョン固定をしていないのだから、一括 upgrade すれば解消する。

**実際:** upgrade では解消しなかった。全パッケージを最新にして「更新可能なもの一覧」が空になった後も、チェックは落ちたままだった。

**差分:**

### そのチェックコマンドは2つの別問題を1つの終了コードに畳んでいる

| 問い | 意味 |
|---|---|
| 宣言されたものがインストール済みか | 環境の**再現性** |
| 最新か | メンテナンスの**鮮度** |

upgrade は後者しか動かせない。そして残った失敗は、実は**どちらでもない第3の状態**だった。サードパーティ配布元が「未信頼」のため、パッケージマネージャが**鮮度を判定できなかった**。インストールは済んでいる。ただ「最新かどうか分からない」だけ。それが「未充足」として報告されていた。

### 「判定不能」は「問題なし」ではなかった — 本物の更新漏れを隠していた

信頼を宣言して評価可能にした直後、**そのパッケージは実際に古かった**（パッチ1つ分）。

決定的なのはここ。未信頼の間、「更新可能なもの一覧」を出すコマンドは**空を返していた**。全パッケージを更新した直後だったから、当然「全て最新」に見えていた。信頼宣言の後に同じコマンドを叩くと、そのパッケージが現れた。

つまり未信頼の間、対象は鮮度チェックの網から静かに外れており、**「全て最新」という表示自体が嘘だった**。更新漏れがセキュリティ修正だったら、気づく手段が無い。

一般化すると: **「評価できなかった対象」を集計から除外して結果を返す仕組みは、除外した事実を結果の中で表現できないと嘘をつく。** 母数が縮んだことを呼び出し側に伝えない集計は全部この形をしている。0件を返すクエリ、フィルタで落ちたレコード、タイムアウトしたヘルスチェック。「0件でした」と「0件かどうか分かりません」を同じ出力に畳んではいけない。

なお当初この件を「インストール済みで古くもない、判定できないだけ」と整理したが、それが誤りだった。**警告を「実害はなさそう」と読んだ時点で同じ罠に踏み込んでいる。**「判定不能」は安全側の情報ではない。

### 一般化: 「判定不能」を「不合格」に畳む設計は、症状から対処法を逆算できなくする

出力は「インストールまたは更新が必要」。実際に必要だったのは**配布元の信頼宣言**で、インストールでも更新でも解決しない。メッセージが指す対処法が、真の対処法と無関係になっている。

だから対処の順序はこうなる。**エラーメッセージが提案する対処を試す前に、そのチェックが何を検査して終了コードを決めているかを確かめる。** メッセージは「検査に落ちた」ことしか正確に伝えておらず、「なぜ落ちたか」は往々にして推測で書かれている。今回、素直に upgrade を実行していたら、33パッケージを更新した上で同じ失敗を見ることになった（実際そうなった）。

### 検証コマンドを選ぶときの基準

再現性と鮮度は分けて実行する。混ぜると、コードを1行も変えていないのに時間経過だけで赤くなる検証ができあがる。赤が常態化すれば誰も見なくなり、**本当に環境が壊れているときの失敗を見逃す**。CI に載せる検証コマンドは「変更がなければ永遠に緑であり続けるか」を必ず確認する。

### 予測に含まれていなかった観点: 既定値の変化は「自分は何もしていない」ときに効いてくる

未信頼は、パッケージマネージャのメジャーバージョンアップで**非公式配布元が一律 untrusted に変わった**ことによる。設定を触っていなくても、ツール側の既定値変更で昨日まで通っていたものが落ちる。「自分は何も変えていないのに壊れた」ときは、依存ツールのメジャーバージョン更新履歴を最初に見る。

**予測:** 設定ディレクトリの存在で導入を検知して分岐する（無条件作成でも、オプトインフラグでもなく）。

**実際:** 同じ。未導入マシンに設定ファイルを先回りで生やすと、そのホストの初回起動時の状態が読めなくなる。フラグ方式は指定忘れが無言の未配線に直結する。

リンク定義が1対1だった前提のもとで、退避処理がバックアップの保存名を**ソース名**から導出していた。1対Nに拡張した瞬間、同一ソースを異なる名前で複数箇所へ配ると、退避先のパスが衝突して先に退避した方が黙って上書き消失する。保存名をソース側ではなく**宛先パス**から導出することで解消した。

一般化: **多重度を 1 から N へ広げる変更では、「1 であることに依存した命名・キー生成」を全て洗い出す。**この種の前提はコード上に明示されないため、型でもテストでも捕まらないことが多い。

## [2026-08-05] | IaC リポジトリのオンボーディング（構成把握とメモリ化）

**判断点:** 静的サイト配信の IaC リポジトリを初見で読み、「次に触る人が最初に事故る箇所」を
1つ選んで永続メモリに残す。選択を誤ると、後続の全員が同じ地雷を踏む。

### 予測 1（HIT）

**予測:** 「DNS が IaC 管理外」。DNS 定義ファイルは拡張子を外して無効化され、
コメントは実在しないファイルを参照し、lock ファイルには宣言のない provider が残っている。

**実際:** 一致。履歴を追うと、無効化はリネームによるもので、コメントが指すファイルは
**一度もコミットされていなかった**。lock への provider 追加は同じコミットに含まれており、
ローカル限りの設定で init された痕跡だった。

**予測に含まれていなかった観点:** ファイルから読み取れるのは「定義が無い」ことまでで、
**事故の向きを決めるのは state 側に何が残っているか**である。

```
定義なし × state あり  → 次の plan が destroy を出す（危険）
定義なし × state なし  → lock の残骸なだけ（無害）
```

この2つは影響が正反対なのに、**リポジトリを何度読んでも判別できない**。
だから残すべき知識は「定義が無い」という事実ではなく、
「着手前に state の在庫を実測する」という**手順**になる。

### 予測 2（部分一致）

**判断点:** state ロック機構が存在しない構成で、apply が中断したとき最初に何を見るか。

**予測:** リモートに保存された state を見る。

**実際:** 入口としては正しい。apply 中も一定間隔で中間 state が永続化されるため、
state は進捗をほぼ保持している。ロックが無いので解除操作も不要（皮肉な副作用）。

**欠けていた観点:** **state は「IaC が知っていること」しか映さない。**
中断時の本当の敵は、実インフラには作られたのに state に載っていない孤児リソース。
突合対象は state 単体ではなく `state ↔ 実体` の差分である。

**実務でどう事故るか:**
中間永続の隙間で落ちると、実体はあるが state に無いリソースが生じる。
次の plan は「新規作成」を出し、**plan は綺麗に通るのに apply だけ名前衝突で落ちる**。
名前が固定のリソース（グローバル一意名、エイリアス、ポリシー名）ほど顕著。
plan の成功が安全を意味しないケースで、原因特定に時間を食う。

なお `refresh` 系の操作は state にある物しか照会しないため、**孤児の発見には使えない**。
「差分を取る」という発想でこの操作に手が伸びるが、対象集合がそもそも state 側だけである。

### 一般化: 前回と同じ盲点が出た

直前のエントリで書いた「リポジトリを読んでも見つからない層」が、
別の形で再出現した。今回の内訳:

```
リポジトリから読み取れる層:
  定義ファイルの有無 / コメント / lock の記載

リポジトリから読み取れない層（実測が要る）:
  [a] state の在庫          → 定義の欠落が destroy になるか無害かを決める
  [b] 実インフラの在庫       → 孤児リソースの有無を決める
  [c] 実行環境の資格情報     → そもそもコマンドが起動するかを決める
  [d] state 保管先の設定     → 壊れた state を巻き戻せるかを決める
```

[c] は実際に確認して判明した。provider 定義に認証プロファイル名が直書きされており、
**作業端末にそのプロファイルが存在しなかった**。つまり読解した内容を検証する手段が
最初から無い状態だった。環境変数による上書きも効かない（設定ファイル側の指定が優先される）。

[d] も同様。state の保管先は、chicken-and-egg のため IaC 自身のコードでは管理されない。
結果として**バージョニングの有無がコードから判定できず、「壊れた state を巻き戻す」という
復旧手段が存在するのかどうかすら不明**になる。復旧計画の前提が可視化されていない。

**教訓:** オンボーディングの成果物に書くべきは、読んで分かった構造ではなく
**読んでも分からなかったことを埋める手順**である。前者は次に読む人も同じ労力で再取得できるが、
後者は実測しない限り誰も気づかないまま危険な操作に進む。

**副次的教訓:** 認証情報がコードに直書きされていると、
「設定を読む」と「設定を検証する」の間に環境依存の壁ができる。
レビューは通るが手元で再現できない、という状態を作り出す。

## [2026-08-05] | OSS のバグ調査から報告まで（記事化と学びの抽出を含む）

前段は同日の別エントリ（不在の主張には探索空間の根拠が要る）の続き。
調査が upstream への報告まで到達したので、その過程での判断点を記録する。

### 判断点 1: 調査体験を記事にするとき、字数の都合で削っても最後まで残すべきものは何か

**予測:** 空振りした過程と誤った仮説。→ **一致**

**予測に含まれていなかった観点:**
「失敗を残す」の理由として普通に想像されるのは**謙虚さや読み物としての面白さ**だが、
今回はもっと強い理由がある。**失敗の記録が、結論の信頼性を担保する唯一の証拠になる。**

この種の記事の結論は抽象化された主張になる。だが抽象化された主張は、読者からすると
**どこまで検証されたのか分からない**。「たまたま思いついた綺麗な説明」と
「証拠に追い詰められて到達した説明」は、文章としては見分けがつかない。

そこで効くのが、その抽象化に到達するまでに**何を棄却したかの記録**である。
誤った切り分けで報告しかけ、差し戻され、判定側は将来対応済みだと判明して
切り分けが変わった——この経緯があれば、読者は結論が消去法で残ったものだと確認できる。

一般化: **失敗の記録は反証可能性の代わりになる。**
だから削れないのは「失敗があったこと」ではなく **「何を棄却したかの具体」**。
「回り道した」とだけ書くのは、書かないのとほぼ同じ。

### 判断点 2: 今回の学びのうち、別プロジェクト・別チームに最も持ち出せるのはどれか

**予測:** 検査不能と異常なしを同じ状態にしない（silent failure）。→ **一致**

**予測に含まれていなかった観点（3段）:**

**(1) これはエラーハンドリングではなく状態モデルの設計ミス。**
問題のコードは `if not result or not result.get("found"):` で
「呼び出しが失敗して None」と「呼び出し成功・検出ゼロ」を同じ分岐に畳んでいた。
必要な状態は3つ——**①検査した→問題なし ②検査した→問題あり ③検査できなかった**。
`try/except` を足しても直らない。型と状態の設計の問題である。

**(2) 畳み込む方向に非対称性がある。**
③を②側（問題あり）に倒せばノイズは出るが危険ではない。①側（問題なし）に倒すと危険。
状態を畳まざるを得ないときは**うるさく失敗する側へ倒す**。

**(3) silent failure の発見しにくさは、その仕組みへの依存度に比例する。**
「異常なし」と言うチェックは、まさに誰も見に行かないチェックである。
だから silent failure が集中するのは、**成功時の出力が「何もしていない」と
見分けがつかない仕組み**——検査系、バックアップ、アラート、レート制限、
そして本 journal の間隔反復機構（backlog に「出題がなくても正常に始まるため
誰も気づかない」と書いたもの）。まったく同じ構造が別の場所で再出現している。

一般化: 「エラーを握り潰すな」より一段強く言える。
**成功が沈黙で表現される仕組みには、動作していることの信号を先に設計する。**

### 副産物: 同じツールを2つのテストで測ったら評価が正反対になった

パターン検査の検出率を2通りの作り方で測った。

```
ルール実装を読んでからケースを書いた   → 検出率 94%
仕様が謳う脆弱性クラスから逆算した     → 検出率  0%
```

前者だけなら「優秀なツール」で終わっていた。

**実際:** 同じ判断。決め手は脅威モデルの切り分けだった。
敵対的な相手には効かない（迂回路が無限にある）が、
**普通に作業しているエージェントが悪意なく目立つ経路で漏らす**ケースには効く。
後者が現実に起きる方で、そこには有限個の経路しかない。

なお実装では、禁止の**理由**をメッセージに書いた。単に禁止とだけ伝えると
別経路を探されるが、目的を伝えれば協調的な相手は迂回しない。
「禁止は経路を変えるだけ」は敵対者を想定した命題で、協調者には別の対処がある。

**差分（予測に含まれていなかった観点）**

**この判断は、防御の粒度をコマンド単位からフラグ単位へ下ろす。**

そして素直に実装すると、危険なフラグを列挙する形（denylist）になる。
だが**その1つ前の判断で、まさに denylist を捨てて allowlist を選んでいた**。
理由は「新しいものが追加されたとき黙って通るのを避ける」ため。
粒度が変わった途端、同じ失敗の形が新しい場所で再発する。

避けられる。「安全と分かっているフラグ以外が付いていたら止める」と書けば
allowlist になる。だが**気づかなければ自然に denylist になる**。

一般化: **基準は判断とセットで記憶されるので、対象が変わると自動では適用されない。**
直前に「なぜその形にしたか」を言語化していても、粒度や対象が変わると
新しい判断として立ち上がり、また素直な方（＝多くの場合 denylist）に落ちる。

### 欠けた軸: 失敗モード

新しい粒度での壊れ方を数えていなかった。
1つ前の判断で得た「壊れ方の向きを選ぶ」という基準を、持ち越せていない。

**次に同種の判断で確認する問い**: 防御を別の粒度・別の対象へ広げるとき、
**直前に採った基準を1回声に出して、新しい粒度でも成立するか確かめる。**

### 副産物: 「囲めないもの」は防御の設計ではなく前提の記述として残す

ファイルとして存在するものは、任意のコマンド・任意の言語から読める。
コマンド文字列を見る層では原理的に囲めない。

ここを曖昧にすると、部分的な防御が「対処済み」に見える。
実装には含めず、囲めない範囲と、別の層で決めるべき選択肢を課題として書き出した。

一般化: **防御の限界は、防御そのものと同じ場所に書く。**
別の場所に書くと、防御を見た人が限界を見ない。

## [2026-08-09] | 落ちたテストが偶然カバーしていたもの

### 判断点: 環境依存のテストを個別に直すか、ハーネスの既定値を変えるか

**予測:** 再発防止を優先し、ハーネスの既定値を変える

**実際:** 同じ判断。1件だけ直すと、同じ形のテストを次に書いた人が同じ罠に落ちる。
テストの前提は個々のテストではなくハーネスが持つべきもの。

**差分（予測に含まれていなかった観点）**

**落ちていたテストは、本体の未検証な経路を偶然カバーしていた唯一のテストだった。**

本体には「引数で渡されなければ、プロセスの現在位置を使う」というフォールバックがある。
テストが環境依存だったのは、テストの書き方の問題である以上に、
**このフォールバックが露出しただけ**だった。

そして既定値を中立化すると、その経路を通るテストが1つも無くなる。
再発は防げるが、**同時に唯一の観測窓を塞ぐ**。

対処として、フォールバックの現在の挙動を明示的なテストとして固定し、
設計の是非は課題として登録した。

一般化: **落ちるテストは、意図していなかった何かを測っていることがある。**
テストの前提を変えるときは、そのテストが偶然カバーしていたものを1つ挙げる。
「壊れているから直す」で消すと、壊れていた理由の方が消える。

### 欠けた軸: 失敗モード

修正案そのものの副作用を数えていなかった。
「環境依存を消す」修正は「環境依存を観測していた経路も消す」。

**次に同種の判断で確認する問い**: テストの前提や既定値を変えるとき、
**その変更で観測できなくなるものを1つ挙げる。**

### 副産物: 1つの環境で確認して一般化していた

そもそもこの不具合は、作業を feature ブランチ上でだけ行い、
「全パス」と報告したことで見逃された。判定材料にチェックアウト中のブランチが
入っていたため、環境を変えた瞬間に結果が変わった。

修正の検証では、同じ環境（main のチェックアウト）で修正前後を走らせ、
片方が落ちて片方が通ることを確認した。

一般化: **「通った」の報告には、どの環境で通ったかが含まれる。**
環境が判定材料に入りうる対象では、環境を変えた再実行までが検証。

## [2026-08-09] | 調査中に出てきた傍証を成果物に入れるかの判断

### 判断点: 自分の報告の2日後に第三者が同じ不具合を独立に報告していた事実を、記事に載せるか

**予測:** 載せない。「他人も報告した」は自己肯定の材料になりやすい。

**実際:** 載せない（判断をそのまま採用）。文書の主旨が「失敗の記録は反証可能性の代わりになる」
である以上、自分の正しさを補強する材料は主旨と逆方向に働く。

**差分（一致。予測に含まれていなかった観点）**

捨てる判断は妥当だが、**同じ事実には別の使い道があった**。
「独立した2人が数日内に同じ箇所を踏んだ」は、著者の正しさの証拠ではなく
**その構造が再現的に同じ障害を生むことの証拠**になる。主語を自分から構造へ移せば、
自己肯定にはならない。

一般化: **傍証を評価するときは「誰が正しかったかの証拠」と「何が起きやすいかの証拠」を
分けて見る。** 前者としてだけ読んで捨てると、後者の証拠も一緒に捨てることになる。
今回の文書には「列挙で書かれた箇所は次のリリースで壊れる」という構造側の主張が既にあり、
そこの裏付けとしてなら主旨と同方向に使えた。

判断そのものは変えない。観点として記録しておく。
