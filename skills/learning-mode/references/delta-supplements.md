## 概念名の供給

**判断が属する一般的な概念名を1つ与え、1文で説明を添える。**

差分を返すだけでは、その判断が「今回限りの話」に見える。
名前が付いていれば、後から自分で調べられるし、別の文脈でも思い出せる。

```
概念: fail-open / fail-close。異常が起きたとき、防御機構が処理を通すか止めるかの区別。
      fail-openは異常時にチェックせず処理を通すので、安全装置として数えてはいけない。
```

**規則**

- **1つだけ。** 3つ並べると、どれも定着しない
- **必ず1文の説明を添える。** 説明を書けない名前は出さない。
  説明を添えれば、捏造した名前はその場で見抜ける
- **説明済みの概念を再掲しない。** 同じ名前が2回目なら書かない
- 名前の無い判断もある。**無いのに作らない**。その回は概念行ごと省く

**書いてよい / いけない**

| | 例 | 理由 |
|---|---|---|
| 書いてよい | 概念・パターン・障害モードの**一般名** | 検索でき、説明が正しいかを自分で確かめられる |
| 書いてはいけない | 書籍名・記事名・URL・章番号・論文の著者名 | **捏造が起きるうえに、権威があるように見えて疑われにくい** |

固有名詞のリソースが必要になったら、提示する前に検索して実在を確認する。
確認できなければ出さない。

## 定石の供給

**判断に付随する、コードレベルの書き方を1つ添える。** 該当が無ければ省く。

`概念` は判断の一般名で、`定石` は具体的な書き方を示す。役割が違うので両方を置く。
判断点をL2以上で取る運用（→ `rules/learning-mode.md`）にしたため、
**設計PredictでL1の書き方を伝えられるのはこの欄だけ**になった。コード学習は、
ユーザーが自分で手を動かす別の経路なので、同じ内容を二重に出題・解説しない。

```
概念: 貫通する関心事（cross-cutting concern）。全レイヤーを上から下まで通して渡す依存のことで、
      後から足すコストが層の数に比例する。
定石: 実行コンテキストは第1引数で受け取り、構造体に保持しない。
      保持すると生存期間がオブジェクトに引きずられ、キャンセルが伝播しなくなる。
```

**規則**

- **1つだけ。** `概念` と合わせて2つが上限
- **「こう書く」と「そうしないと何が起きるか」をセットで書く。**
  理由の無い定石は適用範囲が分からないので、次の文脈でそのまま誤用される
- **コードを伴わない判断（運用手順、設定の配置、ドキュメント構成）では省く。**
  無理にひねり出さない。省いた回は `定石` 行ごと出さない
- 書籍名・記事名・URLを出さないのは `概念` と同じ（→「概念名の供給」の表）

**言語やライブラリのバージョンで振る舞いが変わる定石は、出す前に一次ドキュメントで確認する。**
確認できなければ出さない（→ `rules/proving-absence.md`）。

## 次の問いの立て方

欠けた軸から**機械的に導出**する。何を勉強すべきかを自由に発想しない。

軸名と「今回何が抜けたか」は評価パートで述べ終えている。
ここに書くのは**次回の行動だけ**（→ ADR 0007 D4）。

**必須の形式**

> **次に同種の判断で確認する問い**: [次に同種の判断をするとき、選択の前に済ませる確認]

たとえば次のように書く。

> **次に同種の判断で確認する問い**: 案を選ぶときは
> 「捨てた案の長所を1つ言う」を選択の前に済ませる。

**この文字列は変えない。** `次に同種の判断で確認する問い` は、
過去エントリから判断原則を引くときのgrepキーである。
表記を変えると、過去49件とつながらなくなる（→ `../SKILL.md`「過去の判断原則を接続する」・ADR 0001 D8）。

**禁止**
- 軸名や「今回何が抜けたか」を再掲すること（評価パートと重複する）
- 書籍名・記事名・URL・章番号を出すこと（→「概念名の供給」の表を参照）
- 「設計力を鍛えましょう」「トレードオフを意識しましょう」のような一般論。
  行動に移せないので、読んだそばから忘れられる
