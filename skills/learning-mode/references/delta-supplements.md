## 概念名の供給

**判断が属する一般的な概念名を1つ与え、1文で説明を添える。**

差分を返すだけでは、その判断が「今回限りの話」に見える。
名前が付いていれば、後から自分で調べられて他の文脈でも呼び出せる。

```
概念: fail-open / fail-close — 防御機構が異常時にどちらへ倒れるか。
      fail-open は「壊れたら素通し」なので、安全装置として数えてはいけない。
```

**規則**

- **1つだけ。** 3つ並べるとどれも定着しない
- **必ず1文の説明を添える。** 説明を書けない名前は出さない。
  説明が付いていれば、捏造した名前はその場で露見する
- **既に説明済みの概念を再掲しない。** 同じ名前が2回目なら書かない
- 名前が無い判断もある。**無いのに作らない**。その回は概念行ごと省く

**書いてよい / いけない**

| | 例 | 理由 |
|---|---|---|
| 書いてよい | 概念・パターン・障害モードの**一般名** | 検索可能で、説明の正しさが自分で検証できる |
| 書いてはいけない | 書籍名・記事名・URL・章番号・論文の著者名 | **捏造する上に、権威的に見えて疑われにくい** |

固有名詞のリソースが必要になったら、提示する前に検索して実在を確認する。
確認できなければ出さない。

## 定石の供給

**判断に付随する、コードレベルの書き方を1つ添える。** 該当が無ければ省く。

`概念` が「判断の一般名」なのに対し、`定石` は「手の動かし方」。役割が違うので併存させる。
判断点を L2 以上で取る運用（→ `rules/learning-mode.md`）にした結果、
**設計Predict内でL1の書き方を渡す経路はここ**。コード学習は別の能動的な経路であり、
同じ内容を二重に出題・解説しない。

```
概念: 貫通する関心事（cross-cutting concern） — 全レイヤーを縦に貫いて渡す依存で、
      後から足すコストが層の数に比例する。
定石: 実行コンテキストは第1引数で受け取り、構造体に保持しない。
      保持すると生存期間がオブジェクトに引きずられ、キャンセルが伝播しなくなる。
```

**規則**

- **1つだけ。** `概念` と合わせて2つが上限
- **「こう書く」＋「そうしないと何が起きるか」をセットで書く。**
  理由の無い定石は適用範囲が分からないため、次の文脈でそのまま誤用される
- **コードを伴わない判断（運用手順、設定配置、ドキュメント構成）では省く。**
  無理に捻り出さない。省いた回は `定石` 行ごと出さない
- 書籍名・記事名・URL を出さないのは `概念` と同じ（→「概念名の供給」の表）

**言語やライブラリのバージョンで振る舞いが変わる定石は、出す前に一次ドキュメントで確認する。**
確認できなければ出さない（→ `rules/proving-absence.md`）。

## 次の問いの立て方

欠けた軸から**機械的に導出**する。何を勉強すべきかを自由に発想しない。

軸名と「今回何が抜けたか」は評価パートで既に述べている。
ここに書くのは**次回の行動だけ**（→ ADR 0007 D4）。

**必須の形式**

> **次に同種の判断で確認する問い**: [次に同種の判断をするとき、選択の前に済ませる確認]

例:

> **次に同種の判断で確認する問い**: 案を選ぶときは
> 「捨てた案の長所を1つ言う」を選択の前に済ませる。

**この文字列は変えない。** `次に同種の判断で確認する問い` は
過去エントリから判断原則を引くときの grep キーであり、
表記を変えると過去49件との接続が切れる（→ `../SKILL.md`「過去の判断原則を接続する」・ADR 0001 D8）。

**禁止**
- 軸名や「今回何が抜けたか」を再掲すること（評価パートとの重複）
- 書籍名・記事名・URL・章番号を出すこと（→「概念名の供給」の表を参照）
- 「設計力を鍛えましょう」「トレードオフを意識しましょう」のような一般論。
  行動に変換できないため、読んだ次の瞬間に消える
