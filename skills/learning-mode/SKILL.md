# 学習モードの詳細手順

このskillは常時ruleの発火判定を通過した後に読む。
上限・開示順・保存の正本は `rules/learning-mode.md` の「両学習モードの共通方針」である。
ここでは手順と書式だけを扱う。

## ループ

```
[1] 予測フェーズ  判断点で、答えを出す前に対話ツールで「どの結論を採るか」を選ばせる
[2] 理由フェーズ  選択の直後に「なぜそれを選んだか」を自由記述で問い、メッセージを終える
[3] 開示フェーズ  こちらの答え・調査結果・実装方針を提示する
[4] 差分フェーズ  ★ Delta で結論の差分を返し、判断基準を固定3軸で評価する
```

**順序が本質。** 開示してから問うと再読になり、事前に予測させる効果が消える。

**[1] と [2] を分けるのが本質。** 選択肢に判断基準を書き込むと、
ユーザーは「同意するか」を答えるだけになり、何も想起しない。
判断基準は**ユーザーが自分の言葉で生成したものだけ**が記録と評価の対象になる。

## 対象領域

| 領域 | [1] で選ばせるもの | [2] で問うもの |
|---|---|---|
| 設計判断 | A案かB案か | なぜそちらを採ったか |
| 原因分析 | どのレイヤーを疑うか | どの根拠を重く見たか |
| レビュー力 | 最も重いリスクはどれか | なぜそれを最上位に置いたか |
| 実装方針 | どの方針で書くか | どの制約を効かせたか |

**評価対象は [2] の回答。** [1] の正誤は文脈依存で転移しないが、
[2] で言語化された基準は次の判断へ転移する。

判断基準を問う形に置き換えられない問いは、そもそも判断点ではない。

## 予測フェーズ

常時ruleの停止手段で問う。

- 選択肢は2〜4個。自由記述は「Other」（自動付与されないホストでは「上記以外」を明示）で受ける
- 選択肢には互いに排他的な立場を置く（「どちらとも言える」を選ばせない）

### 選択肢には「結論」だけを置く。判断基準を書き込まない

**ラベルに判断基準を書くと、想起すべきものを選択肢が開示してしまう。**
ユーザーは同意するかを答えるだけになり、何も検索しない。

```
禁止  A) 実装コストを優先し、まず計測で当たりを付ける
      B) 恒久対応を優先し、データアクセス層から直す
      ↑ 「実装コストを優先」「恒久対応を優先」が判断基準。これを渡してはいけない

正しい  A) まず計測で当たりを付ける
        B) データアクセス層から直す
```

判断基準は次の「理由フェーズ」で、ユーザー自身の言葉で取る。

**`description` にも基準を書かない。** 書いてよいのは、その案を採ると
**何が起きるか**（事実）だけ。**なぜ採るか**（評価）を書いた時点で答えを渡している。

### 選択肢は competitive にする

**すべての選択肢が実際に成立しうるものにする。** 数合わせで明らかな捨て案を混ぜない。

もっともらしい誤答が並んでいると、ユーザーは正解を想起するだけでなく
「なぜ他が誤りか」も想起する必要が生じ、そこで初めて選択式が学習として機能する。
逆に捨て案が混ざると、消去法で解けてしまい想起が起きない。

事故の実例: `learning/entries/2026-08-13-フックのタイムアウト値をどう決めるか-4.md`。
選択肢を3つ揃えるために「防御の確実性を優先して元の値に戻す」案を出したが、
対象のフックは fail-open が確定していたため**存在しないトレードオフ**だった。

### 推奨を明示しない

**予測フェーズでは `（推奨）` を付けない。推奨案を先頭に置かない。**
予測を取る前に正解を明示するのは、事前予測の前提そのものを壊す行為。

なお**予測フェーズ以外**（純粋に実装方針の承認を取るだけの場面）では
既定ガイダンスどおり推奨を明示してよい。

## 理由フェーズ

選択が返ってきたら、**次のメッセージで理由だけを問い、そこでメッセージを終える。**

> なぜ A を選んだ？

停止の質を守るため、問いの後に次を書いてはいけない。

- 回答例・書き出しの提示
- **励ましに偽装したヒント**（「〜を考えてみて」「〜の観点で」「〜と比べると」）
- 複数の質問を並べること（1メッセージ1問）
- 括弧書き・斜体による示唆

書いてよいのは内容を含まない一言だけ。

> （外していい）
> （パスしてもいい）

**選択肢は必ず再掲する。** 対話ツールの選択肢は回答後に画面から消えるため、
理由を書く時点で「何と何を比べたか」が見えなくなる。比較対象が見えない状態で
書かれた理由は選んだ案の利点だけを述べたものになりやすく、
**トレードオフ軸が構造的に埋まらなくなる**。

- 再掲するのは**選んだ結論と、他の選択肢のラベル・`description`**
- これはヒントに当たらない。既に提示済みの情報であり、`description` には
  「何が起きるか」しか書かない規約なので判断基準を含まない
- 再掲は箇条書きにとどめ、**補足・比較・評価を足さない**（足した時点でヒントになる）

**「Other」が選ばれた回**は、こちらの選択肢設計が狭かったサインとして扱い、
★ Delta で「その結論を候補に入れられなかった理由」に触れる。

## ★ Delta

```
★ Delta ───────────────────────────────────────
予測: [選んだ結論と、理由フェーズで返ってきた判断基準を原文のまま]
実際: [実際の判断・原因・リスク]
差分: [結論に対する差分。下表に従う]
評価: [欠けていた軸だけを名指しする。全て埋まっていれば下記「全軸が埋まっていた場合」]
概念: [この判断が属する一般的な概念名を1つ ＋ 1文の説明。→ `references/delta-supplements.md`]
定石: [その判断に付随するコードレベルの書き方を1つ。該当が無ければ省く。→ `references/delta-supplements.md`]
次の問い: [次に同種の判断で確認する問い。1文。→ `references/delta-supplements.md`]
─────────────────────────────────────────────────
```

### 過剰帰属の禁止

**ユーザーが実際に表明していない理解を、表明したことにしてはいけない。**

「何が起きるか」を述べたが「なぜそうなるか」を述べていないなら、
**因果の理解を認めずに「何が」の部分だけを認める**。
言っていないことを補って褒めると、本人は理解できているつもりのまま先へ進む。
これは無指摘より害が大きい。

### 過去の判断原則を接続する（該当があれば）

★ Delta を書く時点で、`learning/entries/` に**同型の判断原則**が既にあれば接続する。

```bash
grep -l '^axis: "失敗モード"$' learning/entries/*.md   # 同じ軸が欠けた回
grep -rl '<判断の型を表す語>' learning/entries/         # 同種の判断
```

- **必ず ★ Delta の中で行う。予測を取る前に出してはいけない**（答えを渡すことになる）
- 過去エントリを**そのまま再出題しない**。当時の文脈はもう再現できない。
  取り出すのは末尾の「次に同種の判断で確認する問い」＝**文脈から剥がした判断原則**だけ
- 該当が無ければ何も書かない。無理に結び付けない

### 結論に対する差分

| 予測の結果 | 返し方 |
|---|---|
| 一致 | 一致を認めた上で、**予測に含まれていなかった観点**を1つ名指しする |
| 部分一致 | 欠けていた観点 ＋ **それが実務でどう事故るか**の具体例 |
| 不一致 | 正解を直接言わず、**その予測が破綻する反例**を1つ出す |

### 判断基準に対する評価（3軸・固定）

**軸は増やさない。自由な講評をしない。**
評価を自由文で書ける限り「良い観点ですね」への追従は必ず出る。
軸ごとに「埋まっているか」を判定する形式にして、こちらの裁量を残さない。

| 軸 | 判定すること | 欠落時に実務で何が起きるか |
|---|---|---|
| トレードオフ | **何を捨てたか**を言えているか | 捨てたものを言えない選択は、比較していない。最初に思いついた案を追認しただけになる |
| 失敗モード | 選んだ案が**どう壊れるか**を言えているか | 壊れ方を知らない案は、壊れてから原因究明を始めることになり、復旧時間が読めない |
| 前提の検証 | 根拠が**確認済みの事実か推測か**を区別しているか | 推測を事実として積むと、推論が正しくても結論が外れる。しかも間違いに気づく契機がない |

**軸を名指ししたら、その回で具体的に何が抜けたかを続けて書く。**
軸名だけでは一般論になり、次の行動に変換されない。
（この「具体的に何が抜けたか」は以前 `学習領域` 側にも書いていたが、
同じ内容を2箇所に書くことになるため評価パートへ集約した。→ ADR 0007 D4）

**全軸が埋まっていた場合**: 無指摘で終えない。**その判断基準が通用しなくなる条件**を1つ示す。
基準は必ず適用範囲を持つので、範囲の外側を1つ挙げれば必ず何か言える。
記録では `axis: "全軸充足"` とし、本文に `### 基準が破れる条件` の見出しを置く
（見出しが無い `全軸充足` は記載漏れとして扱う。→ `learning/README.md`）。

**禁止**
- 「その通り」「正解」「良い観点ですね」だけで終えること
- 3軸すべてに講評を付けること（冗長になり、指摘の焦点が消える）。**欠けている軸だけ**を名指しする
- 軸を勝手に増やす・言い換えること（記録の集計可能性が壊れる）

差分フィードバックがこの機構の本体であり、ここを省くと機構全体が無意味になる。

## ★ Delta の補足欄

`概念`・`定石`・`次の問い` を書く前に `references/delta-supplements.md` を読む。

## 記録

★ Deltaを返し、ユーザーが実際に示した判断と理由がある場合だけ、専用学習storeへ
`kind: "decision"` の新形式recordを保存する。結論のhit/missだけを能力証拠にせず、固定3軸、
支援、開始契機、検証、未確認事項を本文へ残す。旧 `learning/entries/` は読み取り専用の履歴である。
schemaと移管境界は `learning/README.md` を参照する。

### 抽象化ルール（セキュリティ要件）

このリポジトリは **PUBLIC**。エントリの作成前に必ず以下を満たすこと。

**禁止**
- 社名・組織名・プロジェクト名・リポジトリ名
- 内部ホスト名・内部URL・エンドポイント
- テーブル名・カラム名・内部ファイルパス
- 業務コードの直貼り

**必須**
- 技術的本質のみを一般化して書く。具体例は最小再現形に置き換える
- 判断に迷ったら書かない

## 迷ったとき

判定の回避パターンは `references/rationalizations.md` を読む。
