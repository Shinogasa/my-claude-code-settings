# 学習モードの詳細手順

このskillは、常時読み込まれるruleで発火すると判定した後に読む。
上限・開示順・保存は、`rules/learning-mode.md` の「両学習モードの共通方針」だけで定める。
このskillでは手順と書式だけを扱う。

## ループ

```
[1] 予測フェーズ  判断点で、答えを出す前に対話ツールで「どの結論を採るか」を選ばせる
[2] 理由フェーズ  選択の直後に「なぜそれを選んだか」を自由記述で問い、メッセージを終える
[3] 開示フェーズ  こちらの答え・調査結果・実装方針を提示する
[4] 差分フェーズ  ★ Delta で結論の差分を返し、判断基準を固定3軸で評価する
```

**順序が何より大事。** 開示してから問うと、ユーザーは答えを読み直すだけになり、
事前に予測させる効果がなくなる。

**[1] と [2] を分けることも同じくらい大事。** 選択肢に判断基準を書き込むと、
ユーザーは「同意するか」を答えるだけになり、何も想起しない。
記録と評価の対象にするのは、**ユーザーが自分の言葉で書いた判断基準だけ**である。

## 対象領域

| 領域 | [1] で選ばせるもの | [2] で問うもの |
|---|---|---|
| 設計判断 | A案かB案か | なぜそちらを採ったか |
| 原因分析 | どのレイヤーに原因があるとみるか | どの根拠を重く見たか |
| レビュー力 | 最も重いリスクはどれか | なぜそれを最上位に置いたか |
| 実装方針 | どの方針で書くか | どの制約を重視したか |

**評価するのは [2] の回答。** [1] の正誤は文脈に依存するので、別の判断へは転移しない。
[2] で言葉にした基準は、次の判断へ転移する。

判断基準を問う形に置き換えられない問いは、そもそも判断点ではない。

## 予測フェーズ

常時ruleに書いた停止手段を使って問う。

- 選択肢は2〜4個。自由記述は「Other」で受ける（自動で付かないホストでは「上記以外」を明示する）
- 選択肢には互いに排他的な立場を置く（「どちらとも言える」を選ばせない）

### 選択肢には「結論」だけを置く。判断基準を書き込まない

**ラベルに判断基準を書くと、ユーザーが想起すべき内容を先に見せてしまう。**
ユーザーは同意するかどうかを答えるだけになり、自分の記憶を探さなくなる。

```
禁止  A) 実装コストを優先し、まず計測で当たりを付ける
      B) 恒久対応を優先し、データアクセス層から直す
      ↑ 「実装コストを優先」「恒久対応を優先」が判断基準。これを渡してはいけない

正しい  A) まず計測で当たりを付ける
        B) データアクセス層から直す
```

判断基準は、次の理由フェーズでユーザー自身の言葉として受け取る。

**`description` にも基準を書かない。** 書いてよいのは、その案を採ると
**何が起きるか**という事実だけ。**なぜ採るか**という評価を書いた時点で、答えを渡したことになる。

### どの選択肢も実際に成立しうるものにする

数合わせのために、明らかに成り立たない捨て案を入れない。

もっともらしい誤答が並ぶと、ユーザーは正解だけでなく「なぜ他が誤りか」も想起しなければならない。
そうなって初めて、選択式が学習として機能する。
捨て案が入っていると消去法で解けてしまい、想起が起きない。

失敗の実例: `learning/entries/2026-08-13-フックのタイムアウト値をどう決めるか-4.md`。
選択肢を3つに揃えるために「防御の確実性を優先して元の値に戻す」案を出した。
しかし対象のフックはfail-openだと確定していたので、このトレードオフは**そもそも存在しなかった**。

### 推奨を明示しない

**予測フェーズでは `（推奨）` を付けない。推奨案を先頭にも置かない。**
予測を取る前に正解を示すと、事前予測という前提が成り立たなくなる。

なお、**予測フェーズ以外**（実装方針の承認を取るだけの場面）では、
対話ツールのもともとのガイダンスどおり推奨を明示してよい。

## 理由フェーズ

選択が返ってきたら、**次のメッセージで理由だけを問い、そこでメッセージを終える。**

> なぜ A を選んだ？

停止を形だけにしないため、問いの後に次のものを書いてはいけない。

- 回答例や書き出し
- **励ましに見せかけたヒント**（「〜を考えてみて」「〜の観点で」「〜と比べると」）
- 複数の質問（1メッセージに1問）
- 括弧書きや斜体による示唆

書いてよいのは、内容を含まない一言だけ。

> （外していい）
> （パスしてもいい）

**選択肢は必ず再掲する。** 対話ツールの選択肢は回答後に画面から消えるので、
理由を書く時点で「何と何を比べたか」が見えなくなる。比較対象が見えないまま書いた理由は、
選んだ案の利点を並べるだけになりやすい。そのため、**仕組みのうえでトレードオフ軸が埋まらなくなる**。

- 再掲するのは、**選んだ結論と、他の選択肢のラベル・`description`**
- 再掲はヒントに当たらない。どれも提示済みの情報で、`description` には
  「何が起きるか」しか書かない規約なので、判断基準を含まない
- 再掲は箇条書きにとどめ、**補足・比較・評価を足さない**（足した時点でヒントになる）

**「Other」が選ばれたとき**は、こちらが用意した選択肢の幅が狭かったと受け止める。
★ Delta では「その結論を候補に入れられなかった理由」に触れる。

## ★ Delta

```
★ Delta ───────────────────────────────────────
予測: [選んだ結論と、理由フェーズで返ってきた判断基準を原文のまま]
実際: [実際の判断・原因・リスク]
差分: [結論に対する差分。下表に従う]
評価: [欠けていた軸だけを名指しする。全て埋まっていれば下記「全軸が埋まっていた場合」]
概念: [この判断が属する一般的な概念名を1つ ＋ 1文の説明。→ `references/delta-supplements.md`]
定石: [その判断に付随するコードレベルの書き方を1つ。該当が無ければ省く。→ `references/delta-supplements.md`]
次の問い: [次に同種の判断で確認する問い。1文。→ `references/delta-supplements.md`]
─────────────────────────────────────────────────
```

### 過剰帰属の禁止

**ユーザーが実際に表明していない理解を、表明したことにしてはいけない。**

「何が起きるか」を述べていても「なぜそうなるか」を述べていなければ、
**因果の理解は認めず、「何が」の部分だけを認める**。
言っていないことまで補って褒めると、本人は理解したつもりのまま先へ進んでしまう。
これは何も指摘しないより害が大きい。

### 過去の判断原則を接続する（該当があれば）

★ Delta を書く時点で、`learning/entries/` に**同型の判断原則**が既にあれば接続する。

```bash
grep -l '^axis: "失敗モード"$' learning/entries/*.md   # 同じ軸が欠けた回
grep -rl '<判断の型を表す語>' learning/entries/         # 同種の判断
```

- **接続は必ず ★ Delta の中で行う。予測を取る前に出してはいけない**（答えを渡すことになる）
- 過去エントリを**そのまま再出題しない**。当時の文脈はもう再現できない。
  取り出すのは末尾の「次に同種の判断で確認する問い」だけで、
  これは当時の文脈を外した**判断原則**にあたる
- 該当が無ければ何も書かない。無理に結び付けない

### 結論に対する差分

| 予測の結果 | 返し方 |
|---|---|
| 一致 | 一致を認めたうえで、**予測に含まれていなかった観点**を1つ名指しする |
| 部分一致 | 欠けていた観点と、**それが欠けると実務でどんなトラブルになるか**の具体例 |
| 不一致 | 正解を直接言わず、**その予測が成り立たなくなる反例**を1つ出す |

### 判断基準に対する評価（3軸・固定）

**軸は増やさない。自由な講評をしない。**
評価を自由文で書ける限り、「良い観点ですね」のような追従が必ず入り込む。
軸ごとに埋まっているかどうかを判定する形式にして、こちらの裁量を残さない。

| 軸 | 判定すること | 欠落時に実務で何が起きるか |
|---|---|---|
| トレードオフ | **何を捨てたか**を言えているか | 捨てたものを言えない選択は、比較をしていない。最初に思いついた案を追認しただけになる |
| 失敗モード | 選んだ案が**どう失敗するか**を言えているか | 失敗の仕方を知らない案は、失敗してから原因を調べ始めることになり、復旧までの時間を見積もれない |
| 前提の検証 | 根拠が**確認済みの事実か推測か**を区別しているか | 推測を事実として積み上げると、推論が正しくても結論が外れる。しかも間違いに気づくきっかけが無い |

**軸を名指ししたら、その回で具体的に何が抜けたかを続けて書く。**
軸名だけでは一般論になり、次の行動に結びつかない。
（以前は「具体的に何が抜けたか」を `学習領域` 側にも書いていた。
同じ内容が2箇所に並ぶため、評価パートへまとめた。→ ADR 0007 D4）

**全軸が埋まっていた場合**: 無指摘で終えない。**その判断基準が通用しなくなる条件**を1つ示す。
基準には必ず適用範囲があるので、範囲の外側を1つ挙げれば必ず何か言える。
記録では `axis: "全軸充足"` とし、本文に `### 基準が破れる条件` の見出しを置く
（見出しが無い `全軸充足` は記載漏れとして扱う。→ `learning/README.md`）。

**禁止**
- 「その通り」「正解」「良い観点ですね」だけで終えること
- 3軸すべてに講評を付けること（冗長になり、どの指摘が大事か分からなくなる）。**欠けている軸だけ**を名指しする
- 軸を勝手に増やしたり言い換えたりすること（記録を集計できなくなる）

この仕組みの中心は差分のフィードバックであり、ここを省くと仕組み全体が意味を失う。

## ★ Delta の補足欄

`概念`・`定石`・`次の問い` を書く前に `references/delta-supplements.md` を読む。

## 記録

★ Deltaを返し、ユーザーが実際に示した判断と理由がある場合だけ、専用学習storeへ
`kind: "decision"` の新形式recordを保存する。結論が当たったかどうかだけを能力の証拠にしない。
固定3軸、支援、開始契機、検証、未確認事項を本文に残す。旧 `learning/entries/` は読み取り専用の履歴である。
schemaと移管の境界は `learning/README.md` を参照する。

### 抽象化ルール（セキュリティ要件）

このリポジトリは **PUBLIC**。記録を作る前に、必ず次を満たすこと。

**禁止**
- 社名・組織名・プロジェクト名・リポジトリ名
- 内部ホスト名・内部URL・エンドポイント
- テーブル名・カラム名・内部ファイルパス
- 業務コードの直貼り

**必須**
- 技術的に大事な点だけを一般化して書く。具体例は最小の再現形に置き換える
- 判断に迷ったら書かない

## 迷ったとき

判定を避けようとする思考のパターンは `references/rationalizations.md` を読む。
