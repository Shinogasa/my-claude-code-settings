# コード学習

実際の変更を題材にして、ユーザーが調査・変更・検証を自分でやり遂げられる範囲を広げる。
ON/OFF、候補の担当、イベント数、開示順、保存状態、成長判定は
`rules/learning-mode.md` の「両学習モードの共通方針」だけで定め、ここでは重ねて書かない。

## 候補選定

次をすべて満たす能力を一つだけ扱う。

1. 現在の実装・修正・リファクタリング・レビューに直接関係する。
2. 正しさ、変更容易性、デバッグ可能性、性能、安全性に具体的に影響する。
3. 別の箇所へ転用でき、本人が同じ対象範囲でまだ実証していない。
4. 本物の作業から切り出した小さな課題にでき、実行できる検査か一次資料で評価できる。

生成物、vendored code、lockfile、ボイラープレート、機械的変更、設定値・文言の変更は除外する。
検証不能なら発火を見送り、通常作業へ戻る。記録が無いだけで未習得とは決めない。
設計Predictの3条件やL2優先ゲートは流用しない。二重出題は共通方針に従って避ける。
本人が原因箇所や仮説をまだ特定していない不具合では、AIが原因を特定する前に、
本人がInvestigateで観測と次の調査を選べるかを優先して確かめる。
演習を作るために、productionへTODOや解法のヒントを書き足さない。

## 足場と形式

TDD、原因調査、security、verificationの実施順序を守る。
TDDなら失敗するテストより先にproduction実装を書かせない。security boundaryにかかる変更では、
本人が知らない危険な実装を支援なしで任せず、安全に検証できる範囲まで担当を狭める。

課題を始めるときは、次の4点だけを短く示す。

- 目的
- 本人が完了まで担当する範囲
- 確認すべき外部挙動と完了条件
- 使える資料と操作環境

解法、答えになるassertion、原因がありそうな箇所を完了条件に含めない。特にInvestigateでは、
対象箇所を先に示さない。本人が範囲を変えること、skipすること、引取りを頼むことを認める。
形式は能力と現在の支援量で選ぶ。Writeが成立するというだけでWriteを優先しない。

| 形式 | 本人がすること | 成立条件 |
|---|---|---|
| Investigate | 仮説を区別できる観測を選び、証拠を解釈し、次の調査・修正・検証を選ぶ | 原因、対象箇所、検証方法の少なくとも一つを本人に任せられる |
| Review | コードと証拠から欠陥を指摘するか、問題が成り立たない理由を示す | 根拠を検証でき、不要なpatchを求めずに済む |
| Modify | 動いている既存コードを追加条件に合わせて変更し、検証する | productionへ教材用の欠陥を仕込む必要がある場合は選ばない |
| Write | 契約に沿う小さな実装か検証コードを書き、実行結果を確かめる | 人工的な穴埋めや広すぎる実装にならない |
| Explain | 必要最小限の前提を理解し、できれば本人が手を動かす形式へ進む | 前提が足りず、上の形式を安全に始められない |

本人が担当している範囲では、工程ごとに新しい演習へ分けない。本人が意味のある提出物か判断を
出すまで待ち、本人が選んだ次の行動を記録する。tool出力、diff、agent報告を先に見せた場合は
支援として扱う。AIがツール操作を代行した回に本人が実証したのは、観測の設計と結果の解釈までである。
コマンド操作や再現環境の構築までできたことにはしない。

最初の依頼に理由質問を同梱しない。応答を待つ対話手段があれば使い、無ければ依頼だけを
示してターンを終える。同じ応答に、完成コード、模範解、答えを含むWHY説明を書かない。

## 理由を自己説明

本人が書いた、直した、指摘した、または観測を解釈した直後に、その選択の理由を一問だけ尋ねる。
回答例、観点の一覧、概念名は添えない。ユーザーのスキップを尊重し、skipした後に理由の回答を強いない。

本人が理由まで回答する前は、答えとなる `★ Review`、定石、WHY説明、模範解を保留する。
通常の進捗、必要な前提知識、本人が得た生の観測結果は隠さない。それらとAIの解釈は区別して示す。

## 事実を検証

型検査、compiler、unit/property test、再現手順を優先し、必要なら一次資料とrepositoryの契約を確認する。
テストが通った事実と、本人が検証方法を選んだ事実を分ける。AIが完成させたテストを通した結果は
実装の証拠には使えるが、本人が検証方法を設計した証拠にはしない。

初回の回答は、事実、repoの慣例、複数の答えが成り立つ判断、未確認事項に分けて検証する。
検査できなかったことを「問題なし」に畳まない。専門的な判断に必要な根拠や検証済みの教師routeが
足りない場合は、言い切る形で採点しない。学習イベントを見送り、通常の品質確認を行う。

## フィードバック

`★ Code Delta` では一つの能力だけを扱い、次の内容を短く返す。本人の行動と理由、検証結果と
一致した点、最も重要な差分、トラブルにつながる条件、別の場面でも使える確認の問い。根拠の種類は混ぜない。

- `verified_fact`: test、compiler、benchmark、一次資料、repositoryの契約で確認した事実
- `repo_convention`: このrepositoryで観測した慣例
- `engineering_judgment`: 複数案が成り立つ場合のtrade-off
- `unverified`: 未確認事項と、確認に必要な検査

重要な誤解には、完成解の代わりに反例または観測差を一つ示し、本人が調べ直して修正し直すのを待つ。
固定の再試行回数や時間を理由に、担当範囲を取り上げない。進展が止まったら、前提を補うか範囲を狭める。
2回以上の再試行も同じevent_idにまとめ、主な誤解・ヒント・修正を残す。

中断した後は、同じ課題と完了条件を確認してから同じevent_idで再開する。観測済みの途中結果を
保存する場合は、未完了だと明記する。完成実装は本人が引取りを依頼するまで保留する。
安全のための介入やAIによる修正では、変更した範囲と理由を示し、本人の自力での成功には数えない。
検証していないユーザーのコードをproductionに採用しない。

## 転移確認

本人が担当範囲を終えたら、条件を一つだけ変えて転移を確かめる。変える条件は入力、依存先の失敗、
同期/非同期、配置先などで、回答・小さなpatch・テストケースのいずれかで検証できる形にする。
今回やり遂げたかどうかと、転移できたかどうかは別々に判定する。
適切な転移課題を作れない、本人が見送る、前提が解消していない、のいずれかなら
`not_attempted` として終えてよい。転移をしなかったことを理由に、今回やり遂げた判定を取り消さない。

次の関連課題では、対象箇所・仮説・検証ケースのどれかの支援を一つ減らすか、
本人が担当する範囲を隣の工程へ一つ広げる。課題を難しくすること自体を成果とみなさない。
開始契機と既知の条件を前回と比べる。

## 学習記録

共通方針の保存手順に従い、本人が実際に調査・変更・レビュー・検証した行動だけを専用storeへ記録する。
理由の説明や転移の回答だけを能力の証拠にしない。初回結果、最後の再試行、転移、開始契機、
提示済みの箇所・仮説・検証、途中の支援、AIによる修正、未解消事項、関連record IDは区別して残す。

公開記録に、業務コード、内部path、顧客名、非公開の型名・データ名を含めない。
抽象化すると判断や証拠が失われる場合は保存せず、「未保存」と伝える。operationは運用回数の記録であり、
能力の証拠に含めない。旧記録を新schemaの成功へ変換せず、teachへも自動同期しない。
