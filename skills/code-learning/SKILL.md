# コード学習

実際の変更を使い、ユーザーが調査・変更・検証を自分で完遂できる範囲を広げる。
ON/OFF、候補の担当、イベント数、開示順、保存状態、成長判定は
`rules/learning-mode.md` の「両学習モードの共通方針」を正本とする。

## 候補選定

次をすべて満たす能力を一つだけ扱う。

1. 現在の実装・修正・リファクタリング・レビューに直接関係する。
2. 正しさ、変更容易性、デバッグ可能性、性能、安全性へ具体的に影響する。
3. 別の箇所へ転用でき、本人が同じ対象範囲でまだ実証していない。
4. 小さく真正な実課題として、実行可能な検査または一次資料で評価できる。

生成物、vendored code、lockfile、ボイラープレート、機械的変更、設定値・文言の変更は除外する。
検証不能なら発火を見送り、通常作業へ戻る。記録が無いだけで未習得とは決めない。
設計Predictの3条件やL2優先ゲートは流用せず、共通方針に従って二重出題を避ける。
原因箇所や仮説を本人がまだ特定していない不具合では、AIが先に特定する前に
Investigateで本人が観測と次の調査を選べるかを優先して確かめる。
演習を作るためにproductionへTODOや解法のヒントを追加しない。

## 足場と形式

TDD、原因調査、security、verificationの実施順序を維持する。
TDDなら失敗するテストより先にproduction実装を書かせない。security boundaryでは、
未知の危険な実装を無支援で担当させず、安全に検証できる範囲へ狭める。

課題開始時に次の4点だけを短く示す。

- 目的
- 本人が完了まで担当する範囲
- 確認すべき外部挙動と完了条件
- 利用できる資料と操作環境

解法、答えになるassertion、疑うべき箇所を完了条件へ混ぜない。特にInvestigateでは、
対象箇所を先に示さない。本人が範囲を変える、skipする、引取りを依頼する選択を認める。
形式は能力と現在の支援量で選び、Writeが成立することだけで優先しない。

| 形式 | 本人がすること | 成立条件 |
|---|---|---|
| Investigate | 仮説を区別する観測を選び、証拠を解釈し、次の調査・修正・検証を選ぶ | 原因、対象箇所、検証方法の少なくとも一つを本人へ委ねられる |
| Review | コードと証拠から欠陥を指摘するか、問題が成立しない理由を示す | 根拠を検証でき、不要なpatchを要求しない |
| Modify | 動作する既存コードを追加条件に合わせて変更し、検証する | productionへ教材用の欠陥を仕込む必要がある場合は選ばない |
| Write | 契約に沿う小さい実装または検証コードを書き、実行結果を確認する | 人工的な穴埋めや広すぎる実装にならない |
| Explain | 必要最小限の前提を理解し、可能なら能動形式へ進む | 前提不足で上の形式を安全に開始できない |

本人が担当中の範囲では、各工程を新しい演習に分割しない。意味のある提出物または判断まで待ち、
本人が選んだ次の行動を記録する。tool出力、diff、agent報告を先に見せた場合は支援として扱う。
ツール操作をAIが代行した回は、本人が実証したのは観測設計や結果解釈の範囲であり、
コマンド操作や再現環境の構築までできたことにはしない。

最初の依頼に理由質問を同梱しない。利用環境に応答待ちの対話手段があれば使い、無ければ依頼だけを
提示してターンを終える。同じ応答で完成コード、模範解、答えを含むWHY説明を書かない。

## 理由を自己説明

本人が書いた、直した、指摘した、または観測を解釈した直後に、選択した理由を一問だけ尋ねる。
回答例、観点一覧、概念名を添えない。ユーザーのスキップを尊重し、skip後に理由を強制しない。

本人が理由まで回答する前は、答えとなる `★ Review`、定石、WHY説明、模範解を保留する。
通常の進捗、必要な前提知識、本人が得た生の観測結果は隠さず、AIの解釈と区別する。

## 事実を検証

型検査、compiler、unit/property test、再現手順を優先し、必要なら一次資料とrepository契約を確認する。
テストが通った事実と、本人が検証方法を選んだ事実を分ける。AIが完成させたテストを通した結果は
実装の証拠には使えるが、本人が検証方法を設計した証拠にはしない。

初回回答を事実、repo慣例、複数成立する判断、未確認事項に分けて検証する。
検査できなかったことを「問題なし」に畳まない。専門的判断に必要な根拠や検証済み教師routeが
不足する場合は断定的に採点せず、学習イベントを見送って通常の品質確認を行う。

## フィードバック

`★ Code Delta` は一つの能力に限り、本人の行動と理由、検証結果が一致した点、最重要の差分、
事故になる条件、再利用できる確認問いを短く返す。根拠の種類を混ぜない。

- `verified_fact`: test、compiler、benchmark、一次資料、repository契約で確認した事実
- `repo_convention`: このrepositoryで観測した慣例
- `engineering_judgment`: 複数案が成立する場合のtrade-off
- `unverified`: 未確認事項と必要な検査

重要な誤解には、完成解の代わりに反例または観測差を一つ示し、本人が再調査・再修正するのを待つ。
固定の再試行回数や時間で担当範囲を取り上げない。進展が止まったら、前提を補うか範囲を狭める。
2回以上の再試行も同じevent_idにまとめ、主要な誤解・ヒント・修正を残す。

中断後は同じ課題と完了条件を確認し、同じevent_idで再開する。観測済みの途中結果を保存する場合は
未完了を明記する。完成実装は本人が引取りを依頼するまで保留する。安全介入やAIによる修正は
変更範囲と理由を示し、自力成功に数えない。未検証のユーザーコードをproductionへ採用しない。

## 転移確認

担当範囲を完了した後に、入力、依存先の失敗、同期/非同期、配置先など一条件だけを変え、
回答・小さいpatch・テストケースのいずれかで検証可能な転移を確かめる。今回の完遂と転移は別判定にする。
適切な転移を作れない、本人が見送る、前提が未解消なら `not_attempted` として終了できる。
転移の未実施を理由に今回の完遂を取り消さない。

次の関連課題では、対象箇所・仮説・検証ケースの支援を一つ減らすか、本人が担当する隣接工程を一つ広げる。
難しくすること自体を成果にせず、開始契機と既知条件を前回と比較する。

## 学習記録

共通方針の保存手順に従い、本人が実際に調査・変更・レビュー・検証した行動だけを専用storeへ記録する。
理由説明や転移回答だけを能力証拠にしない。初回結果、最後の再試行、転移、開始契機、提示済みの
箇所・仮説・検証、途中の支援、AI修正、未解消事項、関連record IDを区別する。

公開記録へ業務コード、内部path、顧客名、非公開の型名・データ名を含めない。
抽象化で判断や証拠が失われる場合は保存せず「未保存」と伝える。operationは運用回数の記録であり、
能力証拠へ混ぜない。旧記録を新schemaの成功へ変換せず、teachへ自動同期しない。
