# コード学習

実際の変更を使い、AIが生成したコードをユーザーが自力で読み、直し、評価できる能力を育てる。
タイピング量やパターン名の暗記ではなく、挙動・依存・失敗条件を説明し、別条件へ転移できることを成果にする。

## 候補選定

次をすべて満たす候補だけを扱う。

1. 実装・修正・リファクタリング・レビュー中の実コードに関係する。
2. 正しさ、変更容易性、デバッグ可能性、性能、安全性のいずれかへ具体的に影響する。
3. 別の箇所へ転用でき、ユーザーがまだ実証していない能力である。
4. 一つの能力に絞った、小さく真正な課題を切り出せる。
5. 実行可能な検査または一次資料で、重要なフィードバックを検証できる。

珍しい構文、短い記法、有名なデザインパターンというだけでは候補にしない。
生成物、vendored code、lockfile、ボイラープレート、機械的置換、設定値・文言の変更は除外する。
ユーザーが同能力を別文脈でも実証済みなら繰り返さない。適格候補が無い回は発火しない。

同じ箇所で設計判断用の `rules/learning-mode.md` と二重出題しない。
設計Predictは結論と判断基準を、ここでは実際のコードの理解・変更・検証を扱う。
pilot中はコード学習を1タスク最大1イベント、設計Predictと合計2イベントを目安にする。
「全部やって」「任せる」「急ぎ」「学習なし」等の明示があれば、そのタスクではOFFにする。
ユーザーはいつでもスキップでき、スキップ後は通常の実装を完了する。

## 足場と形式

適用中のTDD、原因調査、セキュリティレビュー、最終検証の順序を先に守る。
TDDなら失敗するテストより先にproduction実装を書かせない。security boundaryでは、
未知の危険な実装を無支援で書かせず、安全なReviewまたはTraceへ寄せる。

変更の目的、外部から観測できる契約、必要な周辺コード、署名、制約、対象箇所を示す。
概念名、模範コード、答えになるassertionは先に渡さない。ただし前提知識や公式仕様が
不足していれば最小限を先に教える。無知を推測で埋めさせない。

真正かつ安全に成立する最初の形式を次の順に選ぶ。

| 形式 | ユーザーがすること | 選べない条件 |
|---|---|---|
| Write | 挙動を決める約5〜15行を実際の対象へ書く | 人工的な穴埋めになる、広すぎる、危険な実装を無支援で要求する |
| Modify | AIの動作する初稿を、追加条件・依存分離・型・エラー処理のために直す | productionへ教材用の欠陥を仕込む必要がある |
| Review | 挙動、データ・制御・エラーの流れ、重大な欠陥候補、変更影響、必要なテストの一つを指摘する | 文脈不足で検証可能な指摘を作れない |
| Explain | AIが重要な書き方を解説する | 上の能動的な形式が成立する |

Write / Modifyでは、必要な署名・周辺コード・テストの外枠を準備してから、対象箇所と制約を示す。
ユーザーの編集を待つときは、応答を待つ対話手段を使う。利用環境にそれが無ければ、
依頼だけを提示してターンを終える。同じ応答で完成実装を書かない。
最初の依頼に理由質問を同梱しない。コードまたは指摘を見てから、次の応答で理由を一問だけ尋ねる。
Reviewでも「自由にレビューして」ではなく、今回の能力に焦点を絞った一問にする。

例: キャンセルを扱う非同期処理の回帰テストを先に失敗させ、関数署名と変更箇所を示す。
「キャンセル後に結果を反映しない部分だけを書いてください。理由はコードを見た後に聞きます」と依頼する。
この段階で完成コードや一般的な解法名を提示しない。

## 理由を自己説明

ユーザーが書いた、直した、または指摘した直後に、選択した理由を一問だけ尋ねて回答を待つ。
回答例、観点一覧、正解の概念名を同時に与えない。スキップの場合は理由を強制しない。

## 事実を検証

型検査、compiler、unit/property test、再現手順を優先し、必要なら公式言語・標準ライブラリ・
framework資料、repository契約を確認する。テストが通った事実と仕様を満たす判断は分ける。
検査できなかったことを「問題なし」に畳まない。性能なら時間、allocation、I/O、計算量など
評価軸を特定する。「短いから効率的」は根拠にならない。

安価な実装モデルが自作コードを模範と認定し、ユーザー回答を自己採点し、未検証の一般則を教えない。
設計パターン、依存方向、並行性、安全性などに専門的判断が必要なら、ホストの検証済みhandoffを通じた
読み取り専用教師routeが利用できる場合だけ委譲する。routeや根拠が不足する場合はその学習イベントを
見送り、通常の実装・検証へ戻る。教師の自然言語回答もproductionコードの検証証拠にはしない。

## フィードバック

`★ Code Delta` では一つの能力に限って、ユーザーの説明と検証結果が一致した点、
最重要の差分、その差分が事故になる条件、再利用できる確認問いを短く返す。
根拠の種類を混ぜない。

- `verified_fact`: compiler・test・benchmark・一次資料・repository契約で確認した事実
- `repo_convention`: このrepositoryで観測した慣例。一般則と呼ばない
- `engineering_judgment`: 複数案が成立する場合のtrade-off。唯一解と呼ばない
- `unverified`: 未確認事項と、それを確認するために必要な検査

パターン名や言語イディオムは原則としてユーザーの自己説明後に与え、
解決する変更圧力と適用しない条件をセットで示す。ユーザーの成立する別解を模範解との差だけで誤答にしない。
誤ったコードは通常の実装workflowで修正・検証し、未検証のユーザーコードをそのまま採用しない。

## 転移確認

元コードの暗記と区別するため、入力、依存先の失敗、同期/非同期、配置先などの条件を
一つだけ変えた短い問いを出し、回答・小さなpatch・テストケースのいずれかで確認する。
productionへ不要な変更を加えない。転移に失敗したら理解済みとしない。
即時の成功を長期保持の証明と呼ばず、関連する後続タスクで必要なら短く想起する。

## 学習記録

ユーザーが書いた、直した、説明した、レビューした、転移した事実だけを
`learning/code/README.md` の形式で記録する。AIが説明しただけの内容は理解の証拠にしない。
このリポジトリは公開なので、業務コード、内部パス、顧客名、非公開の型名・データ名は保存しない。
抽象化できない場合は保存せず、session内だけで完結させる。
teachへ自動同期しない。反復gapが体系的なmissionに適する場合だけユーザーへ候補を提案する。
