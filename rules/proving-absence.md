# 不在の主張（「無い」と言うときの形式）

## 基本方針

**「X は無い」は二重の主張である。**

1. 探した範囲に X は無かった
2. **探した範囲は、X が在りうる範囲を覆っている**

①は走査で示せる。②は走査では示せない。別の根拠が要る。
**②を書かない不在報告は、情報量がほぼゼロになる。**

**丁寧さは正しさの証明にならない。** ①を丁寧にやるほど「調べ尽くした」感覚だけが強まり、
②の欠落が隠れる。

## なぜ「順序の指示」ではなく「出力の形式」なのか

`rules/ecc-development-workflow.md` の Research & Reuse は
「GitHub code search first, **library docs second**」を mandatory と定めている。
この順序を守っていれば防げたはずの不在誤認が、それでも発生した。

原因は文面の弱さではない。**順序の指示は、守ったかどうかが成果物に痕跡を残さない**ことにある。
違反しても出力は正常に見えるため、書いた本人も読み手も気づけない。静かに死ぬルールだった。

対して形式の規定は監査できる。欄が空なら、読めば分かる。
このファイルが順序ではなく形式を定めているのはそのためで、
**強制力ではなく検知可能性を取っている**。

## 形式

不在を結論として述べるとき、次の4点を添える。埋められない項目は「未確認」と明記する。
**黙って省略しない。** 省略は「確認した」と区別がつかず、この仕組みが静かに壊れる唯一の経路になる。

| 項目 | 書くこと |
|---|---|
| 主張 | 何が無いと言っているのか |
| 探索範囲 | どこを、どの手段で見たか（対象・コマンド・件数） |
| 範囲の根拠 | なぜその範囲が「在りうる範囲」を覆うと言えるか |
| 反証条件 | この「無い」が誤りなら、どこを見ていなかったことになるか |

**範囲の根拠として最も安いのは一次ドキュメント。走査より先に読む。**

### 適用する場面

- 「機構が無い」「対応していない」「設定されていない」と結論するとき
- 「再現しません」「該当なし」「ログに出ていません」と報告するとき
- **他人の不在報告を受け取るとき**（人間・AI・外部ベンダを問わない）。
  調べ方とセットでない不在報告は、そのままでは根拠にしない

## 測定を組む前に、判別可能性を確かめる

> **仮説が偽だったとき、この測定はどんな出力を出すか？**

その出力が真のときと同じなら、それは測定ではない。組む前に止まれる。

例: `grep '^VAR='` は `VAR=`（空文字列）の行にもマッチする。
「値が設定されているか」を測りたいのに「変数が存在するか」しか判別していない。
しかも出力は綺麗に出るため、**動く出力が誤った確信を生む**。

## 「検査できなかった」を「問題なし」に畳まない

必要な状態は3つある。

```
① 検査した → 問題なし
② 検査した → 問題あり
③ 検査できなかった   ← これが落ちやすい
```

畳む方向には非対称性がある。③を②側に倒せばノイズは出るが危険ではない。
①側に倒すと危険だ。**畳まざるを得ないときは、うるさく失敗する側へ倒す。**

母数を数えるときも同じ。「N回中0件」の N に③が混ざっていれば、その 0件 に意味は無い。

## 合理化防止

以下を考えたら、それは②を飛ばしている兆候である。

| 思考 | 現実 |
|---|---|
| 「grep したから無い」 | grep は式の範囲内に無いことしか示さない。式が正しい根拠が別に要る |
| 「全部走査した」 | 走査対象の集合が正しいという根拠が別に要る |
| 「丁寧に調べた」 | 丁寧さは①の質であって、②の証明ではない |
| 「N回試して0件だった」 | 検出できない構成だった可能性を潰したか。N に③が混ざっていないか |
| 「エラーが出ていない」 | 検査が走った証拠か、走らなかった証拠か。区別できるか |
| 「キーが無いから機構が無い」 | 定義場所の思い込み。別ファイル・別階層・別名を潰したか |
| 「ドキュメントは後で読む」 | ②の根拠として最も安い。走査より**先**に読む |
| 「ローカルで全部調べた」 | コードは「何が起きうるか」しか教えない。「実際に何が起きているか」は issue やコミュニティが持っている |
| 「時間がないので裏は後で取る」 | 不在の結論は下流の判断を確定させる。裏取り前に出すと巻き戻せない |
