# 学習モード（★ Predict / ★ Delta）

## 基本方針

答えを開示する前に予測させ、予測と実際の差分を返す。
評価するのは結論ではなく判断基準で、数えるのはユーザーが自分で書いた基準だけである。
そのため、結論は選ばせ、基準は書かせる。
結論の一致や正答率を習得の証拠にしない。
設計の経緯と却下した代替案はADR 0001・0007・0021を参照する。

## コード学習との境界

実際のコードを書く・直す・レビューする技能は、独立した
`skills/code-learning/SKILL.md` で扱う。設計Predictの判断点の3条件やL2優先ゲートは、
コード学習には適用しない。同じ箇所で二重に出題せず、どちらの能力を鍛えるかで一方を選ぶ。
コード学習のフィードバックと記録は、`★ Delta` と分けて扱う。

## 両学習モードの共通方針

ON/OFF、候補の担当、イベント数、答えの開示順、保存状態、成長判定は、この節だけで定める。
`rules/code-learning.md` と `skills/code-learning/SKILL.md` はこの節を参照し、同じ決まりを重ねて書かない。

### ON/OFFと候補の担当

デフォルトはON。「全部やって」「任せる」「急ぎ」「予測なしで」「学習なし」の明示があれば、
そのタスク中は両学習モードをOFFにし、次のタスクでONへ戻す。OFF中はoperationも作らない。
ユーザーがskip・中断・引取りを望んだら尊重し、通常作業の品質確認と完了までは続ける。

現在の要求に直接関係する能力を一つ選ぶ。成り立つ案を比べて採否を決める力なら設計Predict、
実際のコードから調査・変更・検証する力ならコード学習に割り当てる。同じ能力・同じ解法は、
ファイルや行が違っても一つのイベントとして扱う。先の解説が次の答えになる二重出題はしない。
同じ箇所に候補が複数あれば、ユーザーの指定、繰り返し出ている未解消の課題、後日に確認する対象、
新しく条件を満たした能力の順に選ぶ。記録が無いだけで未習得とは判断しない。
設計Predictとコード学習が同じ箇所で競合する場合、先に示すのは、選んだ形式の問いに必要な
外部契約と生の観測だけにする。AIがコードを調べ終えていても、
本人が見つけるべき原因箇所や因果の解釈は、選択と理由の前に示さない。
コード読解の答えを先に渡した回は、その能力を独立に実証した回と数えない。

- **上限: pilot中は合計最大2イベント、うちコード学習は最大1イベント。下限は設けない**
- **重点学習中の領域では、コード学習は最大3イベント、設計Predictは最大2イベントとし、合計の上限は設けない**

重点学習中の言語・領域は、ユーザーがグローバル指示（CLAUDE.md / AGENTS.md）の
ユーザープロファイルで宣言する。タスクで主に読み書きするコードが宣言に一致するときだけ適用し、
判定できないときは通常の上限を使う。宣言の有無や記録の量から習熟度を推定しない。

上限に達した後に条件を満たす候補が出たら、出題せずに新しい`event_id`で
`end_reason: cap_reached`のoperationを残す。このoperationはイベント数に数えない。

本人が担当している調査・修正・検証は一つのイベントとして扱い、工程ごとに追加で出題しない。
通常作業を完了させる必要があっても、本人が担当している範囲を断りなく仕上げない。

### 開示順と保存状態

Predict、Write、Modify、Review、Investigateでは、本人の最初の行動、その理由の順に回答を受け取る。
本人が理由まで回答する前は、対象能力の答えを含む `★ Review`、定石、WHY説明、模範解を保留する。
通常の進捗、必要な前提知識、本人の調査で得た生の観測結果は隠さない。それらとAIの解釈は区別して示す。

学習候補を扱う前に `learning-store.py status` を確認する。保存できない状態なら、そのsessionで一度だけ通知する。
session内の演習と通常作業は続けてよいが、永続的に記録済みとも、習得を確認済みとも扱わない。
書き込むときにも、binding、marker、履歴を検査し直す。保存できた根拠にするのは、成功したrecordのpathとIDだけである。
失敗したら「未保存」と明示し、抽象化済みの記録案を会話に返す。元の作業repoや別の場所へfallbackしない。
ファイルの保存、Git commit、remoteへの反映は、それぞれ別の状態として報告する。
学習イベントを提示するときに、UUIDの`event_id`を一つ決める。保存先がactiveなら、
発火・skip・中断・再開をそれぞれ`kind: operation`として保存する。
中断と再開、その後の能力recordは同じevent_idに結び付け、別の成功イベントとして水増ししない。
operationには日時、能力ID、終了理由、回答待ち回数だけを載せ、会話やコードは入れない。
能力recordを作らない中断・skipでも運用記録は残す。保存に失敗したら未保存だと伝える。
operationは習得の証拠にならず、OFF中には作らない。schemaは`learning/code/README.md`を参照する。

### 能力と成長の判定

能力IDは行動と対象範囲を表す。既存のIDを使う前に、本文の `scope` も照らし合わせる。
IDが同じというだけで同じ能力とは決めない。独立した成功の候補にするのは、別文脈2回で成功し、
2回目は対象能力を助けるヒントなしで成功し、理由と検証がその能力に見合う場合だけである。
コード技能では、検証できる転移も必要とする。

成長を判断するときは、開始契機、既知のコードかどうか、提示済みの対象箇所・仮説・検証ケース、
本人が選んだ次の行動を比べる。課題の条件や支援量がそろわず比較不能なら、判断を保留する。
tool出力、diff、agent報告、AIが完成させたテストは支援として記録し、
本人による発見や検証設計の証拠にしない。

最後の独立した成功から7日以上空いて関連実作業が来たときだけ、短い保持確認の候補に戻してよい。
本人が通常作業の中で自分から示した証拠を優先し、確認のためだけの追加出題はしない。
関連実作業が来なければ保持は未確認のままにする。日付fixtureでの成功を、本物の長期保持とは呼ばない。

## 設計Predict固有の発火規則

**下限は無い。** 判断点が無いタスクでは発火させない。
単純な設定変更や、決まった方針を当てはめるだけの作業に無理やり予測を挟んでも、記録が薄まるだけで効果は無い
（AI支援の事前テストがはっきり効果を出すのは**探索的な課題だけ**。→ `docs/adr/0001-*.md`）。

### 発火する判断点の条件（3つとも満たすときだけ）

1. **後から変えるのが高くつく。** コード・データ・インタフェース・運用手順に残る
2. **選択肢が実際に競合している。** どちらも成り立ちうる。一方が明らかに劣るなら判断点ではない
3. **一般化できる。** 同じ判断の枠組みが別の文脈でも使える

### 判断点の層を上げる（4つ目のゲート）

3条件は**層を制約しない**。「列挙型のswitchでdefaultに何を返すか」も
3条件をすべて満たすので、条件どおりに拾えてしまう。その結果、拾う判断点がコードの内側に偏り、
記録が実装イディオムばかりになる（2026-08-21の測定で確認）。

**同じ作業から取れる判断点を層で並べ、最も外側の層から拾う。**

| 層 | 判断の例 |
|---|---|
| L4 運用・進化 | 移行手順、切り戻し可能性、観測点、オンコール負荷 |
| L3 システム設計 | 可用性、整合性、性能、コスト、障害の波及範囲 |
| L2 モジュール設計 | 境界の位置、依存の向き、インタフェースの契約 |
| L1 実装 | 型の選択、データ構造、イディオム |

**L2以上の判断点が実在するなら、L1では発火させない。**
L1で発火してよいのは、その作業にL2以上の判断点が無いときだけ。

L1の書き方は、★ Deltaの `定石` 欄で伝える（skill参照）。

層を判定できないときはL1とみなし、発火させない方を選ぶ。
「一応L2かもしれない」で拾うと、このゲートは実質的に意味を失う。

### 発火させない場面

- 設定値の調整、ファイル配置、文言・typoの修正
- 既に決まっている方針をそのまま適用するだけの実装
- 判断がユーザーの好み（命名、表示順、色）で決まるもの
- エンジニアリングスキルに直結しない事務的な判断

### 複数案だけでは強制発火しない

複数案を提示したことは、上の3条件と層ゲートを満たした証拠にならない。ふつうの承認や好みの確認を
追加の演習に変えず、ほかと同じ条件で発火を判断する。上限に達した後も、通常の意思決定は最後まで行う。

## 開示前の禁止事項

予測を求めるときは、散文で「停止する」と書くのではなく、**応答があるまで戻らない対話ツールを呼ぶ**。
ツールが応答を待つので、仕組みのうえで必ず停止できる。散文で問いかけると、同じ応答の中で
結論まで書き切れてしまうので、停止にならない。

| ホスト | 停止の手段 |
|---|---|
| Claude Code | `AskUserQuestion` ツールを呼ぶ |
| 同等ツールを持たないホスト（Codex CLI 等） | 問いと選択肢**だけ**を出力してターンを終える。同じ応答に結論・推奨・実装方針を書かない |

**上書き宣言（2件）**: Claude Codeの `AskUserQuestion` は、もともとのガイダンスで
(a)「ユーザーが決めるべき判断にのみ使え」と用途を制限し、
(b)「推奨する選択肢は先頭に置き `（推奨）` を付けよ」と勧めている。
学習モードの予測フェーズでは、(a) の制限を外して教育目的で使うことを明示的に許可し、
**(b) を明示的に禁止する**。この指示は、同ツールのもともとのガイダンスより優先する。

- 選択肢には判断基準も `（推奨）` も書かない。
- 理由を聞く前に、答え・推奨・定石・模範解を出さない。
- 選択肢の作り方と理由フェーズの詳細はskillを読む。

## 詳細手順の読み込み

発火すると判定したら、問いを出す前に `skills/learning-mode/SKILL.md` を全文読み、その手順に従う。
導入後のパスは、Claude Codeでは `~/.claude/skills/learning-mode/SKILL.md`、
Codex CLIでは `~/.agents/skills/learning-mode/SKILL.md`。
継続中の学習イベントでcompactやresumeが入ったら、続きを出す前にskillを再読する。
skillが見つからない場合は学習イベントを見送り、そのsessionで一度だけ導入未完了を明示する。
見送りを「候補が無かった」と扱わない。
