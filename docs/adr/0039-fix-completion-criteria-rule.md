# 作業のぶれを、並列化ではなく完了条件の固定と仕分けで防ぐ

## 背景

この決定で解く問題は、調べながら進める抽象的なタスクで、完了条件が記録されないまま書き換わり、求められた結果から外れていくことである。

2026-10-22の脆弱性対応で、hotfixと報告資料の作成を並列で進めた。これをきっかけに、
「複数タスクの並列可否を判定し、サブエージェントを起動して並列に進め、結果をまとめる仕組み」を作る引継書が書かれた
（`.superpowers/handoffs/parallel-task-orchestration.md`、本体の未追跡ファイル）。

brainstormingで動機をたどると、並列化は目的ではなかった。ユーザーが恐れていたのは次の2つだった。

- 調査を進めるうちにコンテキストが膨らみ、AIの出力がおかしくなる
- やりとりが長くなるうちに、ユーザー自身が当初の目的を忘れたり、ぶれたりする

ぶれは、抽象度が高く調べながら進めるタスクで起きる。依頼者が示すのは結果だけで、完了条件は作業する側が仮説として立てる。
調査のたびに「これも考慮しなきゃ？」という論点が増え、完了条件が記録されないまま書き換わる。

観測した事実は次のとおり。

- cwワークスペースの `tasks/todo.md`（2026-09）は、「作業中に変わった判断」を「当初 → 変更後 → 理由」の表で残していた。
  必要な形は自然に育っていたが、書かれたのは作業の最後だった
- 同じファイルの最終更新は2026-09-18のままで、2026-10-22の急ぎの対応では使われていない。
  `rules/task-management.md` が常時指示しているのに、一番ぶれやすい急ぎのタスクで飛ばされた
- `tasks/todo.md` は1ファイルを使い回すので、同じ作業ツリーの複数セッションで上書きし合う。worktreeには来ない

## 決定

2026-10-22、ユーザーが会話の中で決めた。設計の詳細は `docs/superpowers/specs/2026-10-22-completion-anchor-design.md`。

- 作るものの軸を、並列オーケストレーションから「完了条件の固定」と「作業中の仕分け」へ変える。並列化は選択肢の一つに格下げする
- 新しい常時rule `rules/fix-completion-criteria.md`（`paths:` 無し）で届ける。急ぎのタスクでも外さない
- タスクを始めるとき、`tasks/todo/<タスク名>.md` に「依頼された結果」「暫定の完了条件」「今回は扱わない論点」を書き、ユーザーに確認する
- 作業中の論点を、①完了に必要、②完了条件が変わる、③関係ない、に仕分ける。作業を止めてユーザーの承認を得るのは②だけ。
  ②は「当初 → 変更後 → 理由」を、変わったその場で記録する
- サブエージェントにはタスク用ファイルの絶対パスを渡し、②は親へ返させてユーザーに中継する
- brainstormingが設計書を書いたタスクでは、設計書を完了条件の基準とする
- `tasks/todo.md` の1ファイル前提をやめ、タスクごとのファイルにする
- 並列化の判定と統合は、backlogで事例を溜め、2026-11-22ごろに作るかを決める
- 代表検証は、ユーザーが新しいセッションを開いて手動で行う

## 検討した代替案

### 引継書どおり、並列の判定から統合までを持つ仕組みを作る

採らない。ユーザーの課題（コンテキストの膨張と目的のぶれ）に対して、並列化は直接の解決策にならない。
コンテキストの分離は、サブエージェントに切り出せば逐次でも得られる。目的のぶれは、並列にしても防げない。
今回の事例も、振り返ると逐次で問題なかった可能性が高い。事例が溜まってから作るかを決める。

### skill（descriptionで発火）で届ける

採らない。ユーザーは「すべてのタスクで考えるべきこと」「skillの発火はモデルの判断なので精度が分からない」とした。
常時ruleでも、適用対象かの判定はモデルに残る。ruleが保証するのは本文がコンテキストにあることまでである。
その差を踏まえて、適用条件をrule内に明記し、短く保つことを要件にした。

### skill＋hookで強制する

採らない。抽象度の高いタスクかどうかを、hookが機械的に判定する手段が無い。スクリプトとテストが増えるわりに、判定はモデルに残る。

### 既存の `rules/task-management.md` に組み込む

採らない。ユーザーは新しい常時ruleを選んだ。この案を退けた理由は、ユーザーではなくAIが補ったものである。
仕分けとサブエージェントへの受け渡しは、計画と進捗の管理とは別の関心事で、
task-managementを膨らませると両方が読みにくくなる。task-managementからは新しいruleを参照する。

### brainstormingに寄せる

採らない。brainstormingは小さな変更では設計を会話だけで済ませ、ファイルを残さない。急ぎの対応タスクは、ここに当たりやすい。
また、ぶれが起きるのはbrainstormingが終わった後の調査中である。プラグインなので本文も変えられない。
brainstormingが設計書を書いた場合だけ、それを完了条件の基準として使う。

### ADRの見直し日を知らせる仕組み（SessionStartのhookなど）を作る

採らない。ADR 0031・0035の見直し日も、誰かが思い出さない限り発火しないことを確認した（`hooks/` を「見直す条件」と日付でgrepし、該当なし。
settingsのhook定義やCIは未確認）。それでも、ユーザーは「ニッチな機能がリポジトリに入るのはダサい」と判断し、
日付の決まった見直しを外部のスケジュールに入れた。backlogにも積まない。

## 結果

- ぶれやすいタスクで、完了条件が記録されないまま書き換わることがなくなる見込み。ただし効果は未測定で、2026-11-22ごろの振り返りで確かめる
- 同じ作業ツリーの複数セッションで、タスクの記録が上書きし合わなくなる
- 諦めたこと: 毎セッション、新しいruleの分だけコンテキストを消費する
- 諦めたこと: 並列化の判定は作らない。並列にする価値がある事例が出ても、当面は都度判断する
- 既知のリスク: 適用条件の判定はモデルに残る。過剰発火（小さなタスクで確認を挟む）と未発火（急ぎのタスクで飛ばす）の両方が起こりうる

### 見直す条件

2026-11-22ごろ、ユーザーが外部のスケジュールで振り返る。見るのは、急ぎのタスクでタスク用ファイルが書かれたか、
②の承認の回数、対象外のタスクでの過剰発火、backlogに溜まった並列化の事例。
決定を支える側だけに偏らないよう、反対側の材料も探して見る。タスク用ファイルが無くてもぶれなかったタスクと、逐次で進めて困った事例である
（2026-10-23、原則レビューの問いP20aを受けて追記）。

決定の根拠は、2026-10-22の1件の対応と、cwワークスペースの `todo.md` 1ファイルに限られる。
「急ぎのタスクで飛ばされた」と「逐次でも問題なかった」は、どちらもこの1件から出ている。
タスク用ファイルが無くてもぶれなかったタスクや、反対の見方は集めていない（2026-10-22、原則レビューの問いP20aを受けて追記）。
この見直しを、常時ruleの分のコンテキストを払い続ける価値があるかを確かめる機会として使う。
効果が見えなければ、ruleを外すか、skillへ移すことも選択肢に含める。

振る舞いは文字列の契約テストでは確かめられないので、ruleを直したときは、実装計画に固定した代表検証3本を手動で回し直す。
