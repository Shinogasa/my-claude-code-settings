# 実作業でコード理解を鍛える学習モードを独立させる

## 背景

既存の `rules/learning-mode.md` は、後から変えるコストが高く、複数案が競合し、
一般化できる判断基準を鍛える。ADR 0007は、同じ作業にL2以上の判断があれば
L1の実装判断を予測の題材にしないと決めた。この設計は上位の設計判断を拾う一方、
例外伝播、非同期制御、依存方向、失敗経路、言語固有の危険な書き方など、
AI生成コードを読み、修正し、レビューする能力を継続して練習する経路にはならない。

既存の「コード参加」は設計Predictと同じ発火条件を使い、その代替イベントとして
5〜10行を書くため、この不足を単独では埋められない。ユーザーは2026-09-15に
「短い常時rule＋詳細skill」の構成と、Write → Modify → Review → Explainの優先順位に同意した。
本ADRはその方針を記録する提案であり、ルールやskillの導入はまだ実施していない。

## 決定

### 1. 設計判断の学習とコード技能の学習を分ける

既存の `rules/learning-mode.md` は設計判断の選択と判断基準を扱い、
新しいコード学習モードは実際のコードの挙動、依存、失敗条件、変更影響を理解・検証する能力を扱う。
コード学習の候補選定には、設計判断用の不可逆性やL2優先ゲートを流用しない。
正しさ・変更容易性・デバッグ可能性などへの実質的な影響、他の箇所への転用可能性、
未実証の能力、小さく真正な課題、検証可能な根拠を要求する。

### 2. 常時ruleと詳細skillの二層構成にする

短い `rules/code-learning.md` はコードを作る・直す・レビューするタスクで候補を検出し、
OFF・除外条件と詳細skillへの入口だけを持つ。演習、フィードバック、転移確認は
`skills/code-learning/SKILL.md` が所有する。ruleは常時効くが、長い教育手順は適格時だけ読む。
両ホストで発火することを実測し、共有本文を特定ホストのAPIに依存させない。

### 3. ユーザーの能動的な生成を優先する

真正かつ安全な課題として成立する範囲で、ユーザーが本質的なコードを書く、
AIのコードを変更する、焦点を絞ってレビューする、AIが解説する、の順に形式を選ぶ。
Writeを成立させるためだけの人工的な穴埋めは作らない。ユーザーの実装・指摘の理由を問い、
実行可能な検査や一次資料で事実を確かめ、条件を一つ変えた転移課題を確認する。
AIの解説を読んだだけ、またはテストが偶然通っただけでは理解の証拠としない。

### 4. 既存workflowと教育上の権限を混同しない

コード学習は「どう学ぶか」を決める。TDD、debugging、security review、最終verificationの
実施順序・合格条件を置き換えない。productionコードに教材用の欠陥を仕込まず、
ユーザーが書いたコードも通常どおり検証する。同じ箇所で旧「コード参加」と新skillを
二重に発火させないため、実装時には旧コード参加を新skillへ移管し、既存ruleには責務境界を残す。

安価な実装モデルが自作コードを模範と認定し、ユーザーの回答を自己採点し、
未検証の一般則を教える閉ループを作らない。事実はcompiler、test、公式資料、
repository契約を優先して確認し、検証不能なら発火を見送る。
教師agentへの具体的なモデル割当とhandoffはADR 0010・0011に接続する別判断とし、
モデルtierだけを正しさの証拠にしない。

### 5. teachとは役割を分ける

新skillは実作業中の短いコード能力演習を扱う。`mattpocock/skills` の `teach` は、
専用workspaceでmissionに沿った体系学習を続ける別候補として扱う。
teachを本ADRで導入せず、両者の記録を自動同期しない。反復したgapが体系学習に適する場合のみ、
ユーザーへteachの候補として提案する。

## 検討した代替案

### A. `learning-mode.md` にコード技能の条件と演習を追加する

既存のON/OFFや記録を再利用できる。しかし設計判断の不可逆性・層ゲートと、
頻繁に現れるコード技能の発火条件は異なる。例外を重ねるとADR 0007のL2優先の意味が曖昧になるため採らない。

### B. 独立した常時ruleだけで完結させる

入口は単純になる。しかしコードを扱わないタスクにも演習・採点・記録の長い手順が常駐し、
既存ruleとの競合とコンテキスト消費が増えるため採らない。

### C. teachをそのまま日常のコード学習として導入する

教材と学習記録を継続できるが、teachは明示起動・専用workspace・mission単位の設計である。
production作業中の小さなコード参加へ転用すると成果物の置き場と学習単位が合わず、
調査で挙がった出力先・初回assessmentなどの課題も残るため採らない。
teach自体の採否は別途判断する。

### D. 実装後の説明またはAIコードの受動的な閲覧だけにする

作業の中断は少ない。しかしユーザーの挙動予測、理由説明、欠陥検出、転移を観測できず、
AIの説明を理解したつもりになる危険が残るため、第一の形式にはしない。

### E. 安価な実装モデルに教材選定・採点まで一任する

モデル間handoffと費用を減らせる。しかし誤った実装を同じモデルが正当化する閉ループを
検出しにくい。上位モデルへの全件昇格も費用対効果を失うため採らず、
検証可能な候補収集と教育判断を分ける。具体的なrouteは代表ケースeval後に決める。

## 結果

設計判断の学習を弱めずに、AI生成コードを自力で読み、変更し、評価する練習を作れる。
一方で、発火入口が二つになり、同一箇所での二重出題、中断過多、AIによる誤feedback、
公開記録への情報漏えいを防ぐ必要がある。実装時に発火・除外・skip・転移のscenarioを検証し、
5〜10件の適格タスクでpilotする。即時の転移成功は長期保持を証明しない。

次の運用値は本ADRでは確定しない。実装計画にある数値・ラベルはpilot用の初期案であり、
導入前のレビューまたは後続ADRで決める。

- 既存学習モードと合わせた停止回数、既習判定の閾値
- 学習記録の保存開始時期・形式と公開可能な抽象化基準
- `★ Code Delta` などの出力ラベルとteach提案の閾値
- 教師agentの具体的route、代表ケースevalの合格基準
