# 日本語文書のレビューをフックとレビュー用サブエージェントで行う

## 背景

AIと一緒に書いた日本語の文書には、比喩的な動詞、英語混じり、主述のねじれといったAI特有の言い回しが残りやすい。
2026-10-01にyomiyasuスキルで学習スキルと常時読み込みの指示ファイル14本を書き直したところ、
意味を変えずに直すべき箇所が多数見つかった（PR #58）。

今後、全リポジトリで書く日本語のMarkdown・設定ファイルと、チームで共有するConfluenceへの投稿に、
同じ基準を自動で適用したい。別のPCでも、リポジトリをクローンしてセットアップすれば使える必要がある。

書き直しの作業を通して、次の2点が分かった。

- yomiyasu同梱のリンターが検出できるのは、表面の書式（絵文字、文末コロン、半角空白、登録済みの語）だけである。
  `skills/learning-mode/references/rationalizations.md` は書き直す前からリンターのスコアが100だったが、
  「推測で省くな」「機構としては空になる」のような直すべき言い回しが残っていた
- 意味のずれや主述のねじれを直すには、yomiyasu本体（SKILL.mdとreferenceで約40KB）を読んだうえでの判断が要る

## 決定

1. Write・Edit・NotebookEditの後に、PostToolUseフックが対象ファイルを記録する。作業の終わりにStopフックが記録をまとめ、
   レビュー用サブエージェント `jp-doc-reviewer`（model: opus）にレビューを依頼する。常時ruleは追加しない
2. Confluenceへの投稿は、PreToolUseフックが送る前に1回だけ止め、下書きのレビューを求める。2回目は通す
3. yomiyasuは `skills/yomiyasu` にsubmoduleとして取り込み、commitを固定する
4. 対象はClaude Codeだけとし、Codex対応は後回しにする

詳細は `docs/superpowers/specs/2026-10-01-jp-doc-review-design.md` にある。

## 検討した代替案

**常時ruleだけで指示する**（「日本語の文書を書く前にyomiyasuを読め」）

採らなかった。指示が守られたかどうかは成果物に跡が残らないので、守られなくなっても誰も気づけない
（`rules/proving-absence.md` の「順序の指示」と同じ問題）。

**ruleとフック（リンター）を併用する**

一度はこれを推奨したが、採らなかった。ruleは普段のコンテキストを数行分消費する。しかも、フックのリンターは
意味の問題を検出できないので、二つを足しても、意味のずれが直る確実さは上がらない。
Stopフックが毎回レビュワーを起動する形なら、ruleが無くても、意味を判断する工程を毎回依頼できる。

**書き込みのたびにリンターを実行して指摘を返す**

採らなかった。書きかけの下書きにも指摘が返り、そのたびにメインのコンテキストに入る。
作業の終わりに1回だけまとめる方が、指摘の回数もコンテキストの消費も少ない。

**リンターの指摘があったときだけレビュワーを起動する**

採らなかった。リンターが満点でも意味の問題が残る文書を、レビューしないまま通してしまう（背景のrationalizations.mdの例）。

**Confluenceの投稿を、ユーザーの指示（UserPromptSubmit）から検出する**

採らなかった。フックが見るのはユーザーの文章であり、守りたい「投稿」という操作ではない。
「wikiに」「さっきのページ」のような言い方の揺れ、何ターンも前の指示、エージェント自身の判断による投稿を取りこぼす。
投稿ツールのmatcherなら、言い回しに関係なく投稿そのものを捕まえられる。

**Confluenceでは、レビュー済みの印（ハッシュ）がある本文だけを通す**

採らなかった。エージェントが下書きをHTMLに整え直すと、1文字違うだけでハッシュが一致しなくなり、正しい投稿まで止め続けることになる。
止める範囲が広すぎると、フックごと無効にされる恐れがある。
1回促して通す方式にし、レビューされずに送られたときは画面に表示する。

**yomiyasuを公式手順（`npx skills add`）で入れる**

採らなかった。`npx skills` にはグローバルに入れたスキルの版を固定する手段が無く、`update` は常に最新版にする
（2026-10-01に `npx skills --help` で確認）。PCごとに版がずれ、上流でリンターの出力や判定が変わると、
フックの振る舞いが知らないうちに変わる。submoduleなら、変わるのはsubmoduleを更新したときだけになる。
また、インストール時にテレメトリが送られる（`--metadata` オプションの説明より）。

**Bash経由の書き込みも、セッション開始後の更新時刻で拾う**

採らなかった。セッション中にユーザーがエディタで直した文書まで、レビューの対象に入ってしまう。

## 結果

- 日本語の文書を書く作業では、作業の終わりにレビューが依頼される。普段のセッションのコンテキストは増えない
- 代わりに、日本語の文書を書くたびにopusのサブエージェントが動き、時間とトークンが増える
- Bash経由の書き込みはレビューされない
- メインのエージェントがレビュー依頼に従わなかった場合、2回目のStopで通す。レビューは強制ではなく、1回促す仕組みである
- Codexでは動かない
