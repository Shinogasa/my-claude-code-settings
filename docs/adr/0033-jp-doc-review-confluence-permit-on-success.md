# Confluence投稿のレビューで、許可を投稿の成功時に消し、レビュワーの完了を確かめる

## 背景

ADR 0024の決定2では、Confluenceへの投稿をPreToolUseで1回だけ止め、2回目は通すことにした。
決定6では、2回目の投稿の前にレビュワーが起動したかを会話記録で確かめ、起動していなければ画面に表示するだけにした。
2回目を通すと同時に、その投稿先の記録と下書きを消していた。

2026-10-13、業務リポジトリのセッションで、同じ本文を同じページへ4回送った。本文は4回とも同じだった。

1. フックが止めた。jp-doc-reviewerは「修正不要」と判断し、ユーザーが投稿を承認した
2. フックは通し、記録と下書きを消した。投稿先のAPIは認証切れで `403 Forbidden` を返した
3. 認証し直して送ると、記録が無いので1回目として扱われ、また止められた。同じ文をもう一度レビューさせることになった
4. レビュワーを起動したが、完了する前に止めた。それでも、記録があったのでフックは通した。投稿は成功した

1回目と4回目では「本文が1回目と同じなので、レビューを通らないまま送られる」と表示された。
1回目はレビュワーが修正不要と判断した結果なので、この表示は誤りである。
4回目では、本当にレビューを通っていない投稿を、表示だけで通した。

問題は2つある。

- 記録を消すのが早すぎる。PreToolUseはMCPが動く前に呼ばれるので、投稿が成功したかを知らない
- 「レビュー済み」の判定が、レビュワーの起動しか見ていない。完了したかどうかを見ていない

このセッションの会話記録では、403の結果が `is_error: true` で残っていた。
公式ドキュメントによると、PostToolUseはツールが成功したときだけ動く。MCPツールがエラーの結果を返したときは、
PostToolUseFailureが動く。

レビュワーの完了は、会話記録から確かめられる。jp-doc-reviewerを呼んだ会話記録19件で数えると、次のとおりだった。
非同期で起動した結果（`toolUseResult.status: async_launched`）が56件あった。
完了通知の `<status>` は、`completed` が52件、`killed` と `failed` が1件ずつだった。
同期で呼んで完了した結果（`toolUseResult.status: completed`）が5件あった。

## 決定

1. 記録と下書きは、投稿が成功したときに消す。ConfluenceのmatcherにPostToolUse（`post-tool-use-confluence`）を足し、
   そこで投稿先の記録と下書きを消す。PostToolUseFailureには何も登録しない。失敗したときは記録が残る
2. 2回目の投稿では、止めた時点より後にjp-doc-reviewerが最後まで終わったかを確かめる。
   レビュワーを起動したtool_useのidについて、同期の結果の `status: completed`、または非同期の完了通知の
   `<status>completed</status>` を探す
   - 終わっていれば、何も表示せずに通す。本文が1回目と同じでも通す。通した本文のハッシュを `sent_digest` として記録する
   - 起動していない、起動しただけ、止まった、失敗した、会話記録を読めないときは、`permissionDecision: "ask"` でユーザーに確かめる
   - 完了通知は、1行の中の最初の通知の、先頭にある `<tool-use-id>` と `<status>` だけを読む。
     通知の `<result>` にはエージェントの出力がそのまま入るので、後ろに混ざった値は読まない
3. 通した後で投稿が成功しなかった場合（記録に `sent_digest` が残っている）、再送の本文が `sent_digest` と同じなら通す。
   変わっていれば `ask` で確かめる
4. `ask` のときは記録を変えない。ユーザーが拒否した本文を、次の呼び出しで黙って通さないためである
5. 事前チェックで例外が起きたとき、または時間予算（5秒）を使い切ったときは `ask` にする。
   終了コード1とフックのtimeout（10秒）は、Claude Codeでは止めたことにならず、そのまま投稿されるからである。
   security-reviewer（2026-10-13）が、この経路を指摘した。変更の前からあった問題だが、記録が長く残るようになったので一緒に直す

ADR 0024の決定2のうち「2回目は通す」と、決定6の「表示するだけ」を、この決定で置き換える。
レビュー後にユーザーの確認を取ってから送ることは、これまでどおり1回目の理由に書いた指示に頼る。

## 検討した代替案

**今のまま、2回目を通した時点で記録を消す**

採らなかった。投稿先のAPIが失敗するたびに、同じ本文のレビューをやり直すことになる。
認証切れのように、本文と関係なく失敗する場面で手間が増えるだけで、何も守っていない。

**レビュー済みの本文のハッシュだけで判定し、同じ本文なら何度でも通す**

採らなかった。ADR 0024で、ハッシュが一致する本文だけを通す案を却下している。
エージェントが下書きをHTMLに整え直すと1文字の違いで止め続けることになる、という理由で、今回もそのまま当てはまる。
今回の決定でハッシュを使うのは、通した後の再送で本文が変わったかを見るときだけである。変わっていても止めずに、ユーザーに確かめる。

**レビュワーが完了していなければ、ask ではなく deny で止める**

採らなかった。レビュワーが途中で止まる環境や、ユーザーがレビューなしで送ると決めた場面で、投稿できなくなる。
ユーザーは「確認で面倒になったら別の方法を考える」と判断した。`ask` ならauto modeでも確認が出る。
公式ドキュメントには、hookのaskはclassifierが黙って承認できないと書かれている。

**完了の判定に、Agentツールの結果の文言（"Async agent launched" など）を使う**

採らなかった。文言は表示用で、変わりうる。会話記録の構造化された項目（`toolUseResult.status`、通知の `<status>`）を使う。
ただし、会話記録の形式自体もClaude Codeの公開された契約ではない。形式が変わって完了を見つけられなくなった場合、
フックは「終わっていない」と判定して `ask` を出す。黙って通すことはない。

**askで送った本文も、`sent_digest` に記録する**

採らなかった。フックには、ユーザーが確認画面で許可したか拒否したかを知る手段が無い。PostToolUseが届くのは投稿が成功したときだけで、
許可されたが失敗した場合と、拒否された場合を区別できない。askの時点で記録すると、拒否された本文まで次の呼び出しで黙って通してしまう。
確認がもう一度出る手間の方が、拒否した本文が送られるより害が小さいと判断した。

## 結果

- 投稿先のAPIが失敗しても、同じ本文ならレビューをやり直さずに送れる。下書きも成功するまで残る
- レビュワーが完了していない投稿は、ユーザーの確認なしには送られない
- レビュワーが修正不要と判断した投稿に、「レビューを通らないまま送られる」という誤った表示を出さない

既知の限界:

- 「レビュワーが完了した」ことは、「この下書きをレビューした」ことを意味しない。依頼文や対象のパスは見ていないので、
  別の文書を頼んだレビューでも、完了すれば通す
- このフックは、エージェントがうっかりレビューなしで送るのを防ぐガードレールである。悪意のあるエージェントは防げない。
  エージェントは状態ファイル（`~/.claude/state/jp-doc-review/`）と会話記録を書き換えられ、完了を装う行を足せる
- サブエージェントがConfluenceへ投稿した場合の判定は、実機で確かめていない。サブエージェントはレビュワーを起動できないので、
  毎回 `ask` になる見込みである

既知のリスク:

- 通した後、ユーザーの確認（`ask`）で送った本文が失敗した場合、同じ本文を再送してもまた確認が出る。`sent_digest` を `ask` で更新しないためである
- 送信が成功しないまま放置された記録は、保存日数を過ぎるまで残る。その間に同じ投稿先へ同じ本文を送ると、止めずに通す
- 投稿先のAPIがエラーを `is_error` の無い通常の結果として返した場合は、PostToolUseが動いて記録を消す。
  このときの動きは、今回の変更の前と同じになる
- HTMLの下書きをリンターが検査していない件は、別に扱う（`tasks/backlog.md`）

403のときにPostToolUseが動かないこと、`ask` で確認画面が出ることは、公式ドキュメントと会話記録から判断した。
実機では確かめていない（`tasks/backlog.md` の「実機ではまだ確かめていない点」）。

## 根拠

- Claude Codeのhooksの公式ドキュメント（https://code.claude.com/docs/en/hooks 、2026-10-13確認）。
  PostToolUseFailureの説明（"an MCP tool returned an error result"）、`permissionDecision` の `ask`、auto modeでのaskの扱い
- 2026-10-13の事象の会話記録。403の結果が `is_error: true` であること、4回目のレビュワーの通知が `<status>killed</status>` であること
- jp-doc-reviewerを呼んだ会話記録19件での、結果の `status` と通知の `<status>` の集計
- ADR 0024（決定2・6、却下した「ハッシュがある本文だけを通す」案）
