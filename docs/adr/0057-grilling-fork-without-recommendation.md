# grilling skill を上流からフォークし、推奨回答を外す

## 背景

解く問題: grilling で、ユーザーが自分の判断基準を書かずに AI の推奨へ乗る回答（defer）を減らす。

上流 `mattpocock-skills` の grilling skill は、各問いに推奨回答（➡️）を付け、「yes で推奨を受け入れる」形で問うよう指示している。
この指示は学習の開示順（`rules/learning-mode.md`。予測の前に推奨を出さない）とは逆向きである。
これまで `skills/grilling` は ADR 0035 の形で上流 submodule を指す symlink だった。

### 上流の言い分

「yes で推奨を受け入れる」は、2026-10-07 に上流で足された（`95249b0`、PR #1193、issue #706）。
issue は、推奨と問いの向きが逆だと、同意するのに「No、でも推奨には賛成」と答えることになり、紛らわしいと報告していた。
上流が守ろうとしているのは、推奨に素早く、曖昧さなく同意できることである。
このリポジトリの狙い（同意の前に、ユーザーが自分の理由を書くこと）とは逆を向いている。
推奨を出さなければ、issue の言う向きの食い違いもそもそも起きない。

### 観測

2026-11-19 の利用実態の観測（`tasks/backlog.md` の T1〜T6）で、grilling の返答は承認が大半だった。
2026-09-01〜11-25 の全プロジェクトのメイン会話（390ファイル）で、grilling のラウンドへの返答を数え直した。

| | ラウンド | 問い | 全問を一括で返したラウンド | 理由の印がある返答 |
|---|---|---|---|---|
| ➡️ あり | 30 | 127 | 21 | 24（問いの約19%） |
| ➡️ なし | 5 | 20 | 1 | 10（問いの約50%） |

数え方: AI の本文に `❓ **Q<n>**` があればラウンドとし、次にユーザーが打った発言を返答とした。
返答は番号で問いごとに分けた。分けられなければ、返答全体を1つとした。
理由の印は「なぜなら・ので・から・ため・理由・と思う・だと・なら・けど・が、」で、意味までは見ていない。
集計のスクリプトは git 管理外の `tasks/todo/learning-usage-review/bin/grilling_reasons.py` にある。T6 で研究ノートと一緒に切り出す。

この差は根拠としては弱い。

- ➡️ なしの5ラウンドは、2026-11-19 の1セッションだけである。しかも、ユーザー本人が ➡️ を外すよう指示した後だった。本人が意識して理由を書いた可能性を除けない
- 理由の印は語の一致にすぎない。理由を書かずに「aで」とだけ答えた返答は理由なしと正しく数えられるが、印の語を含む承認も「理由あり」に入る

## 決定

2026-11-25、ユーザーがフォークを選んだ。

- `skills/grilling` を実ディレクトリにする。上流 `4ae2317`（`v1.3.2-3`）の `SKILL.md` と `agents/openai.yaml` を写す
- 書き換えるのは推奨回答の指示だけにする
  - 各問いには自分の答えを付けない。書式から ➡️ を除く
  - 問いは、ユーザーが答えと理由を書く形にする。選択肢は並べるだけにし、どれも推す印を付けない
  - AI の見解は、ユーザーが答えた後に出す。賛成する点と反対する点（あるものだけ）、それぞれの理由、状況を変える事実を述べる。反対なら、次のラウンドでその根拠を添えて問い直す。決めるのはユーザーである
- 配布の経路は変えない。`manifests/skills.json` の `shared` に残す
- 上流の更新の取り込み忘れは、テストで検出する。フォーク元の上流ファイルの blob ハッシュをテストに持たせ、submodule を進めて上流が変わったら落とす

選んだ理由（ユーザー）: 前例の ADR 0054（handoff）と同じ判断である。rule と skill の指示が食い違う形は避けたい。

## 却下した案

### rule で上書きする（symlink のまま、rule に「grilling では ➡️ を付けない」と書く）

上流の更新は自動で入る。しかし、skill の本文には「推奨を付けよ」が残る。
同じ場面で rule と skill の指示が食い違い、どちらを採るかがエージェント任せになる。ADR 0054 で退けた理由と同じである。

### 薄いラッパー（自前の SKILL.md から上流を読ませ、推奨の部分だけ上書きする）

上流の更新は入るが、上流の本文の「推奨を付けよ」がそのまま読まれる。rule での上書きと同じ食い違いが残る。

### 上流へ PR を送る

上流は推奨へ素早く同意できる方向へ変えたばかりである（上流の言い分を参照）。
推奨を外すのは、学習を目的にしたこのリポジトリの事情による。上流の狙いと逆を向くので、送らない。

### 取り込み忘れを検出しない（ADR 0054 の handoff と同じ扱い）

フォークの手間を負うのは、保守するユーザー本人である。忘れると、気づかないうちに上流の改善が入らないままになる。
ハッシュの検査はテスト1つで済み、上流が変わったときだけ手間がかかる。

## 結果

- grilling の各ラウンドで、ユーザーは答えと理由を自分で書く
- ラウンドの進みは遅くなりうる。推奨があれば「yes」で済んだ問いにも、答えを書く手間がかかる
- submodule を進めて上流の grilling が変わると、`TestGrillingFork.test_upstream_unchanged_since_fork` が落ちる。
  差分を読んで `skills/grilling` に取り込み、テストのハッシュを更新する。submodule を進めない限り、上流の更新には気づかない
- `TestGrillingFork` はほかに次の点を検査する。symlink に戻っていないこと、`shared` にあること、➡️ と推奨回答の指示が無いこと、回答の後に見解を出す指示があること

### 見直す条件

フォークの後に grilling を使ったセッションが5つたまったら、AI が背景の表と同じ数え方で測り直す。
きっかけは `tasks/backlog.md` の「defer の場面で理由を促すか」に着手するときか、年1回の棚卸し（ADR 0055）の早いほうにする。

- 理由の印がある返答が、問いの約19%（➡️ ありの値）と変わらないなら、問い方をもう一度見直す
- 上流が推奨回答を任意にしたら、フォークをやめて symlink に戻す

## 根拠

- 上流 `SKILL.md` の8行目と24行目（`4ae2317` の時点）
- 上流のコミット `95249b0`、PR #1193、issue #706（2026-11-25 に `gh` で本文を読んだ）
- 観測の元レポート（git 管理外の `tasks/todo/learning-usage-review.md`）。T6 で `docs/research/` に切り出す
