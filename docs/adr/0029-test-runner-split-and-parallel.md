# テストを遅い組と分けて、uvの一時環境で並列に実行する

## 背景

全テストを `python3 -W error::ResourceWarning -m unittest discover -s tests -p 'test_*.py'` で流すと、
830件で1427秒（約24分）かかっていた。PRのたびに流す手順として長すぎ、待ち時間が作業を止めていた。

### 測定（2026-10-09、ローカルのmacOS・12コア）

| 指標 | 値 |
|---|---|
| 全件の実時間 / user / sys | 1427秒 / 266秒 / 166秒 |
| 遅い上位40件のうち `test_setup_cli` と `test_setup_preflight` | 39件・合計718秒（1件13〜31秒） |
| `setup.sh --all` 1回（テストと同じスタブ条件） | 12.85秒。うち53%は `python3 setup-state.py` 199回の起動 |
| fixtureのコピー（`skills/` など約400ファイル） | 3〜5秒。CPUはほぼ使わない |
| 中身の無いファイルを419個作る | 0.03秒 |

実時間がCPU時間の3倍以上あった主な理由は、このMacで中身のあるファイルを書くたびに入る待ちである。
Jamfの管理下でXProtectが動いており、スキャンによる待ちと推定しているが、どのプロセスかは未確認。

## 決定

打ち手の組み合わせ（分離と並列化をこのPR、Bを別PR）とPR作成時の確認は、2026-10-09にユーザーが推奨案を承認して決めた。

1. **`tests/run.sh` をテストの入口にする。** 既定では、1件ごとに `setup.sh` を実際に実行する
   `test_setup_cli.py` と `test_setup_preflight.py` を除いて流す。`--all` で全件を流す。
   日常の確認は既定の組、PRの前は `--all` を使う
2. **並列化には `uv run --no-project --with pytest==9.1.1 --with pytest-xdist==3.8.0` を使う。**
   uvの一時環境に入れるだけなので、システム・dotfiles・リポジトリに依存を足さない。uvはdotfilesのBrewfileで管理済み。
   hookや `setup.sh` など本番で動くコードは、これまでどおり標準ライブラリだけで動く
3. **pytestへは `tests/` 直下の `test_*.py` だけを渡す。** pytestは既定でサブディレクトリまで集めるため、
   コード学習の演習用fixture（`tests/fixtures/code-learning-host-probe/`）が実行されて失敗した。
   unittest discoverと同じ範囲にそろえる
4. **uvが無い環境では、通知したうえで逐次のunittestへ切り替える。** 今のところ、uvの無い環境は無い
   （両ホストとも同じMacで動き、uvはBrewfileで管理している）。切り替えは、念のための逃げ道として置く
5. **PRの前の全件実行を、記憶ではなくhookで確かめる。** `tests/run.sh --all` は、未コミットの変更が無い状態で全件が通ると、
   HEADを `.git` の下（`tests-all-passed`）へ記録する。PR作成時のhook（`hooks/require-full-tests-before-pr.py`）は、
   テストを流さず、記録とHEADが一致するかだけを見る。一致しなければ止める。
   全リポジトリに効くhookなので、`tests/run.sh` に目印（`TESTS_ALL_PASSED_STAMP`）があるリポジトリだけを対象にする。
   gitが壊れているなどで確かめられないときは止める

決定1〜5は「待ち時間で作業を止めない」ための手段である。これとは別の軸として、再現性のために
pytestとpytest-xdistのバージョンを固定する（日によって結果が変わらないようにするため）。

## 検討した代替案

### B. `setup.sh` が `setup-state.py` を呼ぶ回数をまとめる（別PRで実施）

本番の `setup.sh` も速くなる根本的な対策で、テストの約半分の時間に効く。採らなかったのではなく、
本番コードの変更で影響範囲が大きいため、別の作業（ADR 0030）に分けた。

### C. fixtureのコピーを減らす（当面は採らない）

コピーの待ちは1件3〜5秒ある。ハードリンクにすると約1秒になるが、テストがコピー先を書き換えると
本物のリポジトリまで書き換わるので使えない。必要なディレクトリだけをコピーする案、クラスごとに1回だけコピーする案もある。
並列化で全件が約2分半まで縮み、日常の組は40秒弱になったので、当面は採らない。
Bが入った後もなお遅ければ、再検討する。

### pytestとpytest-xdistをシステムまたはリポジトリの依存として入れる

uvを介さずに済むが、依存ゼロのリポジトリに初めて外部依存を持ち込む。両ホストの環境構築と、
dotfiles（Brewfile）にもインストール手順が波及するため採らない。

### 標準ライブラリだけで並列実行スクリプトを自作する

依存は増えないが、テストの分配、結果の集約、失敗時の出力を自前で持つことになる。
uvがすでに管理下にあり、実績のあるpytest-xdistをそのまま使えるため採らない。

### PRの前に `--all` を流すことを、記憶とREADMEだけに任せる

仕組みは増えないが、このリポジトリにはCIが無いので、流し忘れても誰も気づかない。
hookはシェルとして動くだけで、LLMのコンテキストもトークンもほぼ使わないため、記憶に頼るより安い。

### PR作成時のhookで `--all` そのものを流す

記録を持たずに済むが、PRを作るたびに2分半ブロックされる。記録とHEADの照合なら確認は一瞬で終わり、
テストを流すのはコミットが変わったときだけで済む。ドキュメントだけのコミットでも流し直しが要るのは、許容する。

### 遅いテストを分けずに、並列化だけをする

全件で約2分半まで縮むが、日常の確認としてはまだ長い。分けておけば、Bが入って遅い組が速くなった時点で、
分離をやめる判断もできる。

## 結果

| 実行 | 件数 | 実時間 |
|---|---|---|
| 変更前（unittest、逐次、全件） | 830 | 1427秒 |
| `tests/run.sh`（既定の組） | 741 | 38秒 |
| `tests/run.sh --all`（2回） | 835（追加した5件を含む） | 162秒 / 154秒 |

- 日常の確認が約24分から40秒弱になる
- PR前の全件実行も、並列化で数分になる
- 並列で流しても干渉しないことは、`--all` の2回の実行で確かめた。ただし2回の結果は、干渉が起きないことの証明ではない。
  固定パス・lock・ポートを共有するテストを今後足すと、並列でだけ失敗する可能性がある
- テストの実行にuvが要るようになる。無い環境では逐次に戻り、約24分かかる。今のところ、そうなる環境は無い
- PR作成時に、HEADで全件が通った記録が要る。ドキュメントだけを直したコミットでも、`--all` を流し直す必要がある
- hookはClaude Codeにだけ配線した。Codexには、日本語レビューのhookと同じく配線していない

### 既知のリスク（2026-10-09 security-reviewerの指摘から）

- **記録は手で書ける。** `.git/tests-all-passed` にHEADを書けば、テストを流さずに通せる。このhookは記憶頼みを防ぐガードレールで、
  攻撃に対する境界ではないので受け入れる。本当に強制するならCIが要る
- **推移的依存は固定していない。** pytestとpytest-xdistは `==` で固定したが、その依存（execnet、pluggyなど）は固定していない。
  露出は開発者の手元の実行に限られる。必要になったら、ハッシュ付きのロックファイルを `--with-requirements` で渡す
- **未追跡ファイルの変化は、記録の判定に使えない。** 記録の条件は、追跡中のファイルに未コミットの変更が無いことだけ。
  未追跡ファイルも含めると、gitignoreされていない `skills/synced/` が常にあるため、記録が一度も書かれなくなる
- **`gh -R x pr create` などの書き方は見逃す。** PR作成の判定は日本語レビューのhookと共有しており、先頭の3語しか見ない。
  直すなら両方のhookにかかわるので、別の作業とする（backlog）
- **判定できないときは止める。** 入力や共有の判定関数を読めないとき、文字列から `gh`・`pr`・`create` を含むかで推し量り、含めば止める
