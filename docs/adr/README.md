# ADR（Architecture Decision Record）

**採用した設計判断と、採用しなかった選択肢とその理由**を残す。

## なぜ spec / plan と別に置くか

`docs/superpowers/` には既に設計文書がある。役割が違う。

| 置き場 | 何が書いてあるか | 寿命 |
|---|---|---|
| `docs/superpowers/specs/` | **どう作るか**。実装対象の構造・インタフェース | 実装が終われば参照されなくなる |
| `docs/superpowers/plans/` | **どの順で作るか**。手順とタスク分解 | 実装完了で役目を終える |
| `docs/adr/` | **なぜそう決めたか**。捨てた選択肢と、捨てた理由 | **永続。次の判断の入力になる** |

spec は「現在の姿」を書くため、変更されると過去の姿が消える。ADR は
**判断の時点で何が分かっていて何が分かっていなかったか**を凍結する。

ブラッシュアップのたびに前提を再調査するのを避けるのが目的。
「なぜこの制約があるのか」を ADR で辿れれば、既に否決した案を
もう一度検討し直す無駄が消える。

## 書式

```
docs/adr/NNNN-kebab-case-title.md
```

`NNNN` は 4桁のゼロ埋め連番。**欠番を作らない。取り下げても番号は再利用しない**
（他の ADR からの参照が壊れるため）。

```markdown
---
adr: 1
date: YYYY-MM-DD
status: accepted        # proposed | accepted | superseded by NNNN | deprecated
---

# タイトル（判断の対象を名詞句で）

## 背景

何が問題で、なぜ今決める必要があるのか。**測定値があれば必ず入れる。**

## 決定

決めたこと。断定形で書く。

## 検討した代替案

採らなかった案と、**採らなかった理由**。ここが ADR の本体。

## 結果

この判断で何が良くなり、何を諦めたか。既知のリスクも書く。

## 根拠

参照した一次資料。**実在を確認したものだけ**を書く。
```

## 運用

- **状態を書き換えず、新しい ADR で上書きする。** 判断が変わったら
  新しい番号で書き、古い方の `status` を `superseded by NNNN` に変える。
  本文は消さない（当時の前提が次の判断材料になる）
- **却下した案を必ず書く。** 決定だけの ADR は、次に同じ案を検討し直す無駄を防げない
- **測定値を書く。** 「なんとなく良くなかった」は再検証できない
- このリポジトリは **PUBLIC**。業務固有情報は書かない
  （`rules/learning-mode.md` の抽象化ルールと同じ基準）
