# 本人が宣言した重点学習領域だけコード学習の上限を上げる

## 背景

学習イベントの上限は「pilot中は合計最大2イベント、うちコード学習は最大1イベント」だった。
この数値はADRではなく設計書（`docs/superpowers/specs/2026-09-21-programming-learning-integration-design.md`）に
pilotの初期値として書かれており、ADR 0017は運用値の正本をこの設計書に委ねている。
上限を置いた理由は次の2つで、どちらも測定に基づく値ではない。

- コード学習を1回にしたのは、学習量を減らすためではなく、一つの能力に十分な自己説明・検証・転移を行うため
  （`docs/research/2026-09-16-code-learning-mode-design.md`）
- 合計上限は「中断が多すぎると自己説明の質が下がりうる」という懸念から置かれ、pilotで調整する予定のまま残っていた

ユーザーはGoの初学者で、コード学習（Write・Investigateなど）を多くこなしたい段階にある。
直近のGoの不具合調査では、コード学習1回と設計Predict1回で合計上限に達した。
その後の修正方針の相談は学習なしで進み、理解が追いつかないまま答えを受け取る場面が出た。

### 測定（学習store、2026-09-30〜2026-10-08）

| 指標 | 値 |
|---|---|
| 能力record | 設計Predict 10件、コード学習 1件 |
| コード学習のイベント | 2件（1件はskip、1件は完了） |
| 完了したコード学習イベントの回答待ち | 14回 |
| 上限に達した回数 | **未確認**（operationにタスクIDも上限到達の記録も無い） |

コード学習は設計Predictより一桁少ない。ただし上限が原因か、候補の検出が少ないことが原因かは、
この記録からは切り分けられない。

## 決定

1. **ユーザーが重点学習中と宣言した言語・領域でだけ、上限を上げる。** コード学習は最大3イベント、
   設計Predictは最大2イベント（従来どおり）とし、合計の上限は設けない。
   それ以外のタスクは従来の上限（合計2・コード学習1）のままにする
2. **宣言はグローバル指示のユーザープロファイルに置く。** CLAUDE.mdは両ホストへリンクされるので、
   どちらのホストでも同じ宣言が効く。外すのも本人が行う。最初の宣言は「Go（初学者）」とする
3. **判定できないときは通常の上限を使う。** 宣言の有無や記録の量から習熟度を推定しない
4. **上限で見送った候補を `end_reason: cap_reached` のoperationで残す。** イベント数には数えない。
   次の見直しで、上限が候補を落としているのか、検出自体が少ないのかを切り分けるために使う
5. **上限の数値は共通方針だけに置く。** CLAUDE.mdの数値の重複（「上限2回」「最大2回（コード学習は最大1回）」）を
   参照に置き換える。ADR 0021の「共通方針の正本は1箇所」が、CLAUDE.mdの側で崩れていたため

## 検討した代替案

### A. 全領域で固定値を上げる

最も単純で、判定も要らない。しかし、ある程度書けるKotlinの作業でも中断が増える。
慣れた言語では1タスクに未習得の候補が複数出ることが少なく、上限1回が詰まりの原因になりにくい。
効果の無い領域にまで中断の費用を払うことになるため採らない。

### B. 学習storeの記録から習熟度を自動で判定する

宣言を外し忘れる心配が無い。しかし、ADR 0017の「記録が無いだけで未習得と判断しない」と衝突する。
記録はpilot開始後のものしか無く、Goの記録0件は未習得の証拠にならない。
正答率や成功数で回数を自動調整する案はADR 0001 A3（難易度サーボ）で保留しており、
集計の機構を先に作る必要があるという理由は今も変わっていない。

### C. AIが会話から習熟度を推定する

設定が要らない。しかし、推定が正しかったかを外から検査できない。上限を上げる側にも下げる側にも
都合よく倒せるため採らない。

### D. 上限に達したら、延長するかを1回だけ尋ねる

習熟度の判定が要らず、「理解が追いつかない」場面に直接効く。しかし作業の途中で問いが1つ増え、
上限が実質的に柔らかい既定値に変わる。まず宣言方式とcap_reachedの記録で測り、
宣言外の領域で見送りが多いと分かってから追加を判断する。

### E. Kotlinの「忘れ」に備えて、Kotlinも上限を上げる

Goを続けた後にKotlinへ戻ると、構文やAPIを忘れる場面が見込まれる。しかし、ADR 0017は
公式資料や検索を使うことを認めており、調べれば戻る種類の忘却は演習で補う対象ではない。
保持の確認は共通方針の「7日以上空いた関連実作業で保持確認の候補に戻す」が担う。
ただしこの規定は記録がある能力にしか効かず、Kotlinの記録はまだほぼ無い。上限を変えてもこの穴は埋まらない。

## 結果

- Goの作業では、1タスクで最大5イベント（コード学習3・設計Predict2）の学習機会が得られる
- 1回のコード学習で回答待ちが14回あった実績があり、Goの作業は従来より長くなる。止めたいときはskipと学習OFFで止める
- 宣言を外し忘れると、習熟した後も多めの上限が続く。外す判断は本人に委ねる
- cap_reachedの記録で、上限と検出のどちらが詰まりの原因かを次の見直しで測れるようになる

### 既知のリスク

- 「タスクで主に読み書きするコードが宣言に一致するか」はAIの判定で、外から検査できない
- コード学習の候補が拾われない問題（検出不足）は、この変更では解決しない。backlogで別に扱う
- 上限の数値は今回も測定に基づかない。cap_reachedの記録がたまってから見直す
