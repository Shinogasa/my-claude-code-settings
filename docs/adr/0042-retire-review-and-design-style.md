# ReviewAndDesignスタイルを廃止し、完了報告の3点をruleへ移す

## 背景

`output-styles/review-and-design.md` は、2026-03-17 に作った `mentoring` スタイルの名残である。
作ったときは、WHYの解説、TODO(human)、質問プロンプト、★ Review、★ Design Decision を1つにまとめていた。
その後、教育の役割は ★ Predict / ★ Delta（`rules/learning-mode.md`）とコード学習（`skills/code-learning/`）へ移った。
スタイルのコア原則（WHYを伝える順序、品質を見る目、設計の考え方）と質問プロンプトは、
これらと役割が重なったまま残っていた。ADR 0040 で公式の best-practices と比べたとき、この点を別タスクに回していた。

2026-07-06〜10-28 の会話記録（メイン会話のassistant発言 20,437件。見出しの完全一致で数えた）を調べた。

- ★ Review は33件。7月の多くは、ユーザーが書いたコードを褒めるだけで、指摘が無かった。
  ★ Code Delta と役割が重なり、スタイル自身が禁じている「問題なし」の項目も書いていた。
  9月以降は、残っているリスク・限界・未確認を明かす内容に変わった。価値があったのはこの部分である。
  観点の内訳は Maintainability 28、Security 17、Performance 9
- ★ Design Decision は33件。実際には、ユーザーに判断を依頼する書式として使われていた。
  毎回付く `Recommendation` は、学習モードの「予測の前に推奨を出さない」とぶつかりうる
- ユーザー自身は「Reviewはさらっと読むだけで印象に残っていない。Design Decisionはさらに残っていない」と述べた

公式の output-styles ページは、スタイルを「セッション全体での役割・口調・応答の形式」の仕組みとしている。
特定の種類のタスク向けの手順は skill に、必ず起きるべきことは hook に置く、としている。
best-practices ページは、頼まれたレビュアーは必ず何かを見つけるので、正しさに関わる指摘だけにして
スタイルは指摘させない（`skip style`）とし、効くのは書いた経緯を見ていないレビュアーだとしている。
★ Review は、自分で書いた直後に同じ文脈で行う自己レビューだった。

一方で、スタイルの冒頭にある「ユーザーの成長を最優先に考える」という目標は今も変わっていない。
学習モードには発火の下限が無く、判断点の無いタスクでは発火しない。
そのため学習イベントの外では、成長のための仕組みが何も動いていなかった。

## 決定

1. `output-styles/review-and-design.md` を削除し、`settings.json.template` から `outputStyle` を外す。
   `setup.sh` を次に実行すると、ADR 0041 の仕組みで `~/.claude/settings.json` からも消える
2. 学習イベントの外での「成長最優先」は、AIの仕事をユーザーがレビューできる形で渡すことで実現する。
   完了報告に次の3点を入れる（AIが案を出し、ユーザーが承認した）
   - AIが自分で決めたこと（ユーザーが決めたことと分けて書く）
   - その判断の理由を1行で書く（学習イベントの対象にした判断では、開示順に従い書かない）
   - 残っているリスク・限界・未確認
3. 3点は `rules/` に置く（ユーザーが ★ Predict で選んだ）。どのファイルに足すかはAIが決め、
   既存の `rules/output-formatting.md` に節を足した。両ホストへリンク済みで、Codex の必須読み込みにも入っているため、
   `CLAUDE.md` を直さずに済む
4. ★ Review のチェックリスト、★ Design Decision の書式、質問プロンプト、メンター役の宣言は引き継がない

## 検討した代替案

### スタイルを残し、中身を3点だけに縮める

報告の形式なので、output style の役割（応答の形式）に当てはまると見ることもできる。
しかし `output-styles/` は Claude Code にしかリンクされず、Codex CLI での作業では3点が効かない。
成長という目的はホストに依存しないので採らない。

### `CLAUDE.md` に数行足す

両ホストが読む点は rules と同じである。しかし ADR 0040 で `CLAUDE.md` を、詳細は rules へ案内する目次に近い形へ絞った。
規約の本文を `CLAUDE.md` に戻すと、その方針に逆行するので採らない。

### ★ Review を独立レビューとして作り直す

公式が効くとする「書いた経緯を見ていないレビュアー」は、`/code-review` と、既にある `superpowers:requesting-code-review` が担っている。
同じ仕組みをスタイルで作り直す必要は無い。

### 「メンターとして振る舞う」役割の宣言を rule に移す

役割と口調は `rules/persona.md` が決めていて、「一緒に作業を進めるパートナー」「方針を決めるのは相手」としている。
メンターの宣言を足すと、この役割と食い違う。目標そのもの（シニア/スタッフ/テックリードを目指す）は、
`CLAUDE.md` のユーザープロファイルに書かれている。

## 結果

- 学習と重複していた指示が無くなる。毎セッションの読み込みは、スタイル約110行が減り、rule が約12行増える
- 学習イベントの外でも、AIが決めたことと残るリスクが完了報告に必ず載るようになる。
  ただし rule も指示にすぎず、強制はされない。★ Review が記憶に残らなかったのと同じく、
  載っていても読まれないことがありうる。効いているかは、会話記録を同じ方法で数え直して確かめる
- 各プロジェクトの `.claude/settings.local.json` に `outputStyle: ReviewAndDesign` が残っているかは確かめていない。
  残っていると、そのプロジェクトでは名前が一致せず、Default スタイルになる
- 会話記録の集計は 2026-07-06 以降しか残っていない。サブエージェントの発言と、見出しを崩して書いたブロックは数えていない

## 根拠

- https://code.claude.com/docs/en/output-styles （2026-10-28取得。スタイルの役割、他の仕組みとの使い分け、名前が一致しないときの挙動）
- https://code.claude.com/docs/en/best-practices （2026-10-28取得。「Review against your spec」の `skip style`、独立レビュー）
