# 完了条件を深くする4問と、道具で測ったかの区別を既存のruleに足す

## 背景

ユーザーが Felix Rieseberg のブログ「How to be more ambitious」（2026-10-13）を読み、ルールやスキルに役立てられる部分が無いかを調べるよう依頼した。
ユーザーが特に有効だと考えたのは、Depth の「Insist on the same instruments used by the best in the industry」だった。
記事はこれを、専門家のように振る舞えと頼んでも語彙が変わるだけで方法は変わらない、という観察から導いている。

既存の仕組みとの対応を調べると、外部の判定者（`verification-before-completion`、`/code-review`）と、
信じていることの検証（`rules/proving-absence.md`）は既にあった。
一方で、**主張を確かめるのに、読むだけでなくその分野の道具を使う**ことを求める規約は無かった。
また、作業を「大きく」ではなく「深く」する問いを立てる場面も無かった。

これは予防策である。性能・並行性の主張を読んだだけで「問題なし」とした失敗は、このリポジトリでは観測していない（会話記録も数えていない）。
解きたいのは、Goを重点学習中のユーザーがAIのコードをレビューする場面で、AIの「問題なし」が読んだだけなのか測ったのかを区別できない状態である。
成功は次の2つで判定する。

- 完了報告や不在の主張に「未確認（読んだだけ）」か、使った道具の名前が出る
- タスク用ファイルに、4問の答えで計画を変えた行が残る

どちらも出ないまま関連するタスクが続いたら、この決定を見直す。

手法ごとの分析と、採らなかった手法の再検討の条件は `docs/research/2026-11-04-ambition-blog-analysis.md` にまとめた。

## 決定

1. **深くする4問を `rules/fix-completion-criteria.md` の「始めるとき」に置く。**
   記事のメタプロンプトを、「暫定の完了条件」を書くときに自問する4問にした。
   ①第一線の人なら頼まれていなくてもやること、②最も生の材料、③方法と道具、④自分とユーザー以外で正しさを示すもの。
   完了条件を変えない答えは①として計画に足し、アウトプットを広げる答えは②として承認を待つ。
   役割は名乗らせず、その人がやる方法を実際にやる。計画を変えた答えだけは、タスク用ファイルに1行ずつ残す。
   置き場所はユーザーが選んだ。4問の選び方と文面はAIが決めた。答えを残すことは、原則レビューの指摘を受けてユーザーが決めた
2. **性能・並行性・データの「無い」には、道具で測った結果を範囲の根拠として求める。**
   `rules/proving-absence.md` の「適用する場面」に足した。「競合しない」「遅くならない」も不在の主張なので、
   既存の4点形式に乗る。測っていなければ範囲の根拠を「未確認（読んだだけ）」とする
3. **肯定の主張は完了報告で拾う。** 「速くなった」などは不在の主張ではないので2で漏れる。
   `rules/output-formatting.md` の `残るリスク・未確認:` に、測らず読んだだけの主張を書くよう1行足した。
   2と3の組み合わせは、AIが3案の長所と短所を示し、ユーザーが選んだ

## 検討した代替案

### 4問をskillにする

最初にAIが出した案。ユーザーが起動したときだけ動くので、既存ruleとはぶつからない。
しかし、skillはdescriptionとの一致で発火するので、「深くして」と言わない限り、ほぼ手動の呼び出しになる。
ユーザーがこの点を指摘した。毎セッション読み込まれ、計画を書くタスクだけで効く既存ruleに相乗りする方を採った。

### 4問を自問だけにし、答えを残さない

最初にAIが書いた形。書く手間と行数を抑えられる。しかし決定2で、跡が残る形式を理由に `proving-absence` を選んでおきながら、
4問だけ跡が残らないのは筋が通らない。形だけになっても気づけない（原則レビュー P03a）。
4問すべての答えを書く欄も考えたが、計画を変えない回にまで書かせると、書くこと自体が形だけになる。
そのため、計画を変えた答えだけを残す形にした。

### 4問をUserPromptSubmitのhookで毎回差し込む

確実に発火するが、typo修正のような作業にも4問が出る。`rules/fix-completion-criteria.md` が対象外としている
「すぐ済む明確なタスク」まで巻き込むので採らない。

### 道具の指定を完了報告だけに入れる（A）

最初にAIが出した案。報告に跡が残り、ラベルで数えられる。しかし効くのが最後の報告のときだけで、
測るより「未測定」と書いて済ませる方向に流れやすい。主張をするときに効く `proving-absence` を主にした。

### 道具の指定を新しいruleにする（B）

道具の例を領域ごとに十分書け、`paths:` で `*.go` に絞れば常時読み込むコストも出ない。
しかし順序の指示になりやすく、守ったかの跡が残らない。これは `rules/proving-absence.md` が退けた形である。
また `paths:` 付きのruleは `/compact` の後に再注入されない。道具の例が増えて既存ruleに収まらなくなったら、分けることを検討する。

### 「シニアエンジニアとして振る舞う」役割宣言を戻す

ユーザーは、旧 output-style のシニアエンジニア指示がinstrumentsにつながると考えていた。
記事は、役割宣言は語彙を変えるだけだとしている。ADR 0042 の集計（2026-07の ★ Review は指摘の無い称賛が多かった）とも矛盾しない。
戻さず、4問の注記に「役割を名乗らせない」と書いた。

ただし、反対側の根拠（役割の指定が出力を良くする、または道具の指定が効かないとする研究や事例）は探していない。
裏付けはこの記事1本と、ADR 0042 の集計が矛盾しないことだけである。0042 の集計では、効かなかった原因が役割宣言なのか、
自己レビューだったからなのかを分けられない。反対側の根拠が見つかったら、この却下を見直す。

### 記事の他の手法を取り込む

Unreasonable goals、Produce new knowledge、Altitude を自律的に広げる規約、Range の名詞→動詞と一団の編成は、今回は採らない。
理由と、それぞれを再検討する条件は分析資料に書いた。要点は次のとおり。

- Unreasonable goals: 常時の規約にすると、成功の捏造や検証の省略を招きやすい
- Altitude: 「影響を最小化」と範囲の固定にぶつかる。4問の1つ目が、提案の形で一部を担う
- Produce new knowledge、Range: このリポジトリの作業では場面が少ない

## 結果

- 計画を書くタスクで、範囲を広げずに検証や材料の質を上げる問いが立つ
- 性能・並行性の「問題なし」を、読んだだけで出すことが規約上できなくなる。出しても「未確認（読んだだけ）」と跡が残る
- 常時読み込むruleが約19行増える
- 4問の答えのうち、計画を変えなかったものは残らない。「問うたが変わらなかった」と「問わなかった」は区別できない。
  計画を変えた行が出ないまま、計画を書くタスクが続いたら、置き場所か形を見直す
- 道具の例はGoとDBだけである。ほかの領域では「その分野で使われる道具」をAIが判断する
- 記事本文は取得用のサブエージェントの要約と短い引用で読み、同じ日に別のサブエージェントに主張ごとに照合させた。4問は記事と一致し、決定は変わらなかった（分析資料の「本文との照合」）。AIが全文を直接読んだわけではない
- 記事の手法は著者の経験にもとづき、測定や失敗例は示されていない。0048 の裏付けは、この点でも弱い
