# 仕事の原則集を、書き出したコピーと独立したレビュワーで届ける

## 背景

非公開リポジトリ `sakurai-transcripts` で、動画23本から仕事の原則を抽出し、確認済み25件の原則集を作った（蒸留の1段目）。
各原則には、使う節目（`spec`・`plan`・`advice`）と、成果物に向けた問い（`review_question`）がある。

2段目では、この原則集を次の2つの用途で使う。

1. 仕事の進め方の相談への助言
2. 仕様書・ADR（主）と実装計画（従）を書き終えたときのレビュー

決める必要があったのは、原則集をこの公開リポジトリでどう持つか、レビューをいつ誰が行うか、関係する原則をどう絞るかの3点である。
現時点の件数は、`spec` 11件、`plan` 5件、`advice` 24件。

## 決定

1. 原則集の正本は `sakurai-transcripts` に置く。このリポジトリには、書き出しコマンドで生成したコピーをコミットする。
   コピーには `status: confirmed` の原則だけを入れ、`basis`（動画内容の要約）などの欄を落とす。
   正本とのずれは、書き出しコマンドの `--check` で見つける
2. レビューは、仕様書・ADR・計画を含む `git commit` の直前に、PreToolUse のフックで1回だけ止めて促す。
   「1回だけ」の単位は、セッションとファイルの絶対パスの組にする
3. 成果物を原則と照らすのは、成果物と原則だけを読む独立したサブエージェント `principle-reviewer` とする。
   問いはユーザーに向け、直すかどうかはユーザーが決める
4. 関係する原則は、テーマ索引ではなく原則の `checkpoints` 欄で絞る。テーマは助言で使い分けを示すときに使う
5. 助言はスキル `work-principles` の description で自動発火させる。1段目の仕様が2段目へ申し送った読み替え
   （製品・市場寄りの4件、決める人を前提にした原則）は、このスキルに書き、レビュワーも読む

詳細は `docs/superpowers/specs/2026-10-08-work-principles-design.md` にある。

## 検討した代替案

**スキルとフックが、実行時に非公開リポジトリの原則集を直接読む**

採らなかった。正本が1つで済むが、別のPCでは非公開リポジトリもクローンしないと動かない。
このリポジトリは、クローンしてセットアップすれば動くことを前提にしている（ADR 0024 の背景と同じ）。

**書き出すが、git管理しない生成物にする**

採らなかった。公開リポジトリに原則が載らない利点はあるが、別のPCでは書き出しのために結局非公開リポジトリが要る。
コピーをコミットすれば、公開する内容がレビューできる差分として残る。書き出しの工程が、非公開から公開へ移す関所を兼ねる。

**コピーに `basis` を含める**

採らなかった。`basis` は「話し手がこう述べている」という形で書いた要約である。元は自動字幕で、1段目の確認で動画と照らし合わせたのは原則の主旨だけだった。
照合していない要約を実在の人の発言として公開すると、発言を取り違えて広める恐れがある。レビューは `basis` を使わず、助言の根拠は出典URLで辿れる。
照合してから足すことは backlog に回した。

**書き込みのたびにレビューする**

採らなかった。書きかけの版に何度も問いが出る。ADR 0024 が書き込みのたびのリンターを退けたのと同じ理由である。

**頼んだときだけレビューする**

採らなかった。頼み忘れると素通りし、守られなかったことが跡に残らない。

**PR作成時にレビューする**（ADR 0025 が日本語レビューで採った時点）

採らなかった。仕様書はbrainstormingの中でコミットされ、その直後にユーザーが読む。PR作成は実装の後なので、仕様書を読む前のレビューに間に合わない。
ADR 0025 が挙げたコミットの見分けの問題のうち、リポジトリの取り違えは、記録に絶対パスを使うことで避ける。
包んだ形の取りこぼしは、guard フックの判定を再利用し、同じ範囲で残ることを受け入れる。

**内容のハッシュを「1回だけ」の単位にする**

採らなかった。問いを受けて直すたびに再レビューになり、直してもまた止まる繰り返しになる。

**成果物を書いたメインのエージェントが、原則と照らす**

採らなかった。渡す問いは十数件と小さいので、コンテキストの負担は決め手ではない。
決め手は独立性で、書いた直後のエージェントは、書いたときの前提を共有しているので、その前提の誤りに気づきにくい。
代わりに、会話で決着済みの点をレビュワーが改めて問う誤検知が出る。レビュワーには「会話で決着済みなら、成果物に経緯を足すだけで済む」と添えさせ、
誤検知を「経緯が成果物に書かれていない」という指摘として扱う。

**テーマ索引で、節目に関係する原則を絞る**（2段目に入る前の案）

採らなかった。テーマは共通する価値観のまとまりで、節目とは対応していない。
`checkpoints` 欄は、1段目でこの用途のために作った欄である。

## 結果

- 仕様書・ADR・計画をコミットするたびに、セッションとファイルごとに1回、サブエージェントが動く。時間とトークンが増える
- コミットしない成果物はレビューされない
- 正本を更新したら、書き出してこのリポジトリでコミットし直す手間がかかる。忘れるとコピーが古いまま残る。
  `--check` は非公開リポジトリ側でしか実行できない
- レビューは強制ではない。メインのエージェントが促しに従わなくても、2回目のコミットは通る。そのときは画面に表示する
- Codexでは動かない
