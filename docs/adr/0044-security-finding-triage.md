# セキュリティレビューの指摘を、レビュワーの重さではなく2つの条件で仕分ける

## 背景

レビューの指摘を、大きさを判断しないまま直し続けると終わらない。これを止めたい。

2026-10-29〜30の secret 読み取りガード（ADR 0043）の作業では、コミットごとの自動LLMセキュリティレビューが、
コミットのたびに新しい High を出した。AIは「High は直す」という自分のルールで十回ほど追いかけ、作業が終わらなくなった。

振り返ると、次のことが分かった。

- 序盤の指摘は本物で、早く見つかったことが役立った（読み口の伏せ漏れ、`$HOME` の展開など）
- 中盤以降の指摘は、ほとんどが設計で守らないと決めた「意図して回り込む形」だった。AIの修正そのものが次の指摘を生むこともあった
- いちばん重い穴（改行区切りのコマンドのすり抜け）を見つけたのは、ブランチ全体を見たレビューだった
- 指摘の大きさを判断した人が実質いなかった。AIはレビュワーの High ラベルで決め、利用者は High なら重要だろうと受け取っていた

## 決定

- コミットごとの自動レビューは続ける。修正が新しく開けた穴も、早く見つけるため
- 指摘は、レビュワーの重さではなく、次の2条件で仕分ける。両方を満たす「大きい問題」だけをその場で直し、それ以外は backlog に積む
  1. 普段の作業で起きる形である
  2. 起きたら取り返しがつかない（secret の出力、データの消失、回避できない停止）
- 条件1の判定に迷ったら、大きい側に倒してその場で直し、表に「迷った」と書き添える
- 報告では、大きいと判定した指摘があるときだけ、その理由を表で示す。無いときは「見送り N 件（backlog に積んだ）」の1行にする。利用者が判定を覆せる
- backlog に積んだ小さい指摘は、利用者が定期的に（目安: 月に1回）棚卸しして、直すか捨てるかを決める
- 完了の基準は、大きい問題が無いこと。小さい問題は残してよい

基準は `rules/security-review-policy.md` の「指摘の仕分け」節に置く。

決めた人: 2条件と運用は、AIがたたき台を出し、利用者が2026-10-30に承認した。完了の基準、迷ったときの倒し方、棚卸しの契機は利用者が決めた。

過去の指摘への当てはめ（2026-10-30にAIが確かめた）: 改行区切りのコマンドのすり抜け（`cd /tmp` の次の行で secret のファイルを `cat` する形）は、
AIがふだん書く形で、secret が出力されるので「大きい問題」に入る。`${x:- #}` の中の `#` や `sudo -u ls` のような形は、
わざと組まないと出ないので条件1で落ちる。この区分は、前回の作業で直すべきだった指摘と、追いかけて終わらなかった指摘の区分と一致する。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| PR の前に1回だけレビューする | 修正が新しく開けた穴を見逃す。利用者は、直した結果また新しい問題が出る状況を心配していた |
| レビュワーの High をすべて直す | 2026-10-30に終わらなくなった。レビュワーは脅威モデルを知らず、意図した回り込みも High にする |
| 2回続けて範囲外の指摘しか出なければ止める | 回数で止めると、大きい問題が後から出たときに見逃す。条件で仕分ければ、回数を数える必要がない |
| 判定を別のレビュワーに再確認させる | 再確認のレビューがまた指摘を生み、レビューの連鎖になる。利用者が表で覆す形の方が軽い |
| レビュワーへ脅威モデルを渡す設定（`claude-security-guidance.md`）をユーザー全体に置く | 意図した攻撃を守るべきリポジトリでも感度が下がる。プロジェクトごとに置くかは backlog で決める |

## 結果

- 仕分けの判定はAIが行うので、判定がずれる余地が残る。表で見せて利用者が覆す形で補う
- 1の「普段の作業で起きる形か」は判断を含む。迷ったら大きい側に倒すので、直す量は増えうる
- backlog に積んだ指摘は棚卸しまで残る。棚卸しを忘れると、小さい問題が溜まり続ける
