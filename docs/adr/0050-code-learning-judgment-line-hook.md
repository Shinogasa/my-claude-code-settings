# コード学習の判定を、開示の前に一行で残させ、Stopフックで有無を確かめる

## 背景

2026-11-12、重点学習中と宣言した言語（Go）の作業で、コード学習が一度も発火しなかった。
ユーザーに「学習モードスキップされてる？」と聞かれるまで、AIは自分で見つけたテストの穴
（登録済みの値と初期値が同じなので、引き継ぎの1行を消してもテストが通る）を、答えと理由と
検証手順まで含めて説明していた。

会話記録（user・assistant本文・tool_use、約1,050行）を時系列に並べて、仮説を確かめた。
thinkingは署名だけが残っていて、中身は読めない。

| 仮説 | 判定 | 記録で分かったこと |
|---|---|---|
| 説明の途中で穴に気づいた | 反証寄り | 候補を意識した跡（store の status と skill の行数の確認）は、ユーザーが「詳しく」と頼むより前にある。頼まれていない応答で、答えの材料を先に書いていた |
| skillを読んだのに判定していない | 確定 | skillの全文を読み、operation の書き方まで調べてから、`AskUserQuestion` を一度も呼ばずに答えを書いた |
| 「詳しく」を開示の許可と受け取った | 判定不能 | 意図は記録に無い。開示が頼まれる前から始まっていたので、この仮説が無くても説明できる |
| 別のskillに注意が移った | 形を変えて確定 | Goのコードを読んだ約20時間の調査・説明では、学習への言及が0件。ruleの発火点が「実装の肝心な部分を確定する前」と読めるので、調査と説明が対象外になっていた |
| worktreeで書き込みを拒否された | 確定 | 拒否したのはClaude Code本体（2.1.322のバイナリに文言がある）。このリポジトリのガードではない |

付随して、学習storeの `observed_at` を手書きした結果、実際より15分先の時刻が保存されていた。
このADRを書いたセッションでも、同じ手書きで8分先の時刻を保存している（`date` で確かめた直後だった）。

`tasks/backlog.md` の「コード学習の候補が拾われていない」は、検出側を直すかどうかを決めること、としていた。
今回の事例は、検出の失敗というより、**検出した後に問いへ変えなかった**失敗だった。

## 決定

1. **判定の場面を広げる。** `rules/code-learning.md` で、実装だけでなく、調査・説明・レビューの応答でも、
   AIが新しく見つけたコードの性質を書き出す前に、それが候補かどうかを判定させる。
   イベントを始める前の「詳しく」「説明して」は、開示の許可ではないと明記する。
   skillを読んだこと、statusを確かめたことは、判定の代わりにならないと明記する
2. **判定を一行で残させる。** 重点学習中の領域のコードを扱ったターンでは、所見を書き出す前に
   `コード学習: <能力と対象> → <状態>（<根拠>）` を書く。状態は `出題` `継続中` `見送り` `候補なし` `OFF` の5つ
3. **Claude Codeでは、Stopフックで一行の有無を確かめる。** `hooks/code-learning-check.py` は、
   CLAUDE.md の「重点学習中:」から言語を読み、そのコードをツールで扱ったか、本文で引用したターンで、
   一行が無ければ一度だけ差し戻す。対応表に無い言語や読めない会話記録は、黙って通さずに知らせる
4. **storeの時刻をCLIに作らせる。** `observed_at` を省略すると保存した時点のUTC時刻が入り、
   5分を超えて先の値は拒否する。worktreeに隔離されたsessionでは、入力をファイルに書き、
   `record --input` を単独のコマンドで実行する手順を記録契約に書く

ユーザーは仕組みを、文面だけ、文面＋開始時の注入、文面＋Stopフックの3案から選んだ（設計Predict）。

## 検討した代替案

### A. 文面だけで担保する

保守の費用が無く、ノイズも無い。しかし、今回の事故はskillの全文を読んだ直後に起きている。
文面を読んだことが判定の代わりになった事例に、文面を足すだけで対処することになる。
守られなかったときに、誰も気づけない（`rules/proving-absence.md` の「形式で強制する」考え方とも合わない）。

### B. 文面＋開始時の注入フック（UserPromptSubmit / SessionStart）

ノイズは少ない。しかし、注意を一行入れるだけで、守られたかを確かめない。
今回の事故は注意が足りなかったのではなく、判定を飛ばしたまま答えを書いたことにある。これでは捕まえられない。

### C. フックで判定の中身まで確かめる

一行の有無だけでは、中身の無い「候補なし」で通ってしまう。しかし、能力が候補かどうかは
文脈の判断で、正規表現でもLLMでも、フックの中で決定的に確かめる方法が無い。
LLMに判定させると、AIが自分の判定を採点する閉ループになる（ADR 0012の4で避けたもの）。
中身は、出題の記録（operation）と、ユーザーの「スキップされてる？」のような観測で確かめる。

### D. 判定を応答の冒頭に固定する

一行の位置が決まり、確かめやすい。しかし、応答の冒頭はまだコードを読む前のことが多い
（事故の記録でも、最初の本文は「突き合わせるね」だった）。読む前の判定は形だけになる。
位置は「所見を書き出す前」とし、フックはターン内のどこかにあればよいとする。

## 結果

良くなること:

- 事故の記録の前半で再生すると、11-11の最初の調査のターン、04:00のターン（答えの材料を書いた応答）、
  04:05のターン（答えを書いた応答）のどれでも差し戻す。修正前は04:05のターンが素通りした
  （ツールではGoのファイルに触れず、記憶から説明していた）。本文での引用も対象にして直した
- `observed_at` を手書きできなくなり、未来の時刻が保存されなくなる

諦めること・既知のリスク:

- **ノイズが大きい。** 過去のGoのプロジェクトのセッション30件・548ターンで数えると、231ターン（42%）で一行が要る。
  一行を書く手間が、毎回かかる
- **形だけの手順になりうる。** フックが見るのは一行の有無だけで、中身の無い「候補なし」でも通る
- **Stopは事後に走る。** そのターンの本文は表示された後なので、開示そのものは防げない。
  防ぐのは文面（書く前に判定する）の役目で、フックは判定漏れを次のターンまでに直させる役目
- Codex CLIでは、文面だけで守る。Codexにも `Stop` はあるが、会話記録の形式が違うので、このフックは使えない
- 「重点学習中:」の書式や言語の対応表が変わると、フックは黙って何もしなくなる。対応表に無い言語は知らせるが、
  宣言の行そのものが見つからない場合は「宣言なし」と区別できない
- 効果（判定が増え、出題が増えるか）は未測定。operationの `fired` と `cap_reached`、それにユーザーからの
  「スキップされてる？」の有無で、次の見直しまでに測る

## 根拠

- 事故の会話記録（Claude Codeのsession記録。公開しない）。時系列の抜き出しと判定はタスク用ファイルに残した
- `rules/code-learning.md`、`skills/code-learning/SKILL.md`、`rules/learning-mode.md`
- [ADR 0012](0012-code-learning-mode.md)（自己採点の閉ループを避ける）、[ADR 0021](0021-learning-mode-rule-skill-split.md)（判定を常時ruleに残す）、
  [ADR 0027](0027-code-learning-focus-area-cap.md)（重点学習領域の宣言と、検出不足が未解決だったこと）
- `hooks/skill-read-check.py`（「読んだか」しか確かめられないフックの前例）
