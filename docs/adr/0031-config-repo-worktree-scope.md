# 設定リポジトリでworktreeを使ってよい範囲を、動作中の設定に効かない作業へ広げる

## 背景

解く問題: 並列で動いているセッションが読む規約を入れ替えずに（ユーザーが承知のうえで進める場合を除く）、動作中の設定に効かない作業（テスト・ADR・backlog・仕様書）をworktreeで進められるようにする。

`rules/parallel-worktree.md` は、このリポジトリを丸ごとworktreeの対象外にしていた（2026-08-12の設計書の項目7）。
理由は2つあった。1つは、`~/.claude/` などのリンクが本体の作業ツリーを指すので、worktreeで編集しても動作中のエージェントに反映されないこと。
もう1つは、worktreeで `setup.sh` を実行するとリンク先が移り、worktreeを消すとリンクが切れることだった。

どちらも、動作中の設定に効くパスの編集と、`setup.sh` の実行に限った問題である。テスト・ADR・backlogの作業には当たらない。
丸ごと対象外にした結果、すべての作業を、本体でブランチを切り替えて進めることになった。
本体のブランチが動くと、並列で動いているセッションが読む規約が入れ替わる（2026-08-13に、規約が25コミット分巻き戻った状態で作業が進んだ）。
2026-10-09には、PR #68の作業は実際には一時ディレクトリのworktreeで進んでおり、規約と実態がずれていた。

## 決定

2026-10-09、ユーザーが会話の中で決めた。材料は、2026-08-12の設計書の項目5〜7、backlogの規約巻き戻りの記録、同じ日に観測したworktreeのコストである。
ユーザーは、現状維持・対象外を狭める・常にworktreeの3案から「対象外を狭める」を選んだ。次に判定方法（パスで判定し、作業前に確認する）を選び、最後に強制の範囲（規約と `setup.sh`・pre-commitだけ）を選んだ。

- `setup.sh` がsymlinkを張る元のパスを「本体で作業するパス」とし、それ以外の作業はworktreeで行ってよい。一覧の正本は `setup.sh` のリンク定義とする
- どちらで作業するかは、触る予定のパスから判定し、作業前にユーザーへ確認する。途中で変わったら確認し直す
- 本体でブランチを切るのは、並列セッションがいないときだけにする。いれば、待つ・worktreeに回す・構わず進めるのどれにするかをユーザーに聞く。終わったら本体を `main` に戻す
- worktreeは `.claude/worktrees/` に作る
- `setup.sh` は、worktreeで実行されたら何も変更せずに止まる
- `setup.sh` を実行して初めて効くファイルを変えたPRをマージしたら、エージェントが本体で `setup.sh` を実行するよう提案する。実行は `~/.claude/` などを書き換えるので、ユーザーの了承を得てから行う。実行忘れを検出する仕組みは無いので、マージの手順に組み込む（2026-10-13に追加）
- `.githooks/pre-commit` は、worktreeでは本体の作業ツリーにある `patterns-local.txt` を読む

設計の詳細は `docs/superpowers/specs/2026-10-09-config-repo-worktree-scope-design.md`。

## 検討した代替案

### 現状維持（丸ごと対象外）

並列で作業するたびに本体のブランチが動き、背景に書いた規約の巻き戻りが起き続ける。規約と実態のずれも解消しない。

### 常にworktreeで作業し、本体は `main` に固定する

本体のブランチが動かなくなるので、巻き戻りは起きない。採らなかったのは、フックや規約の変更を、マージ前に実機で確かめられなくなるため。
このリポジトリの変更の多くは、動作中のエージェントで挙動を確かめてから完了にしている。

### worktreeの中で本体用のパスを編集したら警告するフック

すべてのリポジトリで、Edit・Writeのたびに判定のコストがかかる。作業前の確認と役割が重なる。分類を誤っても、反映が遅れるだけで壊れはしない。

### 並列セッション検出フックの除外を外し、このリポジトリでも通知する

この案は、`tasks/backlog.md` に着手条件付きで積んである別の課題で、条件をまだ満たしていない。この変更と独立に判断できる。

### 一覧のパスを触らない作業では、作業前の確認を省く（保留）

確認の手間は減るが、触る予定のパスの見積もりを誤ったときに誰も気づかない。確認は作業を始めるときの1回だけなので、今は負担が小さいと判断した。運用して負担に感じたら検討し直す。

### 「影響がある作業」を作業者の判断だけで決める

基準が人によって揺れる。パスで判定すると、すぐに反映しなくてよい規約の修正まで本体で行うことになるが、事前確認でユーザーが覆せる。

## 結果

- 動作中の設定に効かない作業は、本体のブランチを動かさずに並列で進められる
- 本体のブランチが動くのは、動作中の設定に効く作業で、並列セッションがいないときだけになる
- 諦めたこと: worktreeで始めた作業が途中で実機確認を要するようになると、pushして本体へ移る手間がかかる
- 諦めたこと: worktreeのセッションは、本体の永続メモリを読めない。2026-10-13にユーザーが受け入れると決めた。作業の計画は本体のセッションで立て、worktreeでは実装を進める運用になる見込みである。計画に要る文脈は本体側で読める。worktree用のメモリを本体へリンクする案と、ユーザーについてのメモリをグローバルへ寄せる案は採らなかった
- 既知のリスク: worktreeでの作業が全体として速くなるかは実測していない。worktreeを1つ用意するコストは測った（作成、サブモジュールの初期化、`patterns-local.txt` のコピーで3回とも22〜25秒、2026-10-09）。同じ日に、worktreeでのコスト（`patterns-local.txt` が無くコミットが止まる、サブモジュールを含むので削除に `--force` が要る、永続メモリが空から始まる）を観測している。前の2つはこの変更で軽くなるが、メモリの分断は残る

### 見直す条件

運用開始から1か月（2026-11-09ごろ）に、worktreeで始めた作業のうち本体へ移ったものを数える。半分を超えていたら、パスでの判定か一覧の範囲を見直す。数えるのはPRの振り返りで足りる程度にとどめる。

決定の材料は、どれもworktreeを広げる側を支えるもので、反対の立場からの指摘は集めていない（決定の後の原則レビューを除く）。
この見直しを、方針が誤っていたかを確かめる機会として使う。本体へ移した作業の数に加えて、worktreeにしたために起きた不便
（メモリが読めずに困った場面など）も拾う（2026-10-13、原則レビューの問いP20aを受けて追加）。

### 見直しの結果（2026-11-09）

**方針は維持する。** worktreeで始めた作業10件のうち、本体へ移ったのは1件だった。
ユーザーが下の集計と想定外の点を見て、会話の中で維持を決めた。

数え方: 2026-10-09〜11-09の対話セッションの会話記録（`~/.claude/projects/` の本体とworktreeのディレクトリ）から、
cwdがworktreeになった記録を抜き出した。そのうえで、作業の場所が本体へ移った跡があるかを、前後のやり取りで確かめた。
記録のブランチ名が本体側に出るだけのもの（マージ後の片付け、本体から `git -C` でworktreeを操作した場合）は数えていない。
statusline の表示を試すために作ったworktree 2つは、作業ではないので除いた。
クラウドのセッションと、本体のディレクトリ以外から起動したセッションは数えていない。

- 本体へ移った1件: `rules/completion-anchor.md` の追加（PR #102）。代表検証のために、本体でブランチをチェックアウトする必要があった
- 想定外だったこと: 「本体で作業するパス」をworktreeで直した作業が3件あった（`rules/`、`commands/`、`bin/`）。
  うち2件は、本体で別のセッションが動いていたためである。確認はマージ後に本体を pull するか、本体でチェックアウトして済ませた。
  おかしくなったものは無かった。パスでの判定は、実際には「本体が空いていれば本体で」くらいの強さで使われていた
- 不便だったこと:
  - worktreeに入ったセッションからは、本体のファイルの編集と本体での `git switch` を Claude Code が拒否する。
    2件とも、ユーザーが端末でコマンドを打って回避した
  - `bin/detect-parallel-sessions` をworktreeから実行し、本体のセッションが出ない結果を「誰もいない」と読み違えた（スクリプトは仕様どおり）
  - rtk が書き換えた `git` をworktreeの分離チェックが拒否した（ラッパーで回避済み）
- メモリが読めずに困った場面は、会話記録のキーワード検索（「永続メモリ」「メモリが読」など）では見つからなかった。
  検索は言い回しに依存するので、ユーザーにも確かめた。困った覚えは無いとのことだった

決定の文面と運用の実態のずれは、ADRの決定を変えずに `rules/parallel-worktree.md` を直して解消した（ユーザーが決めた）。

- 並列セッションがいて本体のパスの作業をworktreeに回したときの確かめ方（マージ前に本体でチェックアウトするか、マージ後に pull して確かめるか）を、作業前の確認で一緒に決めることにした
- worktreeに入ったセッションが本体を操作する必要が出たときの手順を書いた

`bin/detect-parallel-sessions` の読み違えは運用の誤りで、決定の文面とのずれではないので、`tasks/backlog.md` で判断待ちにした。

## 根拠

- `docs/superpowers/specs/2026-08-12-parallel-session-worktree-isolation-design.md` の項目5〜7
- `tasks/backlog.md` の「動作中のエージェントの規約が背後で入れ替わる」
- `git help rev-parse`（Git 2.55.0）の `--git-common-dir` と `--path-format`。手元で、本体では `--git-dir` と `--git-common-dir` が同じ `.git` を返し、worktreeでは `--git-dir` だけが `.git/worktrees/<名前>` を返すことを確かめた（2026-10-09）
