# setup.sh から setup-state.py を対象ごとではなく一括で呼ぶ

## 背景

`setup.sh` は、配布対象（`--all` で39件）ごとに `python3` を起動して `bin/setup-state.py` の関数を呼んでいた。
1回の実行で、同じ種類の起動が対象の数だけ繰り返されていた。

- preflight の分類（`classify_target`）。preflight は2回走るので、2回×39件。生成物はさらに checksum の読み出しで1回ずつ増える
- リンク配置の検査（`validate_link_target_topology`）。2回×37件
- snapshot の取得（`snapshot_targets`）と再検査（`validate_target_snapshots`）。それぞれ39件
- リンクの適用（`link_target`）。37件。各件で snapshot を再検査し、既にリンクがあれば分類も呼ぶ

全テスト830件で約24分かかり、遅い上位40件のうち39件が `tests/test_setup_cli.py` と
`tests/test_setup_preflight.py` だった。どちらも1件ごとに `setup.sh` を実行する。

### 測定（macOS、2026-10-09）

テストと同じ条件で測った。スタブの claude/codex/git をPATHに置き、偽のHOMEに `.claude` と `.codex` を作った。
そのうえで `setup.sh --all` を `bash -x`、`PS4='+${EPOCHREALTIME} ${LINENO}: '` でトレースし、
行ごとの経過時間をコマンド別に集計した。

| 指標 | 値 |
|---|---|
| `setup-state.py` を使う `python3` の起動 | 200回、7.0秒 |
| それ以外の `python3` の起動（主にリンク配置の検査） | 100回、3.4秒 |
| `dirname` | 410回、0.7秒 |
| 実行時間（トレースなし、5回の中央値） | 10.79秒 |

1回の起動の内訳も測った（30回の中央値。別のテストが並行して動いている状態での値）。

| 起動するもの | 時間 |
|---|---|
| `python3 -c pass` | 18.7ミリ秒 |
| `python3 -S -c pass` | 12.6ミリ秒 |
| `setup-state.py snapshot-paths` に1件を渡す | 42.4ミリ秒 |
| `setup-state.py snapshot-paths` に39件を渡す | 41.6ミリ秒 |

時間のほとんどは、インタプリタの起動と標準ライブラリのimportにかかっている。処理する件数を増やしても、時間はほぼ変わらない。

## 決定

1. **`setup-state.py` に一括処理のサブコマンドを4つ足す。** `classify-targets`、`snapshot-paths`、
   `check-link-topology`、`apply-links` で、どれも全対象を引数で受け取り、1回の起動で処理する。
   判定とメッセージは、従来の関数と heredoc のものをそのまま使う
2. **`apply-links` は、対象ごとに「snapshot 再検査 → `mkdir -p` → 既存確認 → `ln -s`」の順を保つ。**
   検査からリンクまでの間隔は、従来と同じく1件分に留める。`mkdir` と `ln` は Python の関数を使わず、
   従来どおりPATHから外部コマンドとして呼ぶ。最初の失敗で止まり、後の対象には触れない
3. **引数で渡し、結果は1件1行で受け取る。** パスにどの文字が入っていても、引数なら区切りが崩れない。
   出力は分類名か compact JSON だけで、改行はエスケープされる。setup.sh は受け取った行数を対象数と照らし、
   合わなければ失敗させる（検査できなかった対象を「問題なし」に畳まない）
4. **移行予定の skills 親が無いときは、`is_pending_skill_child` が `dirname` を起動しない。**
   通常の実行では、移行予定の親は空である
5. **件数の少ない呼び出しは1件ずつのまま残す。** 競合の退避（`backup_conflicts`）、旧形式の skills 親の
   判定と移行、生成物の確定（`commit_claude_files`）が対象

## 検討した代替案

### A. setup.sh 全体を Python で書き直す

起動は1回になる。しかし、1000行のシェルを書き直すことになり、変更の大きさに見合わない。
テストは、PATHに置いたスタブの `git`・`ln`・`mkdir` で、競合の割り込みを再現している。
書き直すと、これらの差し込み口をすべて作り直すことになる。出力メッセージ・終了コード・失敗の集約を
すべて同じに保つ確認の費用も大きい。一括処理だけで、`setup-state.py` の起動は200回から10回に減った。
残りの効果は小さいので採らない。

### B. 呼び出しはそのままで、Python の起動を速くする

`-S` で site の読み込みを省く、`setup-state.py` のimportを遅延させる、といった方法がある。
上の測定では、何もしないインタプリタの起動だけで18.7ミリ秒（`-S` でも12.6ミリ秒）かかった。
importを削っても、1回あたり約20ミリ秒の下限が残る。200回なら約2.5〜4秒で、起動回数に比例するという構造も変わらない。
`-S` は、利用者の環境の site 設定にも依存する。効果が回数に比例して残るので採らない。

### C. 常駐する Python プロセスに、bash から要求を送る

`coproc` などで1つのプロセスを使い回せば、1件ずつの順序を完全に保ったまま起動を1回にできる。
しかし、macOS の `/bin/bash` 3.2 には `coproc` が無い。要求と応答のプロトコル、エラー時の後始末も新たに要る。
決定2の `apply-links` で順序は保てるので、複雑さに見合わない。

### D. リンクの前の snapshot 再検査を、ループの前に1回だけまとめて行う

起動は減るが、検査から `ln -s` までの間隔が、1件分からループ全体に広がる。
既存の正しいリンクが、ループの途中で同じ先を指す別のリンクへ差し替えられても、検出できなくなる。
外から見える安全性が変わるので採らない。決定2のとおり、検査とリンクを同じプロセスで1件ずつ交互に行う。

### E. `apply-links` の中で `os.makedirs` と `os.symlink` を使う

外部コマンドを起動しない分だけ速い。しかし、既存のテストはPATHに置いた偽の `ln` と `mkdir` で
割り込みを再現している（`test_late_settings_edit_is_not_overwritten`、`test_late_symlink_is_not_deleted`）。
Python の関数に替えると、これらのテストが割り込みを再現できなくなる。失敗したときの `ln` と `mkdir` の出力も変わる。
テストの変更はこの作業の範囲外なので採らない。

## 結果

同じ条件で測り直した（macOS、2026-10-09）。

| 指標 | 変更前 | 変更後 |
|---|---|---|
| `setup-state.py` を使う `python3` の起動 | 200回 | 10回 |
| `python3` の起動の合計 | 300回 | 36回 |
| `dirname` | 410回 | 143回 |
| 実行時間（トレースあり、1回） | 13.76秒 | 4.94秒 |
| 実行時間（トレースなし、5回の中央値） | 10.79秒 | 2.09秒 |

外から見た挙動は変えていない。作るリンク、出力メッセージ、終了コード、退避、失敗の集約が対象で、
`tests/test_setup_cli.py`、`tests/test_setup_preflight.py`、新しい `tests/test_setup_state_batch.py` の
108件がすべて通る。

諦めたことと既知のリスク:

- snapshot の取得と再検査は、全対象をまとめて取ってから比べる。最初の不一致で止まる点は変わらない。
  ただし、後の対象のsnapshotは、従来より数ミリ秒早く取られる
- 一括処理の中で予期しない例外が起きたときは、従来と同じく traceback を出して非0で終わる。
  終わる位置は「その対象の処理中」から「一括処理の途中」に変わるが、setup.sh の終了コードは変わらない
- 残っている `python3` の起動（26回）は、`setup-state.py` とは関係が無い。内訳は、Claude プラグインの確認
  （一覧の検証と、有効な8件それぞれの確認で約10回）、skills manifest の読み込み（8回）、
  入力の検証、Codex 設定のスクリプトなどである。この判断の範囲には含めていない

## 根拠

- `setup.sh`、`bin/setup-state.py`（変更前は main の 3013e48）
- 上の測定は、テストの `copy_repository` と `make_stub_commands` を使い、一時ディレクトリの偽HOMEで行った
