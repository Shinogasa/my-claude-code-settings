# 判断点を層で選別し、実装レベルの経験は定石欄で供給する

## 背景

ADR 0001 で予測フェーズを再認から生成へ変えた後、機構は安定して回っていた。
一方で「記録の内容と出題の有用性が期待に届かない」という不満が出た。
`learning/entries/` 76件を測定した結果は次のとおり。

| 観測 | 値 |
|---|---|
| 総エントリ数 | 76 |
| 題材が機構を載せている設定リポジトリ自身のメタ作業 | 約半数（2026-08-19 は11件中10件） |
| `## 概念` を持つエントリ | 23件（D6 導入の 2026-08-14 以降28件中） |
| エントリ間の相互リンク（wiki 記法・相対 `.md` リンク） | 実質0件 |
| 「過去の判断原則との接続」節（散文のみ・たどれない） | 23件 |
| `### 判断点` 見出しの一致 | 76件中31件 |
| `result: hit` | 63/76 = 83% |

診断は2つに分かれた。

**(1) 発火条件が層を制約していない。** 現行の3条件（不可逆・競合・一般化できる）は
判断の**抽象度**について何も言っていない。「列挙型の switch で default に何を返すか」
「フィルタ結果の slice をどの容量で確保するか」はいずれも3条件を全て満たすため、
正当に拾える。結果として判断点がコードの内側に張り付き、
境界の位置・可用性・移行手順・観測点といった外側の判断が構造的に拾われない。

**(2) 抽出された概念名の抽象度は既に十分だった。**
`fail-safe defaults` / `failure domain` / `policy-mechanism separation` /
`plan/apply separation` / `risk-based testing` / `desired-state reconciliation` など、
語彙としては上位レベルのものが出ている。つまり **★ Delta の出力側ではなく、
予測フェーズの入力側（何を判断点として選ぶか）が偏りの原因**だった。

加えて、対話ツールの選択肢が回答後に画面から消えるため、
理由フェーズで「何と何を比べたか」が見えなくなるという運用上の欠陥が報告された。

## 決定

### D1. 発火条件に「層」を4つ目のゲートとして追加する

同じ作業から取れる判断点を層（L1 実装 / L2 モジュール設計 / L3 システム設計 /
L4 運用・進化）で並べ、**最も外側の層から拾う**。
**L2 以上の判断点が実在するなら L1 では発火させない。**

層を判定できないときは L1 とみなす（発火させない側へ倒す）。
「一応 L2 かもしれない」で拾い始めた時点でゲートは無効化するため、
曖昧な回は落とす方向に固定する。

### D2. ★ Delta に `定石` 欄を新設し、L1 の技術的経験はそこで供給する

D1 は L1 を予測の**題材**から外すが、L1 の技術的経験そのものは捨てない。
`概念`（判断の一般名）とは別に、その判断に付随する**コードレベルの書き方**を
1つ添える。`概念` と合わせて上限2つ。

「こう書く」＋「そうしないと何が起きるか」をセットで書く。
コードを伴わない判断（運用手順、設定配置、ドキュメント構成）では節ごと省く。

**判断は上の層で取り、手を動かす経験は下の層で渡す。**

### D3. 理由フェーズで選択肢を必ず再掲する

選んだ結論と、他の選択肢のラベル・`description` を箇条書きで再掲する。
補足・比較・評価は足さない。

再掲はヒントに当たらない。既に提示済みの情報であり、`description` には
「何が起きるか」しか書かない規約（ADR 0001 D1）のため判断基準を含まない。

比較対象が見えない状態で書かれた理由は、選んだ案の利点だけを述べたものになりやすい。
これは **トレードオフ軸が構造的に埋まらない**経路であり、
実際に同軸の欠落は10件と3軸中で最少だが、ADR 0001 の測定で
「得意だからではなく検出できていないだけ」と判明した前例がある。

### D4. 評価パートと学習領域の重複を解消する

`評価` と `学習領域` が、軸名と「今回何が抜けたか」を二重に述べていた。
実出力の例:

```
評価: 前提の検証軸 — （何が抜けたかの説明）
学習領域: 前提の検証軸が抜けていた → （同じ説明の再掲） → 次の問い
```

「具体的に何が抜けたか」を**評価パートへ集約**し、`学習領域` は
`次の問い` へ改名して**次回の行動だけ**を書く節に縮約する。

`**次に同種の判断で確認する問い**:` の文字列は変えない。
これは過去エントリから判断原則を引く grep キーであり（ADR 0001 D8）、
2026-08-31 時点で49件が持っている。表記を変えると接続が切れる。

判定を記録する。**却下したものも含めて残すのは、同じ指摘が再度来たときに
再検証しないため。**

### 観察

4件中3件が、条文の読み落としか、ADR 0001 で測定済みの方向の再提案だった。
レビュアーは `rules/learning-mode.md` **単体**を読んでおり、
ADR 0001（測定値と却下案7件）・本 ADR・`rules/persona.md`・`learning/entries/` を読んでいない。

**根拠を渡さずに外部レビューを求めると、却下済みの案が新提案として返ってくる。**
次回以降、外部レビューへ出すときは関連 ADR を同梱する。

## 検討した代替案

### A1. 評価の3軸に上位レベルの軸（可用性・コスト・組織）を足す（却下）

不満の表明が「スタッフエンジニアとして有用な出題になっていない」だったため、
評価軸の抽象度を上げる案を検討した。却下した理由は2つ。

- 現行3軸（トレードオフ / 失敗モード / 前提の検証）は**層に依存しない**。
  L1 の判断にも L4 の判断にも同じように当たるので、軸は原因ではない
- `rules/learning-mode.md` は軸の追加を明示的に禁止している。
  軸が増えると過去エントリとの集計互換が壊れる（ADR 0001 の測定が依存している）

原因は軸ではなく題材だったため、D1 で入力側を直す方を採った。

### A2. 概念ノート層を新設してエントリと相互リンクする（今回は見送り・却下ではない）

参照した外部事例（エバーグリーンノート実践）が採る方式。
原子性（1ノート1概念）・概念指向・密なリンク・MOC ハブ・バックリンク自動生成。
測定した「概念23件が一度も再訪されていない」「相互リンク実質0件」に直接効く。

ADR 0001 A5 でカレンダー駆動の間隔反復を却下した理由は
「エピソードは当時の文脈を再現できず orphan prompt になる」だった。
**概念ノートはこの制約に当たらない**（概念は文脈から剥がされた単位である）ため、
A5 の却下理由はこの案を却下する根拠にならない。

今回見送ったのは順序の判断であり、案そのものの否決ではない。
**未着手の課題**として扱う（登録は下記「未登録の残タスク」を参照）。

### A3. エントリ書式を機械可読に固定し、過去76件を遡って統一する（今回は見送り）

見出しの揺れ（`### 判断点` が76件中31件）と、
`learning/README.md` のテンプレートが `## 概念` を欠いていた仕様ドリフトは実在する。
テンプレート側のドリフトは今回修正したが、**過去エントリの遡及統一は行わない**。

理由は、統一そのものが学習効果を持たない一方で、
本文を触ると ADR 0001 が依存している「移行時に本文を1文字も変更していない」
という保証が失われるため。A2 と同様、未着手の課題として扱う。

### 残タスクの登録先

A2 / A3 / A4 はいずれも否決ではなく順序の判断であり、
`tasks/backlog.md` の「学習モード」節へ**決めること・着手条件つきで登録済み**。

### A4. 実作業の外から題材を持ってくる（保留・次の判断点）

実作業に該当する判断点が無い日でも出題できるようにする案。
本 ADR の範囲外とし、別途決める。

**未解決の論点**: 予測に対する「実際」を何で担保するか。
AI が正解を作ると差分フィードバックの信頼性が落ちるため、
マージ済み OSS PR・公開 postmortem のように**正解が外部に既に存在する題材**に
限定できるかを先に決める必要がある。

## 結果

### 良くなること

- 判断点が L2 以上に寄るため、記録が境界・可用性・移行・観測の語彙で埋まる
- `定石` 欄により、L1 を題材から外しても手を動かすレベルの経験は残る
- 理由フェーズで比較対象が見えるため、トレードオフ軸の欠落を検出できるようになる
- ★ Delta から軸名と「今回何が抜けたか」の二重記述が消え、出力が1ブロック分短くなる

### 諦めること

- **発火回数が減る可能性がある。** L2 以上が無い作業では発火しないため、
  設定値の調整のような回は記録が残らない。これは意図した挙動
- 層の判定はこちら（AI）の裁量に依存する。外形から検査できない

### 既知のリスク

- **層ゲートの効果を測る経路が現時点で無い。** 出題の質を測れる指標は `result` の
  hit 率だけで、これは出題難易度と混ざるため単独では読めない。
  A2 / A3 を入れるまで、この変更が当たったかは判定できない
  （この構図自体をオープンループ制御として記録した →
  `learning/entries/2026-08-21-学習機構の改善で出題側と記録側のどちらから着手するか.md`）
- **`次の問い` の縮約で、軸と行動の対応が読み取りにくくなる可能性がある。**
  評価パートと `次の問い` が離れた位置にあるため、
  「どの軸の欠落から出た問いか」が1行では追えなくなる。
  記録側（`learning/entries/`）は `axis` frontmatter で紐づくため集計には影響しない
- **`定石` は捏造しやすい。** 言語やライブラリのバージョンで振る舞いが変わるものは、
  出す前に一次ドキュメントで確認する規約を置いた（→ `rules/proving-absence.md`）が、
  確認したかどうかは出力から検査できない
