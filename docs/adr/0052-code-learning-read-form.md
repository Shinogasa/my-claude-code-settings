# AIが書いた正しいコードの読解を、コード学習の形式「Read」として切り出す

## 背景

ユーザーは Go を重点的に学んでいる。AIが書いた良い Go コードを、その場で止まって読み解けるようにしたい。
ADR 0012 は、コード学習の形式を Write → Modify → Review → Explain の順に選ぶと決めた。
このうち Explain は「AIが解説する」形式で、前提が足りずに他の形式を始められないときの受け皿だった。
欠陥の無いコードを読む練習には、発火する経路が無かった。

PR #139（Muse との対話で作った案）は、Explain に「読解」という2つ目の発火を足した。
レビューで、この案は次の理由でそのままでは目的を果たせないと分かった（2026-11-16）。

- 記録できない。`learning/code/README.md` は「Explainだけなら能力recordを作らない」「説明・転移回答だけは保存しない」と定めている。
  `bin/learning_store/schema.py` の `MODES["code"]` にも explain は無い。PR が述べた「記録 schema を無変更で再利用できる」は成り立たなかった
- カタログに書いた「問う範囲」（例: mutex を含む struct をコピーしていないか）が見るべき箇所を名指ししていて、出すとヒントになる
- 「パターンが初見なら AI が先に説明してよい」を、AIが推定で発動できる
- 早期 return や命名のような慣例寄りの項目が多い。AIが書く Go のほぼすべてに当たり、発火が多くなりすぎる

## 決定

grilling（2026-11-16〜17）でユーザーが決めた。

1. 読解は、新しい形式 **Read**（記録の mode は `read`）として扱う。Explain は元の定義に戻す
2. 証拠にするのは、本人が出した外れうる予測（「ここを○○に変えると△△が起きる」）と、その変更を使い捨てのコピーで実行した結果との照合だけである。説明だけで終わった回は証拠にしない。実行で確かめられない予測しか立たない箇所は対象にしない。
   「なぜこう書くか」は、予測の後に聞く理由質問（SKILLの「理由を自己説明」）で扱う。Readは「なぜ」の読解を捨てたのではない。「なぜ」は理由質問で聞き、証拠は予測にする、という二段で扱う。
   コピーの作成と実行はAIが行い、支援として記録する。本人が担うのは変える場所の選択と予測で、手間は記録の都合を持ち込んだ側（AI）が負う
3. 最初の依頼は「どこかを一つ変えたら何が起きるかを予測して」だけにする。変える場所を本人が選ぶことも、能力の一部とする。カタログの観点と変更の例は採点用で、本人に見せない
4. ヒントは段数を決めずに出し、本人が答えを求めるまで答えを出さない（既存の引取りの扱いと同じ）。出したヒントは record 本文の「支援と再試行」に書く。schema に新しいキーは足さない
5. AIが先に解説するのは、本人が「分からない」と答えるか、解説を選んだときだけにする
6. 対象はAIがコードを生成した時点で決め、その箇所の意図は以降の応答にも完了報告にも書かない。出題は、テストが通ってコードが落ち着いてからにする。
   伏せた意図は、本人がskipや中断をしたとき、Readを終えたとき、出題しないまま作業を終えるときに開示する。完了報告で理由を示す決まり（`rules/output-formatting.md`）も、学習イベントの対象にした判断は理由を後で示すので、これと揃う。学習者としての価値を先に取るが、AIのコードを判断するための意図はタスクの中で必ず開示する
7. Read は他の形式とは別の枠で数え、pilot の間は1タスク1回までにする。pilot は、mode=read の record が5件たまり、backlog の「Readの回数枠を見直す」で上限を決め直した時点で終わる。同じ箇所・同じ能力に手を動かす形式の候補があれば、そちらを優先する
8. 転移確認では、条件を一つ変えて予測し直し、実行で確かめる

この ADR は、ADR 0012 の決定3（形式の優先順位）を部分的に置き換える。Read は優先順位の列に並ばず、別の契機（AIが正しいコードを書いたこと）で発火する。

## 検討した代替案

| 案 | 採らなかった理由 |
|---|---|
| Explain の拡張（PR #139 の当初案） | Explain だけの回は記録しないと決めている（README・schema）。記録に残らないと成長を追えない。記録できるようにすると、AIが解説しただけの回まで証拠に紛れ込む |
| Review に入れる | Review の定義は「問題が成り立たない理由を示す」も含むので、形の上では入る。ただ、本人が欠陥を探す構えで読むことになり、「なぜこう書くか」を読む練習にならない。記録でも Review と区別できない |
| 本人に「何をしているか・なぜか・変えると何が壊れるか」を説明させ、説明を採点する | 説明の採点はAIの判断に頼るため、自己採点の閉ループ（ADR 0012 の決定4）に近づく。予測なら当たり外れを実行で観測できる |
| ヒントを3段（注目する行 → カタログの問い → AIの解説）に固定する | ユーザーが、本人が答えを求めるまでヒントを出す今のやり方を選んだ。段の区切りは課題ごとに違い、固定しても比べられない |
| 読解に独自の枠を設けて、1タスクに複数回出す | 効き目がまだ測れていない。先に回数を増やすと、作業が中断されるコストだけが先に来る。record が5件たまったら見直す（backlog） |

## 結果

- 良くなること: 正しいコードを読む練習が、記録に残る行動（予測と実行）として成り立つ。カタログが答えを漏らさない
- 諦めること: 実行で確かめられない読解（interface の置き場所、命名、早期 return）は Read の対象にしない。レシーバのうち、値かポインタかで挙動が変わる部分は実行で確かめられるので、カタログに残した。linter の指摘に任せる（backlog）
- リスク: 実際の Go の作業でどれだけ発火するか、ヒントがどれだけ出るかは測っていない。pilot で記録を見る。使い捨てのコピーで実行する手間はAIが負うが、待ち時間で作業の流れが止まりすぎるかもしれない。止まりすぎるなら、backlog の見直しで回数と合わせて扱う

## 根拠

- ADR 0012（コード学習の形式と優先順位）、ADR 0050（判定の一行）
- `learning/code/README.md`、`bin/learning_store/schema.py`
- Go カタログの項目は、次の基準で一次資料から選び直した（2026-11-17）: 公式の一次資料が扱っている、AIが書く Go によく現れる、実行で確かめられる予測が立つ。
  当初の13項目は、Muse 案の15項目から3つ外して1つ足した結果で、数に根拠は無かった。選び直して16項目になった
- 各項目の出典と、何で確かめたか（原文・要約経由・実行）は、カタログの項目ごとに書いた。要約経由のものは原文を確かめていない。
  当初この節に「検証routeは一次資料で確かめた」と書いたが、実際に確かめていたのは5件だけで、言い過ぎだったので直した
- backlog の linter 案の根拠: revive の RULES_DESCRIPTIONS.md（`indent-error-flow`・`receiver-naming` の実在を確かめた）
