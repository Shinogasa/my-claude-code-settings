# 並列セッションの作業ツリー分離設計

## 背景

複数のコーディングエージェントを同一リポジトリで並列に走らせると、同じ作業ツリーを
共有するためブランチが衝突する。片方がブランチを切り替えると、もう片方は
自分の足元が変わったことに気づかないまま作業を続ける。

`git worktree` で分離すれば解決するが、**分離の指示を人が毎回出すのは成立しない**。
並列であることに気づいた時点では既に衝突している。機構側で検出し、判断材料を
自動で供給する必要がある。

## 調査結果（実機検証済み・2026-08-12）

### 1. worktree 経由なら排他は git が保証する

```
$ git worktree add ../wt-x2 feat/x
fatal: 'feat/x' is already used by worktree at '.../wt-x'
```

同一ブランチの二重チェックアウトを git が拒否する。**worktree 経由に統一するだけで
ブランチ単位の排他は成立する**ため、ブランチ衝突を検出する独自機構は不要。

### 2. worktree の作成コストは無視できる

追跡ファイル 105 件・履歴 76MB のリポジトリで **0.049 秒**。オブジェクトはコピーされず
追跡ファイルの展開のみのため、履歴サイズにほぼ依存しない。

### 3. 重いのは追跡外資産の再構築

作成直後の worktree に来なかったもの:

| 欠けたもの | 対処 |
|---|---|
| サブモジュール（ディレクトリが空） | `git submodule update --init` |
| `.env` | 手動コピー |
| gitignore された実行時参照ファイル | 個別に復元 |

一般のアプリケーションリポジトリでは依存パッケージ・仮想環境・ビルドキャッシュが
これに加わる。**「起動できなくなる」の第一の原因はここ**で、再構築すれば解消する。

### 4. worktree は実行環境を分離しない

再構築では解消しない層がある。

- 開発サーバのポートの取り合い
- 同一のローカル DB を指すことによるマイグレーションの相互干渉
- コンテナ名・ボリューム名の衝突

**worktree はファイルシステムの分離であって実行環境の分離ではない。**
この層は worktree の採否と独立に並列作業へ付いてくる制約であり、本設計の対象外。

### 5. グローバル設定は worktree の影響を受けない

`~/.claude/` 配下は絶対パスのシンボリックリンクで本体の作業ツリーを指している。

```
agents@ / CLAUDE.md@ / commands@ / hooks@ / output-styles@ / rules@ → 本体の作業ツリー
```

CWD に依存しないため、worktree に入っても rules・hooks・agents・output-style は
同じものが読まれる。**エージェントの挙動に効く要素はすべてここに集中しており、影響なし。**

### 6. CWD で切り替わるのは会話履歴と永続メモリ

```
~/.claude/projects/<CWD のスラッシュをハイフンに置換した名前>/
  ├── *.jsonl   会話履歴（--resume の対象）
  └── memory/   永続メモリ
```

worktree に入ると CWD が変わるため別の名前空間になり、**永続メモリは空から始まる**。
`ExitWorktree` の仕様にも CWD 依存キャッシュ（system prompt sections, memory files,
plans directory）のクリアが明記されている。

本リポジトリでは `memory/` が未作成のため現時点の実損は無いが、
メモリを使い始めた後は worktree ごとに分断される点に注意が必要。

### 7. 設定リポジトリ自身は worktree の対象にできない

項目5の裏返しとして、`~/.claude/rules` 等が本体の作業ツリーを指す以上、
**worktree 側で rules や hooks を編集しても動作中のエージェントには反映されない。**
「設定を直したのに効かない」という形で現れる。

さらに `setup.sh` を worktree で実行するとリンク先が worktree になり、
その worktree を削除した時点でリンクが全て壊れる。

→ **本リポジトリは worktree 対象外とする。**

### 8. `EnterWorktree` の生成先は gitignore されていない

`.claude/worktrees/` に作成されるが `.gitignore` に無く、`.git/info/exclude` も空。
実測で `?? .claude/` が `git status` に出た。

### 9. 並列セッションの検出はプロセス検査で可能

`pgrep -x claude` と `lsof -a -p <pid> -d cwd` で全セッションの作業ディレクトリが取得できる。
**7 プロセスで 326 ms**。セッション開始フックで回せる速度。

判定キーは `git rev-parse --git-common-dir`。worktree から呼んでも本体と同じ値を返すことを
実測で確認済み（本体・worktree ともに同一パス）。

| 状況 | 判定 |
|---|---|
| common-dir 一致 ＋ CWD 一致 | 衝突中 |
| common-dir 一致 ＋ CWD 相違 | 分離済み |
| common-dir 不一致 / 非 git | 無関係 |

### 10. `EnterWorktree` は指示が無いと使えない

ツール仕様が発動条件を「ユーザーが明示的に worktree と言った時」または
**「CLAUDE.md / memory がそう指示している時」**に限定している。
規約ファイルを置くことは丁寧さではなく、ツールを利用可能にするための必須条件。

## 設計判断: 検出成功時の振る舞い

セッション開始フックからツールは呼べない。できるのはコンテキストへの情報注入まで。

### 採用: 通知型（検出結果を知らせ、分離するかは都度判断）

作業ディレクトリが機構の判断で動かないことを優先する。
誤検出があっても、失われるのは注入されたテキスト1件分のコンテキストのみ。

### 却下 A: 指示注入型（「worktree に入れ」を指示として注入）

忘却は撲滅できるが、worktree が有害なリポジトリ（項目7）を除外リストで管理する必要が生じ、
そこが漏れると設定が反映されない事故を起こす。除外リストは追加を忘れる方向に倒れやすく、
失敗が静か。

### 却下 B: リポジトリ単位のオプトイン（宣言したリポジトリは常に worktree）

判定が消えるため誤検出はゼロになるが、宣言し忘れたリポジトリが完全に無防備になる。
宣言の必要性に気づくのは最初の衝突が起きた後であり、予防にならない。

### 通知型が後発セッションにしか届かない件の手当て

セッション開始時の注入は、後から起動した側にしか届かない。3つに分けて埋める。

| 経路 | 手当て |
|---|---|
| サブエージェント経由の並列 | `Agent` ツールの `isolation: "worktree"` を規約で既定化する。起動する側がエージェント自身なので検出も通知も不要 |
| 後発セッション | 通知が届く。**移動すべきは後発**（先発は作業中で中断コストが高い） |
| ほぼ同時起動 | 双方が相手を検出するため両方に通知が出る |

## 変更内容

### `bin/detect-parallel-sessions`（新規）

検出ロジック本体。フックに埋め込むと単体で試せないため、コマンドとして切り出す。

- 引数なしで実行し、同一リポジトリ・同一 CWD の他セッションを JSON で標準出力へ
- 検出ゼロなら空配列
- `pgrep` / `lsof` / `git` のいずれかが使えない場合は空配列を返して正常終了（fail-open）
- **出力に含めるのは同一リポジトリのセッションのみ。** 無関係な他プロジェクトの
  絶対パスをコンテキストへ漏らさない

### `hooks/detect-parallel-sessions.sh`（新規・SessionStart）

`bin/detect-parallel-sessions` を呼び、検出があれば `additionalContext` を出力する。
フック自身は判定を持たない。

- **対象外リポジトリの判定**: `~/.claude/rules` の実体パスを解決し、その common-dir が
  現在のリポジトリの common-dir と一致するなら何もしない。設定リポジトリ名を
  ハードコードせず、リンク構造から導出する（リポジトリを別名で配置しても効く）
- 検出ゼロなら無出力で `exit 0`
- 既存の `warn-branch-behind-main.sh` と同じく、判定できない場合は黙って通す

### `rules/parallel-worktree.md`（新規）

- 通知を受けたときの判断材料と手順
- サブエージェント起動時は `isolation: "worktree"` を既定とする
- worktree 移行後の追跡外資産の復元手順（サブモジュール初期化・`.env` コピー）
- **worktree 対象外リポジトリ**として本リポジトリを明記し、理由（項目7）を併記

### `CLAUDE.md`

`rules/parallel-worktree.md` への参照を追加する。ホスト別の差異
（Codex CLI では自動読み込みされない）を既存の表記法に合わせて併記する。

### `.gitignore`

`.claude/worktrees/` を追加する（項目8）。

### `settings.json.template`

`SessionStart` に `hooks/detect-parallel-sessions.sh` を配線する。

### `tests/test_detect_parallel_sessions.py`（新規）

既存の `tests/test_warn_branch_behind_main.py` の流儀に合わせる。

- 同一 CWD の他セッションがある場合に検出されること
- 別 worktree にいる場合は検出されないこと（common-dir 一致・CWD 相違）
- 別リポジトリのセッションが出力に混入しないこと
- `lsof` が利用できない環境で空配列を返し、異常終了しないこと

## 検証手順

1. 一時リポジトリに worktree を2つ作り、`bin/detect-parallel-sessions` が
   「分離済み」と判定することを確認する
2. 同一ディレクトリでセッションを2つ起動し、後発側の SessionStart で
   通知が注入されることを確認する
3. 本リポジトリでセッションを起動し、**通知が出ないこと**を確認する（対象外の確認）
4. `lsof` を PATH から外した状態で異常終了しないことを確認する

## スコープ外

- **実行環境の衝突**（ポート・ローカル DB・コンテナ名）。項目4のとおり worktree では
  解決しない。並列作業一般の制約として別途扱う
- **非 git の親ディレクトリで起動したセッションからの編集。** 判定キーが common-dir で
  あるため、親が非 git だと値が取れず捕捉できない。拾おうとすると無関係な親ディレクトリの
  セッションまで巻き込み、誤検出の主因になる
- **リモートやコンテナで動くセッション。** プロセス検査は同一ホストに限る
