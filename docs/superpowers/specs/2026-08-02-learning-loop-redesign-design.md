### 根本原因

**A. 発火しない（learning-mode）**

1. **散文の「停止する」は上位指示に負ける。** システムプロンプトには「情報が揃ったら行動しろ」「タスクを完遂しろ」が入っている。`rules/` の散文指示は毎回これに敗北する。「もっと強く書く」では直らない。
2. **下限が無い。** 「1タスク内で問いかけは最大2回まで」は上限のみの規定で、0回が常に合法。
3. **OFF条件が広すぎる。** 「実装して」はコーディング依頼のほぼ全てに含まれる語。実質デフォルトOFF。
4. **発火条件が主観的。** 「判断が成長に繋がるとき」は自己判断で却下しやすく、合理化を防ぐ仕掛けが無い。
5. **目標と手段のズレ。** 目標はシニア/スタッフ（設計判断・障害分析・説明力）だが、手段は「5〜15行のコードを手で書かせる」。摩擦（エディタ往復）が高い割に目標能力に効いていない。

**B. 浅い（protege-output）**

1. **retrieval ではなく restudy。** 「なぜYにしたの？」を、AIが直前に説明した**直後**に問うている。ユーザーは言い換えるだけで済み、学習科学的に最も効果の薄い形になる。
2. **フィードバックが本体化していない。** 「その通り」で終わる設計で、学習効果の主要因である訂正フィードバックが発生しない。
3. **記録先が無い。** 上記ファクト1・2により、回答しても蓄積されない。間隔反復の材料がゼロ。

## 2. 目標と非目標

### 目標

以下4能力すべてを、**単一の機構**で鍛える。

- 設計判断・トレードオフ評価
- 原因分析・システム理解
- コード品質の目（レビュー力）
- 実装力（方針レベル）

- SessionStart hook による間隔反復出題（→ 段階2。journal に材料が溜まってから）
- TODO(human) 方式の維持（→ 廃止）
- `learning-output-style` プラグイン側の挙動変更（→ 触らない）

## 3. 中核設計 — ★ Predict / ★ Delta ループ

`learning-mode` と `protege-output` を廃し、1つのループに統合する。

```
[1] 予測フェーズ  最重要判断点で、答えを出す前に AskUserQuestion で予測を求める
[2] 開示フェーズ  AI の答え・調査結果・実装方針を提示する
[3] 差分フェーズ  ★ Delta で「予測と実際の差分」を返す
```

4能力すべてがこの1機構に載る。

| 能力 | 予測フェーズの問い |
|---|---|
| 設計判断 | 「A案とB案、どちらを選ぶ？」 |
| 原因分析 | 「調査結果はこれ。どのレイヤーが原因だと思う？」 |
| レビュー力 | 「この変更で最初に壊れるのはどこだと思う？」 |
| 実装力 | 「この関数、どういう方針で実装する？1行で」 |

### 3.1 順序が本質

予測は必ず**開示より前**に置く。開示後に問うと再読（restudy）になり、pretesting 効果が消える。この順序が守られない実装は、この設計を満たしていない。

### 3.2 停止の構造的担保

予測フェーズは **`AskUserQuestion` ツールの呼び出しを必須**とする。散文の「停止する」に依存しない。

- 同ツールは応答があるまで機構的に戻らない
- `settings.json.template` に `askUserQuestionTimeout: "never"` が既に設定済み
- 選択肢2〜4 ＋ 自動付与される「Other」により、回答コストは1クリック〜1行

**上書き宣言（必須）**: `AskUserQuestion` の既定ガイダンスは「ユーザーが決めるべき判断にのみ使え」だが、学習モードの予測フェーズでは教育目的の使用を明示的に許可する。ユーザー指示はツール既定ガイダンスに優先する。この宣言を書き忘れると、既定ガイダンスを根拠に回避される。

### 3.3 差分フィードバック — 機構の本体

★ Delta ブロックで、予測と実際の**差分のみ**を返す。

```
★ Delta ───────────────────────────────────────
予測: [ユーザーの予測]
実際: [実際の判断/原因/リスク]
差分: [下表に従った内容]
─────────────────────────────────────────────────
```

| 予測の結果 | 返し方 |
|---|---|
| 一致 | 一致を認めた上で、**予測に含まれていなかった観点**を1つ名指しする |
| 部分一致 | 欠けていた観点 ＋ **それが実務でどう事故るか**の具体例 |
| 不一致 | 正解を直接言わず、**その予測が破綻する反例**を1つ出す |

**禁止事項**: 「その通り」「正解」のみで終えること。一致した場合でも必ず一段深い観点を1つ足す。

### 3.4 発火規則

- **下限: 1タスクにつき最低1回（必須）。** タスク終了前に一度も発火していなければ、完了報告の前に必ず1回入れる
- **上限: 2回**
- **発火点の選び方**: そのタスクで最も「後から変えるのが高くつく判断」を1つ

下限の明文化が現行との最大の差である。

### 3.5 合理化防止テーブル

本リポジトリ既存パターン（`superpowers` 由来、`tdd-workflow` / `verification-loop` / `planner` で採用済み）に合わせる。

| 思考 | 現実 |
|---|---|
| 「今回は自明だから不要」 | 自明なら選択肢を2つ書けないはず。書けるなら問える |
| 「急いでいそうだから省く」 | OFFは明示指示のみ。推測で省くな |
| 「もう説明したから予測は不要」 | 説明後の質問は再読であって想起ではない。**説明の前**に問え |
| 「後でまとめて聞く」 | 開示後の予測は pretesting にならない。順序が本質 |
| 「タスクが小さすぎる」 | 小さいタスクほど判断点は1つに絞りやすい |

### 3.6 OFF条件

明示指示のみに絞る: 「全部やって」「任せる」「急ぎ」「予測なしで」

**「実装して」を除去する**（誤OFFの主因）。1タスク完了後は自動的にONに戻る。

## 4. learning-journal の仕様

### 4.1 配置と追跡

- 実体を `tasks/learning-journal.md` に置き、**git で追跡する**
- `.gitignore` から `tasks/learning-journal.md` の行を削除
- `setup.sh:220-260` の symlink 集約ブロックを**削除**（移行元リポジトリへの依存が消え、機構が1つ減る）

理由: 移行元は PRIVATE かつ業務用リポジトリであり、個人の学習ログの置き場として適切でない。このリポジトリで追跡することでマシン間同期とバックアップが得られ、後から振り返れる。

### 4.2 抽象化ルール（セキュリティ要件）

本リポジトリは **PUBLIC**（`gh repo view` で確認済み）。journal への書き込み前に必ず以下を満たすこと。

**禁止**
- 社名・組織名・プロジェクト名・リポジトリ名
- 内部ホスト名・内部URL・エンドポイント
- テーブル名・カラム名・内部ファイルパス
- 業務コードの直貼り

**必須**
- 技術的本質のみを一般化して書く。具体例は最小再現形に置き換える
- 判断に迷ったら書かない

抽象化の強制はセキュリティ要件であると同時に、「本質だけを取り出して言語化する」訓練そのものとして機能する。

### 4.3 記録フォーマット

末尾に追記（日付昇順を維持）。予測を外した回には `[MISS]` タグを付ける（段階2の優先出題用）。

```
## [YYYY-MM-DD] | [タスク概要] [MISS]

**判断点:** [何を判断する場面だったか]

**予測:** [ユーザーの予測をそのまま記録]

**実際:** [実際の判断・原因・リスク]

**差分:** [★ Delta で返した内容]
```

見出しは `## [YYYY-MM-DD] | ...` 形式に統一する（現行は `## YYYY-MM-DD | ...` との混在がある）。

### 4.4 既存11エントリの移行

移行元 PRIVATE リポジトリの `tasks/learning-journal.md`（11件・143行、2026-04-17〜2026-07-01）を本リポジトリへ移行する。

**方針**: 抽象化して移行し、**原本はアーカイブとして移行元リポジトリに残す**（以降は書き込まない）。抽象化で失われる業務固有のディテールを、PRIVATE 側で保持しておくため。

**手順**

1. 11件を1件ずつ読み、4.2 の抽象化ルールを適用して書き換える
2. 日付昇順に並べ替える（原本は最新の2026-07-01が先頭に混入している）
3. 見出しフォーマットを `## [YYYY-MM-DD] | ...` に統一する
4. 本リポジトリの `tasks/learning-journal.md` に配置する
5. **コミット前にユーザーが全文をレビューする**（PUBLIC への公開となるため、AI の抽象化判断だけで確定させない）

**抽象化で置換が必要な既知の要素**（読解時に追加分を検出すること）

- 業務リポジトリ名 → 役割で表現する（例: 「負荷試験スクリプトのリポジトリ」）
- 業務システム固有の構成・エンドポイント・パラメータ名 → 一般化するか削除する
- 技術トピック（分散DBの基礎、Kotlin の `by lazy`、モックテストの観点 等）は一般的知識であり、そのまま残してよい

**移行元リポジトリ側の後始末**は本リポジトリからは実施しない。実装完了後に引継書を作成し、当該リポジトリ側の Claude に委譲する（対象: `setup.sh` の symlink 集約ブロック、`README.md` の「個人ナレッジ集約」節、devcontainer の bind mount の要否、共有ワークスペース側 symlink の後始末）。

## 6. エビデンス対応

| 設計要素 | 根拠 |
|---|---|
| 開示より前に予測させる | **Pretesting effect**（Richland et al. 2009; Kornell et al. 2009）— 事前テストは、答えを外した場合でもその後の学習を促進する |
| 差分フィードバックの必須化 | **Hypercorrection effect**（Butterfield & Metcalfe）— 確信を持った誤りは訂正後に最も強く定着する |
| 「その通り」で終えるのを禁止 | **Deliberate practice**（Ericsson）— 効果の本体は反復量ではなく即時かつ具体的な訂正フィードバック |
| 予測を1行で言語化させる | **Generation effect**（Slamecka & Graf 1978）/ **Self-explanation effect**（Chi et al. 1989） |
| 想起させる形にする（再読をやめる） | **Testing effect**（Roediger & Karpicke 2006）— 再読より想起の方が長期保持に有利 |
| journal 蓄積 → 段階2で再出題 | **Spacing effect**（Cepeda et al. 2006 メタ分析）— 長期保持への最大レバー |
| TODO(human) の廃止 | **Cognitive load theory**（Sweller）/ **Expertise reversal effect**（Kalyuga）— 熟達が進んだ学習者に過剰な足場は逆効果 |
| 上限2回の維持 | **Desirable difficulties**（Bjork）— 困難は有効だが過剰だと逆効果。テンポとの均衡点 |

## 7. 検証方法

プロンプトレベルの変更のため、静的検証と実地検証を分ける。

**静的検証（実装直後）**
1. `grep -rn "protege\|Protégé" . --exclude-dir=docs --exclude-dir=claude-code-best-practice --exclude-dir=.git` が0件であること（削除したファイルへの参照が残っていないことの確認）
   - 注: `TODO(human)` は `learning-output-style` プラグインが管理する別機構であり、`output-styles/review-and-design.md:105` の言及は**残す**。grep 対象に含めないこと
2. `bash setup.sh` を2回連続実行し、冪等であること・journal 関連のエラーが出ないこと
3. `git status` で `tasks/learning-journal.md` が追跡対象として現れること

**実地検証（運用開始後）**

4. 以降3タスクで、`tasks/learning-journal.md` にエントリが3件追加されていること（＝下限1回の保証が効いている証拠）

検証4が満たされない場合、この設計は失敗している。その場合は hook による強制注入（段階2の前倒し）を検討する。

### 7.1 検証4を自動発火させる仕組み

検証4は将来時点の観察であり、ユーザーの「検証して」という指示に依存させてはならない。**それは今回修正しようとしている故障（誰も気づかないまま放置される）と同じ構造だから**である。

そこで、**journal のヘッダに検証チェックポイントを埋め込む**。

- `tasks/learning-journal.md` の冒頭に、判定基準と失敗時のアクションをコメントで記載する
- AI は追記のたびに必ずこのファイルを開くため、構造上ヘッダが目に入る
- `rules/learning-mode.md` に「journal 追記時にヘッダの検証項目を確認する」を1行加える

新しいファイルも hook も増やさず、既存の「journal を開いて追記する」という動作に検証を相乗りさせる。発火していない失敗ケースでは AI が journal を開かないことになるが、その場合は「エントリが増えていない」という形でユーザー側から一目で可視化されるため、検知漏れにはならない。

これでも見落とすようなら段階2の hook 方式に上げる。ただし B を試す前に hook を作ると、有効性が未確認の機構に実装コストを払うことになるため順序として後に置く。
