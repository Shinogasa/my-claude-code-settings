# 日本語文書のレビューとスキル読み込み確認の設計

## 目的

Claude Codeが書いた日本語のMarkdown・設定ファイルをコミットするとき、またはConfluenceへ投稿するときに、
yomiyasuの基準で文章をレビューし、自然な日本語に直す。

普段のセッションで消費するコンテキストは増やさない。yomiyasu本体（SKILL.mdとreferenceで約40KB）を読むのは、
レビュー用のサブエージェントだけにする。サブエージェントは、メインのエージェントに結果の要約だけを返す。

レビューは、文書が完成した時点で1回だけ行う。書いている途中の版を何度もレビューすると、
コストがかさむうえに、メインのエージェントが覚えている文面とファイルがずれて編集が失敗しやすくなるからである。
完成の合図は、ファイルではコミット、Confluenceでは投稿とする。

あわせて、スキルの読み漏れを会話記録から機械的に見つける（5節）。読み漏れとは、スキルを呼んだのに、
そのスキルが読むよう求める資料を読まないまま作業を進めることを指す。

判断の経緯と却下した案は `docs/adr/0024-jp-doc-review-hook.md` に記録する。

## 範囲

| 項目 | 内容 |
|---|---|
| 対象ホスト | Claude Codeのみ。Codex対応はbacklogに積む |
| 対象リポジトリ | すべて（グローバル設定の `settings.json` に配線する） |
| 対象ファイル | 日本語を含む `.md`・`.toml`・`.yaml`・`.yml`・`.json` |
| 対象の投稿 | Confluenceのページ作成・更新、フッターコメント、インラインコメント |
| 読み込み確認の対象 | 対応表に登録したスキル。最初はyomiyasuだけを登録する |

次のものは対象外とする。

- Bash経由の書き込み（`cat > file` やスクリプトによる書き込み）。Write・Editを通らないため、記録できない
- gitの管理下に無いファイルと、コミットしないファイル。完成の合図が無いため、レビューを依頼する時点が無い
- submoduleの中のファイル、`node_modules`、`vendor`、`dist`、`build`、ロックファイル
- 使い捨ての作業ファイル。`tasks/todo.md`、`.superpowers/` の下、実体が `~/.claude/` の下にあるファイル
  （memory、plans、projectsなど。このリポジトリが管理する設定はリポジトリ側へ解決されるので、ここには入らない）、
  一時ディレクトリの下（scratchpadを含む）
- レビュー用の下書き置き場（`~/.claude/state/jp-doc-review/drafts/`）

## 全体の流れ

```
[書き込み]  Write / Edit
     │  PostToolUse: 対象ファイルなら、パスと書き足した日本語の文字数を記録する（出力なし）
     │  レビュワー（agent_type = jp-doc-reviewer）の書き込みは記録しない
     ▼
[コミット]  Bash の git commit
     │  PreToolUse: そのリポジトリの中で、まだ存在し、かなを含み、
     │  書き足した日本語が100文字以上のファイルを記録から集める
     │  該当があれば1回目だけコミットを止め、jp-doc-reviewerへのレビュー依頼を返す
     ▼
[レビュー]  サブエージェント jp-doc-reviewer（model: opus）
     │  yomiyasuを全部読み、このセッションで書いた箇所を、意味を保って直す。リンターで確かめる
     │  メインには「変えた点」と「書き手に確かめたい点」だけを返す
     ▼
[メイン]  直したファイルをステージし直して、もう一度コミットする（2回目は通す）

[Confluence]  create/updateConfluence*
     └ PreToolUse: 日本語が100文字以上なら、1回目だけ止めて下書きのレビューを求める
```

## 構成要素

| 追加・変更するもの | 役割 |
|---|---|
| `skills/yomiyasu`（submodule） | commitを固定したyomiyasu本体。`manifests/skills.json` の `shared` に追加し、既存の仕組みで両ホストにリンクする |
| `hooks/hook_support.py` | 会話記録の読み取りと、フックの出力の組み立てをまとめた補助モジュール。下の2本のスクリプトが使う |
| `hooks/jp-doc-review.py` | 1本のスクリプトで、記録・コミット時の依頼・Confluenceの事前チェックを担う。第1引数でイベントを切り替える |
| `hooks/skill-read-check.py` | スキルごとの必読資料を会話記録と照合する、汎用の確認。StopとSubagentStopで動く |
| `manifests/skill-required-reads.json` | スキル名と必読資料の対応表 |
| `agents/jp-doc-reviewer.md` | レビュー用サブエージェント。Codex用の定義も既存の生成スクリプトで作られるが、Codexには起動するフックが無い |
| `settings.json.template` | フックを配線する（PostToolUse、PreToolUseのBashとConfluence、Stop、SubagentStop） |

常時読み込みのruleは追加しない。

## 定数

| 名前 | 値 | 意味 |
|---|---|---|
| `MIN_JP_CHARS` | 100 | レビューを依頼する下限。書き足した日本語の文字数で数える。コミット時とConfluenceで共通 |
| `TARGET_SUFFIXES` | `.md` `.toml` `.yaml` `.yml` `.json` | 記録の対象にする拡張子 |
| `STATE_RETENTION_DAYS` | 7 | 状態ファイルを残す日数。これを過ぎたものは掃除する |
| `REVIEWER_AGENT` | `jp-doc-reviewer` | レビュワーのagent名。記録から除外する判定にも使う |

日本語の文字数は、ひらがな・カタカナ・漢字の数で数える。ただし、かなを1文字も含まない文字列は0とみなす。
漢字だけの文字列は、中国語と区別できないからである。

## 1. 記録（PostToolUse）

matcherは `Write|Edit` とする。NotebookEditは `.ipynb` だけを書き、対象の拡張子に当たらないので、matcherに入れない。

1. 入力の `agent_type` が `jp-doc-reviewer` なら何もしない
2. 書き込み先のパス（`file_path`）を取り、symlinkを解決した実体のパスにする。同じファイルを別のパスで書いても、まとめて数えるためである
3. 拡張子が `TARGET_SUFFIXES` に無い、または対象外のパスなら何もしない
4. 書き込んだ文字列（Writeは `content`、Editは `new_string`）の日本語の文字数を数える
5. `~/.claude/state/jp-doc-review/<session_id>.jsonl` に `{path, jp_chars}` を1行追記する

ツール名がWriteかEditなのに、入力に `file_path`（文字列）が無い、またはWriteに `content`、Editに `new_string` のキーが無い場合は、
入力の形が変わったとみなしてエラーにする（6節）。黙って何もしないと、全リポジトリで記録が止まっても誰も気づけない。
Editの `new_string` が空文字列なのは削除として正当なので、キーの有無で判定する。

標準出力には何も出さない。だから、この段階ではコンテキストを消費しない。

submoduleの判定は次のとおり。ファイルのあるディレクトリから親へたどり、最初に見つかった `.git` で決める。
`.git` がファイルで、その `gitdir:` が `.git/modules/` の下を指していればsubmoduleの中とみなす。
git worktreeの作業ツリーにも `.git` ファイルが置かれるが、`gitdir:` は `.git/worktrees/` の下を指すので、submoduleとは区別できる。
`node_modules` などの除外ディレクトリは、見つかったリポジトリのルートより下の部分だけで判定する。

## 2. コミット時の依頼（PreToolUse: Bash）

matcherは `Bash` とする。コマンドが `git commit` でなければ何もしない。
`git commit` かどうかは、コマンドを区切り（`&&`、`;`、`|` など）で分けた各部分について、
環境変数の代入と `git` のグローバルオプション（`-C <path>` など）を飛ばした最初のサブコマンドが `commit` かで判定する。
コミット先のリポジトリは、`-C <path>` があればそのパス、無ければ入力の `cwd` から決める。

**1回目のコミット**

1. 記録を読み、パスごとに日本語の文字数を合計する
2. 次をすべて満たすパスを集める
   - コミット先のリポジトリの中にある
   - ファイルがまだ存在する
   - 中身にかなを含む
   - 合計が `MIN_JP_CHARS` 以上
3. 該当が無ければ通す。記録は残し、次のコミットまで書き込みを合算する
4. yomiyasu（`~/.claude/skills/yomiyasu/SKILL.md`）か、jp-doc-reviewerの定義（`~/.claude/agents/jp-doc-reviewer.md`）が
   見つからなければ止めない。レビューを省略したことを、`systemMessage` でセッションに1回だけ表示する
5. 入力に `agent_type` がある（サブエージェントの中のコミット）なら止めない。サブエージェントはレビュワーを起動できないためである。
   代わりに、未レビューの日本語の文書がコミットされることを `systemMessage` で表示する
6. それ以外なら、依頼したパス、その時点の記録の件数、会話記録の大きさを `<session_id>.dispatched.json` に書き、
   `permissionDecision: "deny"` で止める

denyの理由には、対象のパスの一覧と、次の指示を書く。

- jp-doc-reviewerサブエージェントにこれらのパスを渡し、このセッションで書いた箇所を伝えて、その範囲だけを直させる
- 直したファイルを `git add` し直してから、もう一度コミットする
- レビュワーの報告を受けたら、変えた点と書き手に確かめたい点をユーザーに伝える

**2回目のコミット**

`dispatched.json` があるときのコミットは通す。メインのエージェントが依頼に従わなかった場合も、ここでコミットできる。
1回だけ促し、それでも動かなければ通す作りである。

通す前に、依頼した時点までに記録された行のうち、依頼したパスの行だけを消す。
依頼の後に書き足された分は、次のコミットのために残す。そのうえで、依頼した時点より後の会話記録に、
`subagent_type` が `jp-doc-reviewer` のAgent呼び出しがあるかを確かめる。無ければ、レビューが実行されなかったことを
`systemMessage` で表示する。メインのエージェントが自分で書き直したと報告しても、ユーザーはこの表示で気づける。


## 3. Confluenceの事前チェック（PreToolUse）

matcherは `mcp__.*__(create|update)Confluence(Page|FooterComment|InlineComment)` とする。
MCPサーバー名が変わっても捕まえられるように、サーバー名の部分は正規表現で受ける。

1. `body` と `title` に含まれる日本語が `MIN_JP_CHARS` 未満なら通す
2. 投稿先のキーを作る。ツール名と、`pageId`・`parentCommentId`・`title` のうち最初に見つかった値を組み合わせる
3. そのキーへの投稿が、まだ止めていない投稿なら、次のようにする
   - 本文を `~/.claude/state/jp-doc-review/drafts/` に書き出す。拡張子は `contentFormat` に合わせる（`markdown` は `.md`、`html` または指定なしは `.html`、`adf` は `.json`）
   - 本文のハッシュと、その時点の会話記録の大きさを、キーと一緒に記録する
   - `permissionDecision: "deny"` で止め、理由で次を指示する。下書きをjp-doc-reviewerに渡し、このセッションで書いた箇所だけを直させること。
     HTMLのタグや `data-*` 属性は変えさせないこと。直した下書きの内容で投稿し直すこと
4. すでに止めた投稿先なら通し、そのキーの記録を消す。次のどちらかに当たれば、レビューされないまま投稿されたことを `systemMessage` で表示する
   - 本文のハッシュが1回目と同じ
   - 止めた時点より後の会話記録に、jp-doc-reviewerのAgent呼び出しが無い

1回目は止めるので、Confluenceには何も送られない。通した後に同じ投稿先へまた投稿すると、もう一度止める。

## 4. レビュワー（agents/jp-doc-reviewer.md）

| 項目 | 値 |
|---|---|
| tools | Read, Edit, Bash（リンターの実行用） |
| model | opus |

手順は次のとおり。

1. yomiyasuのSKILL.mdを全文読む
2. ファイルごとにドメイン（tech・business・essay）を決める
3. 書き直す前に、構文変換原則、語彙カタログ、決めたドメインの仕様を、Readツールで全文読む
4. 依頼で範囲を指定されたら、その範囲だけを、意味の4点（主張・比重・言い切りの強さ・文の働き）を保って直す。
   範囲の指定が無ければファイル全体を対象にする。ファイルはEditでその場で書き換える
5. 同梱のリンターで確かめる。リンターの指摘を消すためだけの言い換えはしない
6. メインには、ファイルごとに「変えた点」と「書き手に確かめたい点（最大2点）」だけを返す。
   資料を読めなかったときは書き直さず、読めなかった資料を報告する

レビュワーは社内文書を読むので、本文に仕込まれた指示でコマンドを実行されないよう、定義のhooksで道具を絞る。

- Bashは、`python3 <yomiyasuの置き場>/scripts/yomiyasu_lint.py <ファイル1つ>` の形だけ通す。区切りや引用符付きの `~` は通さず、`-` で始まる対象も止める（`pre-tool-use-reviewer-bash`）
- Editは、依頼文に書かれたファイルだけを通す。`Agent|Task` のPreToolUseフック（`pre-tool-use-agent`）が、`jp-doc-reviewer` への依頼文から
  `/` を含む語をパスとして取り出し、実在する通常ファイルの実体を `<key>.reviewer-allow.json` に和で記録する。
  `pre-tool-use-reviewer-edit` は、許可リストにある実体だけを通す。許可リストが無い、読めない、壊れているときは止める。
  yomiyasuの置き場、フックのディレクトリ、レビュワー定義、`settings*.json` は、許可リストにあっても止める。
  日本語やスペースを含むパスは取り出せないので、そのファイルは直せない

次のものは変えない。

- エージェント向けの指示ファイル（CLAUDE.md、`rules/`、`skills/`、`agents/`、`output-styles/`）の★ブロック・表・太字・箇条書き
- コード、識別子、URL、パス、コマンド
- テストやgrepが参照している文言（対象のリポジトリでgrepして確かめる）
- Confluence下書きのHTMLタグと属性

## 5. スキルの読み込み確認（汎用）

スキルを呼んだのに、そのスキルが読むよう求める資料を読まないまま作業を進める失敗を、会話記録で見つける。

この仕組みで確かめられるのは「読んだかどうか」だけである。「使うべき場面でスキルを呼んだか」と
「読んだ内容に従ったか」は確かめられない。前者は、2〜3節のようなスキルごとの発火条件で補う。
後者は仕組みにしない。

**対応表**（`manifests/skill-required-reads.json`）

スキルごとに、置き場と必読資料を登録する。

```json
{
  "schemaVersion": 1,
  "skills": {
    "yomiyasu": {
      "root": "~/.claude/skills/yomiyasu",
      "alternateRoots": ["~/.claude/skills/yomiyasu/skills/yomiyasu"],
      "allOf": ["references/gemini-syntax.md", "references/slop-catalog.md"],
      "anyOf": [["references/domains/tech.md", "references/domains/business.md", "references/domains/essay.md"]]
    }
  }
}
```

`allOf` の資料はすべて読む必要がある。`anyOf` は、組ごとに少なくとも1つを読めば満たす。
`alternateRoots` には、同じスキルの複製の置き場を書く（yomiyasuのリポジトリには、同じスキルの複製が入っている）。
どの置き場から呼んでも、どの置き場の資料を読んでも、同じスキルとして扱う。

対応表には、読み漏れが実際に起きたスキルだけを登録する。条件付きで読む資料
（「迷ったときに読む」など）は登録しない。登録しすぎると正しい作業まで止めてしまい、
フックごと外される恐れがある。

**確かめ方**（`hooks/skill-read-check.py`）

1. 会話記録を読む。Stopでは `transcript_path`、SubagentStopでは `agent_transcript_path` を使う。
   最後のcompactより後の部分だけを対象にする。SubagentStopで `agent_type` が空なら何もしない
   （Claude Codeの内部のエージェントでも発火するため）
2. その範囲で、登録されたスキルが呼ばれたかを調べる。次のどれかがあれば、呼ばれたとみなす
   - Skillツールの呼び出し（`plugin:name` の形なら、`:` より後の名前で照らし合わせる）
   - そのスキルの `SKILL.md` のRead
   - スラッシュコマンドで呼んだときに残る `Base directory for this skill: <置き場>` の行
3. 呼ばれたスキルごとに、必読資料を読んだかを調べる。Readツールの呼び出しのほか、
   Bashのコマンドに資料のパスが含まれていれば読んだとみなす（`cat` などで読む場合のため。`grep` で一部だけを見た場合も数える近似である）。
   パスはsymlinkを解決した実体で比べる
4. 足りない資料があり、`stop_hook_active` が `false` なら、blockして読んでいない資料の一覧を返す
5. `stop_hook_active` が `true` なら通し、資料が読まれないまま終わったことを `systemMessage` で表示する

compactの区切りは `{"type": "system", "subtype": "compact_boundary"}` の行で見分ける。
会話記録の形式はClaude Codeの内部仕様で、公開された契約ではない。読めなかったときは、
確認できなかったことを `systemMessage` で表示する。

## 6. 失敗時の扱い

検査できなかったことを、問題なしとして扱わない。必ず画面に表示する。

| 状況 | 振る舞い |
|---|---|
| スクリプト内で例外が起きた | 内容を標準エラーに出し、終了コード1で終える。作業は止めないが、フックのエラーとして画面に表示される |
| 入力の形が想定と違う（1節） | 例外と同じ扱いにする |
| yomiyasuかjp-doc-reviewerの定義が見つからない | レビューを依頼せず、`systemMessage` でセッションに1回だけ表示する |
| 状態ディレクトリに書き込めない | 例外と同じ扱いにする |
| 記録が壊れている（JSONとして読めない行がある） | その行を飛ばし、飛ばした件数を `systemMessage` で表示する |
| 会話記録を読めない（形式が変わった） | 確認できなかったことを `systemMessage` で表示し、止めない |
| 対応表の資料がディスクに無い（上流で名前が変わった） | 対応表が古いことを `systemMessage` で表示し、その資料の確認を飛ばす |

状態ファイルと下書きは、社内文書の写しを含みうる。ディレクトリは0700、ファイルは0600で作る。
状態ファイルを読んで書き戻す処理は、セッションごとのファイルロックで囲み、一時ファイルには一意な名前を使う。
同じセッションのメインとサブエージェントが並行して書いても、状態が壊れたり、確認が素通りしたりしないようにするためである。

## 7. 導入と移行

**新しいPC**: `git clone --recurse-submodules` の後に `bash setup.sh` を実行するだけで使える。
setup.shには、submoduleを初期化する処理が既にある。

**npx版から移る既存のPC**: 先に `npx skills remove -g yomiyasu` で外してから、`bash setup.sh` を実行する。
npx版を残したままにすると、`npx skills update` がsubmoduleへのリンクを通して、submoduleの中身を上書きする恐れがある。
setup.shは既存のリンクを衝突として検出するので、確認してから置き換える。

READMEには、この移行の手順と、新しいフックがClaude Code専用であること、状態ファイルの置き場を書く。

## 8. テスト

**単体テスト**（TDDで書く）

合成した入力をスクリプトに渡し、次を確かめる。

- 記録: 対象拡張子・除外パス（使い捨ての作業ファイルを含む）・submodule・worktree・レビュワーの除外・かなを含まない文字列・入力の形が違うときのエラー
- コミット時の依頼: `git commit` の判定（`-C`、環境変数、区切り）、リポジトリの外の記録を数えないこと、99文字と100文字の境界、
  サブエージェントの中のコミット、yomiyasuやagent定義が無いときの表示、2回目で通すこと、依頼の後の書き足しを残すこと、
  レビュワーが起動していないときの表示
- Confluence: 99文字と100文字の境界、1回目のdenyと下書きの作成、2回目の許可、本文が同じときとレビュワーが起動していないときの警告、投稿先のキーの優先順位
- 読み込み確認: Skill呼び出し・SKILL.mdのRead・スラッシュコマンドのどれでも起動とみなすこと、複製の置き場、Bashでの読み込み、`allOf` と `anyOf`、
  compactより前のReadを数えないこと、空の `agent_type` のSubagentStopで何もしないこと、2回目は通して表示すること、会話記録が読めないときの表示
- 状態ファイル: 権限、並行して書いたときに壊れないこと
- 失敗時: 例外での終了コード、壊れた記録行の扱い

状態ディレクトリなどの置き場は環境変数で差し替えられるようにし、テストでは一時ディレクトリを使う。

**配線のテスト**: `settings.json.template` のフックのmatcherとコマンドを固定する。

**実機での確認**: 合成した入力でのテストが通っても、実機で動く証拠にはならない。
実際のClaude Codeのセッションで次を確かめ、結果を記録する。

1. 日本語のMarkdownを書いてコミットしようとすると止められ、jp-doc-reviewerが起動する。直した後のコミットは通る
2. レビュワーの書き込みが記録されない（`agent_type` が実際に入力に入っている）
3. Confluenceへの1回目の投稿が止められ、下書きが作られる（止めるので何も送られない）
4. yomiyasuを呼んで、referenceを読まずに作業を終えようとすると止められる。referenceをBashで読んだ場合は止められない
5. 対話のセッション（プロンプト候補が有効）で、SubagentStopの誤った表示が出ない

## 既知の制約

- Bash経由の書き込みはレビューされない
- gitの管理下に無いファイルと、コミットしないファイルはレビューされない
- レビュワー以外のサブエージェントが書いた文書も、メインのセッションの記録に入る（2026-10-02に実機で確認）。
  そのため、サブエージェントに書かせた文書も、メインがコミットするときにまとめてレビューされる。
  サブエージェント自身がコミットした場合は止めず、表示だけにする
- `git commit` の判定は、コマンドの文字列から行う近似である。エイリアスやスクリプトの中のコミットは捕まえない
- yomiyasuのリポジトリには同じスキルの複製（`skills/yomiyasu/`）が入っているため、スキル一覧に `yomiyasu:yomiyasu` が重複して出ることがある
- レビューのたびにopusのサブエージェントが動くので、日本語の文書を含むコミットは時間とトークンが増える
- 読み込み確認で分かるのは、資料を読んだかどうかまでである。読んだ内容に従ったかは確かめられない。Bashでの読み込みは、パスの有無で判定する近似である
- レビュワーがリンターを実行したかは確かめない
