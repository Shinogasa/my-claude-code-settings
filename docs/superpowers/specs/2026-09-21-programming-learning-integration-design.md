# 実務内の判断・コード学習と専用学習記録リポジトリ

## 1. 目的と承認範囲

ユーザーがAIの助けを徐々に減らし、自分で調査し、判断し、コードを変更・検証できるようにする。
成功は説明量や正答率ではなく、別の実作業で必要な判断・検証を自分から行えるかで確認する。

ユーザーは、既存learning-modeの再利用、両モードの競合整理、専用学習repoへの記録集約を概ね採用した。
誤答後の本人による再修正、支援量の記録、全能動形式での答えの先渡し防止も採用済み。
teachは今回は導入しない。学習repoはまだ作成していない。

本書は実装前の最終設計案。新repo作成、記録の移管、runtimeの変更はまだ行わない。
repo名は `programming-learning`、初期clone先は `~/garage/programming-learning` を提案値とする。
公開範囲はユーザー指定によりPUBLIC。repo名・clone先の配備値を共有ruleへ埋め込まない。

## 2. 現状と改善対象

- `rules/learning-mode.md` は判断の予測・理由・差分・過去原則との接続を持つ。
- `rules/code-learning.md` と `skills/code-learning/SKILL.md` は実コードの演習を持つ。
- 現状は設計判断とコード技能で発火・停止・先渡し防止の記述が分散している。
- 設計Deltaの定石が後続のコード演習を先に解説する経路がある。
- 同程度の出題抑制と、後日の保持確認を両立させる規約が弱い。
- 学習記録は設定repo内にある。調査時の判断記録99件には旧形式も含まれる。
- 過去には別repoが未cloneで、記録先のリンク作成を黙って省いた運用事故がある。

現時点で、教育効果の因果関係は未検証。静的テストや架空の学習者の応答を、実ユーザーの成長証拠にしない。

## 3. 所有範囲

| 資産 | 所有する責務 |
|---|---|
| `rules/learning-mode.md` 共通節 | ON/OFF、回数、候補の担当決定、答えの開示順、記録先の確認 |
| 同ファイルの設計判断節 | 既存Predict、理由の自己説明、判断基準の3軸、Delta |
| `rules/code-learning.md` | コード技能の候補検出と詳細skillへの入口 |
| `skills/code-learning/SKILL.md` | 調査・レビュー・変更・実装の演習、再修正、転移確認 |
| `learning/README.md` / `learning/code/README.md` | 記録契約、能力の範囲、保持確認、旧記録の扱い |
| `bin/learning-store.py`（追加予定） | 保存先の識別、構造検査、記録の読み書き、旧記録の取込検査 |
| 専用学習repo | ユーザーの観測記録と、そのGit履歴 |

共通方針の正本を既存learning-modeに置く。新しい常時ルーターや学習用runtime hookは増やさない。
コード側は共通節を参照し、異なる既定値を重ねない。CLIは教育判断・採点・出題をしない。

## 4. 発火と競合の調整

1. 明示OFFを最初に確認する。OFF条件と次タスクでの復帰は現在のまま維持する。
2. 現在の要求に直接関係する能力を一つ特定する。記録が無いだけで未習得と判断しない。
3. 成立する案の比較・採否を鍛える場合は設計判断、実コードからの調査・変更・検証を鍛える場合はコード技能へ割り当てる。
4. 同じ能力・同じ解法に対する出題は一つにする。ファイルや行が違っても、先の解説が答えになる場合は別イベントにしない。
5. 回数はpilot中、合計最大2イベント、うちコード学習最大1イベント。下限は設けない。

設計判断の「後から変更すると高コスト・競合・一般化可能」とL2優先は、設計判断だけへ適用する。
可逆的な観測や局所的な調査にも学習価値があるため、コード技能へこのゲートを流用しない。
「複数案を提示したら必ず発火」は廃止し、複数案の相談も同じ適格条件と上限で判断する。
普通の承認・好みの確認を、追加の演習に変えない。

同じ箇所で複数能力が候補になる場合は、ユーザー指定、反復する未解消の課題、後日の確認対象、新しい適格能力の順に選ぶ。
設計候補内の層の比較は従来どおり行う。品質・安全性に必要な通常の調査や修正は、学習イベント数にかかわらず実施する。

## 5. 既存ループを使った自力調査

形式は「鍛える能力と現在の支援量」から選ぶ。Writeが成立するという理由だけで他形式より優先しない。

| 能力 | 形式 | 観測する本人の行動 |
|---|---|---|
| 原因を絞る・検証方法を選ぶ | Investigate | 仮説を区別する観測を選び、得られた証拠を解釈する |
| 挙動・依存・失敗条件を読む | Review | コードと証拠に基づき指摘または問題が成立しない理由を示す |
| 追加条件へ対応する | Modify | 既存の正しいコードを条件に合わせて変更する |
| 局所的な実装を組み立てる | Write | 契約に沿う小さい実装や検証コードを書く |
| 前提知識を得る | Explain | 必要最小限を理解してから、可能なら能動形式へ進む |

Investigateも新たな独立モードではなく、コード技能の一形式とする。
既存の原因分析の「予測→理由→観測との差分」を使い、対象箇所・仮説・観測方法・結果の解釈のうち
今回の能力に該当する一つを本人へ委ねる。AIが把握した故障箇所を先に本人へ示してから、
自力で原因を特定したと評価しない。AI自身が通常の品質確認で先に調査することは妨げない。

ツール操作をAIが代行した場合、本人が行ったのは観測の設計や結果の解釈であると記録する。
コマンド操作・再現環境構築まで本人ができたことにはしない。

局所修正を独立して示した次の関連課題では、対象箇所・検証ケース・仮説の支援を一つ減らす。
前提知識不足なら説明を補い、範囲を狭める。難しくすること自体を成果にしない。
TDD・原因調査・security・verificationの実施順序は維持する。

## 6. 回答、フィードバック、再修正

- 最初の行動と理由の自己説明は、既存どおり順番に取得する。予測前に推奨や採点観点を渡さない。
- 本人が理由まで回答する前は、対象能力の答えを含むReview、定石、WHY説明、模範解を保留する。
- この保留は設計Predict、Write、Modify、Review、Investigateすべてに適用する。
- 通常の進捗説明・必要な前提知識は示せる。教材用の欠陥をproductionへ入れない。
- 初回回答を検証し、事実・repo慣例・複数成立する判断・未確認事項を区別する。
- 重要な誤解には反例か最小限のヒントを示し、本人が小さく再修正・再説明する機会を一度作る。
- 再試行は同じイベントに含める。解消しなければ未解消として残し、通常の作業を完了する。際限なく問わない。
- 解消後は一条件を変えた転移を確かめる。再試行後も前提が崩れている場合は転移を省き、未実施理由を残す。
- スキップ後は理由・再修正・転移を強制しない。未検証のユーザーコードは採用しない。

設計判断も、AIの採用案との一致を正しさの証拠にしない。別解の成立条件と根拠を扱う。
専門的判断に必要な検証や既存の教師routeが不足する場合、断定的な採点をしない。
教師routeの新設・未評価モデルへの授業委譲は本設計の対象外で、既存の教育上の制約を維持する。

## 7. 成長と後日の確認

能力IDは行動と対象範囲を表す。例は `async.cancel-result-application`、
`diagnosis.distinguish-competing-hypotheses`。異なる範囲をまとめて「非同期ができる」としない。
3軸名は設計判断の評価項目として残し、能力IDの代わりにはしない。
ID新設前に既存IDと対象範囲の一覧を確認し、同じ行動・範囲なら既存IDを使う。
同じIDであることだけを能力の同一性の証拠にせず、本文の対象範囲も照合する。
既存IDに重複が見つかった場合は記録の訂正で統一し、旧版を重複集計しない。意味検索用DBは追加しない。

状態は関連する証拠から都度判定し、AIの総合点や正答率で固定しない。

| 状態 | 条件と扱い |
|---|---|
| 観測あり | 行動を観測した。失敗・支援付き成功・未検証も区別して残す |
| 独立成功の候補 | 別文脈2回で成功し、2回目は対象能力を助けるヒントなし。能力に合った理由・検証がある |
| 保持を観測 | 時間を置いた関連作業でも、過去の答えやヒントを見る前に能力を独立して示した |
| 再確認が必要 | 同型の失敗、新しい制約、過去の証拠の不備が見えた |

コード技能の独立成功候補には検証可能な転移も要求する。設計判断では結論のhitではなく、
別文脈に合う判断基準とその根拠を評価する。
「保持を観測」は観測日・条件つきの事実であり、将来の保持や上位能力の保証にしない。

pilotでは最後の独立成功から7日以上空いた関連実作業で、短い自力確認を候補に戻せる。
7日は運用の試行値で、教育研究が保証する最適間隔ではない。
同程度の課題を控える規則には、この後日確認を明示的な例外として設ける。
本人が通常作業の中で自発的に示した場合は、その証拠を使い、確認のためだけに追加出題しない。
対象作業が来なければ保持は未確認のまま。カレンダー通知や過去エピソードの丸ごと再出題は実装しない。

「誤答ほど定着する」「正答率が高ければ必ず易しすぎる」は削除する。
同等の課題で必要な支援が減ったか、後日・別文脈でも行動できたかを主に見る。

## 8. 専用学習repoの構成

```text
programming-learning/
  README.md
  .learning-store.json
  records/
    decision/YYYY/YYYY-MM-DD-<UUID>.md
    code/YYYY/YYYY-MM-DD-<UUID>.md
  operations/YYYY/YYYY-MM-DD-<UUID>.json
  legacy/
    decision/<旧ファイル名>.md
    code/<旧ファイル名>.md
  imports/<取込UUID>.json
```

新規の能力記録は1イベント1有効レコード。既存記録を上書きせず、訂正は新しいrecord IDと
`supersedes`（直前のrecord ID）で保存し、同じevent_idを維持する。
読み取り時は同じイベントの訂正前の版を成功回数から除き、有効な末尾の版だけを使う。
訂正の分岐や参照先欠落は競合として返し、都合のよい版を選んで既習認定しない。
新しく行った再確認は別イベント、過去の採点や支援履歴の訂正は同じイベントとして区別する。
両種別は同じ保存先・識別方法を使い、判断基準とコード行動の本文は別にする。
teach用教材、MISSION、復習scheduler、DB、常駐サービスは設けない。

### 新規記録の共通契約

- `schema_version`、UUIDの `id` と `event_id`、`observed_at`、`kind`、`mode`、`capability_id`。
- `initial_result` は `pass / partial / fail / unverified`。
  `retry_result`、`transfer_result` は同じ値に `not_attempted` を加える。未検証・未実施を成功と区別する。
- 提示した文脈、ヒント、部分解、AIが修正した範囲を本文に残す。
- 初回自力の結果と支援後の結果を分け、今回実証できた範囲を明示する。
- ユーザーが実際に示した行動と理由、検証方法と結果、未解消の課題、関連記録IDを残す。
- 判断記録は既存の固定3軸を維持し、コード記録へ機械的に同じ採点を押し付けない。
- 説明を聞いただけ・無回答・スキップを能力記録にしない。自発的な実行動も同じ証拠条件で保存できる。

支援の有無を後から判定できない記録は、「ヒントなし」の成功回数に数えない。
対象箇所の特定を鍛えている回では、AIがその箇所を示すことも支援になる。
元の契約など必要な文脈を示しただけで常に支援ありとするのでもなく、対象能力との関係を書く。

ファイルはMarkdown本文と、CLIが生成する固定キーのfrontmatterを持つ。
frontmatterは `key: JSONスカラー` の限定形式にし、文字列は必ずJSONの引用・escapeを使う。
汎用YAMLを独自解釈せず、未知のschema versionや構造を明示的な読取失敗にする。
旧形式はlegacyとして本文をそのまま読み、新schemaの採点に混ぜない。

`operations` はpilotの発火・見送り・skip・中断回数を数える最小限の運用記録。
日時、event_id、能力ID（特定済みの場合）、終了理由、回答待ち回数だけを持ち、コードや会話を入れない。
能力の習得証拠には使わず、能力記録に保存しない事象を無理に「学び」へ変換しない。
OFF中に新しい運用記録は作らず、全タスクを網羅した計測であるとは主張しない。

公開範囲を問わず、業務コード・顧客名・非公開URL・内部パス等を記録へ持ち込まない。
原文を安全に残せない場合は、抽象化したことを明示して逐語引用と区別する。
抽象化で判断や証拠が失われる場合は保存せず、その事実をユーザーへ伝える。

## 9. 保存先の発見と書込み

マシン固有のbindingを `$XDG_CONFIG_HOME/agent-learning/config.json` に置き、
XDG_CONFIG_HOME未指定時は `~/.config/agent-learning/config.json` とする。
内容は `schema_version: 1`、`store_root`（正規化した絶対パス）、`store_id`（UUID）。
両ホストで同じbindingを使い、共有rule・作業repo・公開設定repoへユーザー固有の絶対パスを埋め込まない。

保存先の `.learning-store.json` はschema version、同じstore_id、`state: prepared / active` を持つ。
repo名だけで保存先を推測しない。preparedでは構造確認・取込だけを許し、新規イベントを書き込まない。
helperはbinding、marker、Git rootの実体一致、書込先の実体がroot内にあることを確認する。
記録先に外部を指すsymlinkを認めず、名前にユーザー入力のpathを使わない。

helperの操作は次に限定する。Python標準ライブラリと既存Gitを使用する。

| 操作 | 契約 |
|---|---|
| `init --repo <absolute-path>` | 明示された空ディレクトリにprepared状態のローカル学習repoを初期化しbindingを作る。既存の内容やbindingを無断置換しない |
| `status` | bindingとrepoを検査し、root・store_id・保存可否・具体的な失敗理由を返す |
| `bind --repo <absolute-path>` | clone・移設した既存storeのmarker、store_id、Git rootを確認し、ローカルbindingだけ作る。別bindingへの変更は明示的な `--replace-binding` がある場合だけ行う |
| `list` / `list --capability <id>` | 引数なしは既存能力IDと短い対象範囲を列挙し、ID指定時は対象能力の有効な新形式記録を返す。0件と読取失敗を区別する |
| `record --input <json-file>` | active状態で構造を検証し、指定record IDのファイルを排他的・原子的に作る。同じID・同じ内容の再実行なら既存を返し、異なる内容なら競合を返す |
| `import --source <settings-root>` | 旧記録を本文不変で取り込み、source commit・相対path・SHA-256をmanifestに残す。全件照合後だけactiveにする。旧記録0件も空manifestで確認する |

`record`の入力は抽象化後の内容だけ。機密の生データを一時ファイルに吐いてから消す運用にしない。
record入力の種別は `decision / code / operation` とし、operationには運用記録専用schemaを使う。
同じbinding・排他的書込みを使い、競合するイベントを同じファイルへ追記しない。
同じevent_idに能力記録とoperation記録を関連付けられ、冪等性の単位は種別とrecord IDの組とする。
同じevent_idの二つ目以降の能力記録には有効なsupersedesを要求する。作成時はイベント単位で排他し、
参照先が現在の末尾であることを確認する。他マシンとのGit統合で生じた分岐もlist時に検出する。
helperはネットワーク操作、Git push、ホスト権限の変更、教育上の正誤判定を行わない。
Git commitは通常の作業手順で新規の対象ファイルだけをstageして行い、既存の無関係な変更を含めない。
学習repoは `learning-records` ブランチで初期化し、mainへの直接コミット規約と衝突させない。
他のブランチへ移っている場合は勝手に切り替えず、保存とコミットの可否を分けて報告する。

### ホストへの配布

既存setupが配布するbinを使う。Claude Codeの入口は `~/.claude/bin/learning-store.py`、
Codexの入口は `~/.codex/bin/learning-store.py`。共有契約にこの対応表を置き、本文を片ホストへ固定しない。
現行setupの通常実行で学習repoを勝手に作らない。初回だけ明示したrootでinitを実施する。
別マシンでは既存repoをcloneしてbindし、statusで同じstore_idを確認する。新規initや再importは不要。
GitHub remoteを作成する場合は採用された名前・可視性で別工程として行い、helperの暗黙副作用にしない。

### 保存できない場合

学習候補を扱う前にstatusを確認し、保存不能をそのセッションで一度通知する。
通常の実装は継続でき、演習もsession内で実施できるが、永続記録済み・既習確認済みとは扱わない。
書込み時も再検査し、成功したレコードのpathとIDだけを保存完了の根拠にする。
失敗時は「未保存」と明示し、安全に抽象化済みの記録案を会話へ返す。元repoや別の場所へ黙って保存しない。
保存失敗を隠すretry loopや、保存のためのsandbox迂回を行わない。
ファイル保存、Git commit、remoteへの反映は別の状態として報告する。

## 10. 既存記録の移管

1. 旧記録も公開用の抽象化基準を満たすか確認し、不適合なら取込を止めて修正方針を別に決める。
   実施時点の対象件数とSHA-256を取得する。現在の99件という数値を固定の期待件数にしない。
2. 新repoのlegacyへ本文を変更せずcopyし、import manifestで全件照合する。
3. 再実行は同じsource path・hashなら追加せず、同名異内容は競合として止める。
4. 照合成功後、新規記録の保存先を新repoへ切り替える。途中で失敗したら切替を完了扱いにしない。
5. 設定repoの過去ファイルは既存ADRリンクを壊さない読み取り専用の履歴として残す。新規記録の追加先にはしない。

これは一度の歴史資料の複製であり、二つの書込先を同期する設計ではない。
新しい記録の正本は常に専用repo。過去の本文を新しいschemaに合わせて改作しない。
旧エントリのhitやAIの評価を、新しい独立成功・保持の証拠へ自動変換しない。
legacyは必要な文脈で参照し、本人が後日の実作業で示した能力は新規記録として残す。

## 12. 検証とpilot

### 保存機構

- 別の作業repoから両ホスト経路で同じstoreを参照できる。
- 未設定・未clone・marker不一致・権限不足・破損したrecordを、0件や保存成功に畳まない。
- 同時記録と同じ入力の再試行で、上書きや重複を起こさない。
- 同じイベントの訂正を受け入れ、旧版を成功回数に加えない。訂正の分岐を明示的な競合にする。
- 能力IDを知らない新規sessionでも既存能力を発見でき、範囲を照合して再利用する。
- 別マシンのcloneや移設先へbindでき、異なるstoreへの無断再接続を拒否する。
- 内容を確認できない既存ファイルを壊さない。migrationの中断・再実行で照合が成立する。
- file保存成功/commit失敗を区別し、無関係なdirty差分をcommitしない。
- legacyの原文hash、件数、既存参照、active保存先の切替を確認する。

### 実際の対話

- 同じ能力が両モードに該当しても、一方だけが出題する。
- 対象を先に特定しないInvestigateと、支援を一つ減らす課題が成立する。
- 誤答後に本人が再修正する。未解消・skipでは無理に転移や既習認定へ進まない。
- Write・Modify・Review・Investigate・Predictで、理由回答前の解説漏れを確認する。
- 正しい別解、誤った理由、事実不明、過去の支援量不明を正しく区別する。
- 複数案の相談、OFF、イベント上限、保存不能時でも本来のタスクが完了する。
- 日付を変えたfixtureは後日確認の選択動作だけを検証し、本物の長期保持と呼ばない。

静的契約・模擬対話・実ホストの動作を区別する。実ホストでの順序と保存を確認後、
5〜10件の適格な実作業でpilotし、支援量、自力修正、別文脈での行動、後日の成功、
中断回数・skip・採点の誤りを観測する。機会が来なかった後日確認は未確認のまま残す。
この件数を教育効果の因果推定や、教師の低い誤り率の証明には使わない。

## 13. 採らない案と理由

- **teach導入を前提にする**: ユーザーが今回は見送った。保存と継続確認は独立して成立させる。
- **二つの学習モードを全面的に一つの採点形式へ揃える**: 判断基準の説明とコードの実行動を混同する。
- **二つの入口に共通規則を重複記載する**: OFF・回数・先渡しの矛盾を再発させる。
- **毎回Writeを第一候補にする**: 原因の特定や検証方法の選択を本人が行う機会を減らす。
- **過去の判断エピソードを日付だけで再出題する**: 当時の文脈を失う。現在の実作業へ同型の能力を適用する。
- **二つのrepoへ新規記録を同時保存・同期する**: 正本と修正順序が曖昧になる。
- **全記録を毎sessionへ注入する**: 読取費用と答えの先渡しが増える。能力IDで必要な証拠だけ読む。
- **保存不能なら元repoへfallbackする**: 学習状態の所在が環境によって変わり、過去の静かな記録欠落を再発させる。

## 14. 根拠と限界

- [ADR 0001](../../adr/0001-learning-mode-prediction-format.md): 自己生成、元の判断エピソードの機械的再出題を却下した理由。
- [ADR 0007](../../adr/0007-learning-mode-decision-layer-gate.md): 設計判断の層ゲートと既存評価の限界。
- [ADR 0012](../../adr/0012-code-learning-mode.md): コード技能の責務と外部検証、teachとの境界。
- [旧設計](2026-08-02-learning-loop-redesign-design.md): 学習先repoが未cloneで記録されなかった経緯。
- [コード学習の初期評価](../../research/2026-09-17-code-learning-skill-eval.md): 模擬評価と実ユーザーの成果の区別。
- [Bisra et al., 2018](https://link.springer.com/article/10.1007/s10648-018-9434-x): 自己説明の研究上の支持。今回の全手順や実務者への効果の直接証明ではない。
- [Richland et al., 2009](https://learninglab.uchicago.edu/Pre-Testing_files/RichlandKornellKao.pdf): 誤答した事前テストにも後の学習効果があり得る。「誤答が多いほど良い」は導かない。
- [teachの現行説明](https://github.com/mattpocock/skills/blob/main/docs/productivity/teach.md): 専用workspaceと復習機構の範囲。今回のruntime依存にはしない。

本書の7日、既習候補2文脈、回数上限、運用記録の粒度はpilotの初期値である。
この設計を実装したことと、ユーザーの能力が伸びたことは別々に検証する。
