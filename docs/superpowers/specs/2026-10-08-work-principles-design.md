# 仕事の原則集の届け方 設計仕様

- 作成日: 2026-10-08
- 前提: 非公開リポジトリ `sakurai-transcripts` で作った原則集（確認済み25件、6テーマ）。
  作り方と各欄の意味は、同リポジトリの `docs/specs/2026-10-06-principle-extraction-design.md` にある
- 位置づけ: 蒸留の2段目。1段目で作った原則集を、スキルとフックで作業に届ける
- 判断の記録: `docs/adr/0026-work-principles-delivery.md`

## 1. 目的

原則集を次の2つの用途で使えるようにする。

1. **助言**: 仕事の進め方の相談を受けたとき、関係する原則を引いて助言する。スキルの description で自動発火させる
2. **レビュー**: 仕様書・ADR（主）と実装計画（従）を書き終えたとき、原則に照らした問いをユーザーへ出す

成功の基準は、節目のレビューで原則に照らした問いが実際に出て、ユーザーがそれを見て成果物を直すかどうかを決められること。
原則を読み込んだこと自体は成功に数えない。

## 2. 前提と制約

- このリポジトリは公開である。原則集の正本は `sakurai-transcripts`（非公開）に置き、ここには書き出したコピーだけを置く
- コピーに入れてよいのは `status: confirmed` の原則だけ。字幕の原文は持ち込まない
- `basis`（動画内容の要約）は公開しない。1段目の確認で動画と照らし合わせたのは原則の主旨で、`basis` の記述は照合していない。
  実在の人の発言として公開するには照合が要るので、backlogに回す
- レビューの指摘はユーザーに向ける。直すかどうかはユーザーが決める
- Claude Codeだけを対象にする。Codex対応は後回しにする
- Claude自身の振る舞いへ常に反映させるルールは作らない

## 3. 全体構成

```
sakurai-transcripts（非公開・正本）            my-claude-code-settings（公開）
principles.yaml + themes.md                    skills/work-principles/
   │                                             ├─ SKILL.md         助言（description で自動発火）と読み替えの規則
   └─ uv run transcripts-export ──────────────▶  └─ principles.json  生成物。直接編集しない
                                                agents/principle-reviewer.md   レビュワー（Read・Grepだけ）
                                                hooks/principle-review.py      PreToolUse(Bash) で git commit を1回止める
```

| 単位 | 置き場所 | 役割 | 依存するもの |
|---|---|---|---|
| 書き出し | `sakurai-transcripts` の `src/transcripts/export.py` | 正本から公開してよい欄だけを生成する。公開の関所を兼ねる | 正本、1段目の検証 |
| 原則集のコピー | `skills/work-principles/principles.json` | スキルとレビュワーが読む | なし（生成物） |
| 助言スキル | `skills/work-principles/SKILL.md` | 相談に原則を引いて助言する。読み替えの規則を持つ | 原則集のコピー |
| レビュワー | `agents/principle-reviewer.md` | 成果物を節目の原則と照らし、問いを返す | 原則集のコピー、スキルの読み替えの節 |
| フック | `hooks/principle-review.py` | 節目を検出し、レビュワーの起動を1回促す | git、会話記録（`hooks/hook_support.py`） |

## 4. 書き出し（sakurai-transcripts 側）

`uv run transcripts-export --dest <パス> [--check]`

- 1段目の検証（`transcripts-principles`）と同じ検査を先に走らせ、失敗したら書き出さない
- `status: confirmed` の原則だけを、`id` の順に並べる
- 公開する欄: `id`・`principle`・`scenes`・`checkpoints`・`review_question`（あるものだけ）・`not_applicable`・`source_url`・`theme`（テーマ名）
- 公開しない欄: `basis`・`risk`・`status`・`reject_reason`・`source.at`
- テーマの見出し、説明文、「使い分け」の注記を `themes` として同じファイルに書く。「原則なし」の節は書かない
- ファイルの先頭のコメントに、生成元、直接編集しないこと、再生成のコマンドを書く
- 設定リポジトリのテストは標準ライブラリだけで書くので、YAMLではなくJSONにした
- 同じ正本からは、毎回まったく同じ内容を出す（`--check` で比べるため）
- `--check`: 書き出さずに、生成した内容と `--dest` のファイルを比べる。差があれば差のある原則IDを出し、非ゼロで終わる
- `--dest` のファイルやディレクトリが無いときは「検査できなかった」として非ゼロで終わる。`--check` を成功にはしない

正本を更新したら、書き出してこのリポジトリでコミットする。正本とコピーのずれは `--check` で見つける。
このリポジトリ側からは正本を読めないので、`--check` は `sakurai-transcripts` で実行する。

## 5. 助言スキル（`work-principles`）

- description: 仕事の進め方（計画、企画、伝え方、レビュー、協働、自己管理）で迷っている相談のときに使う、と書く。
  コードの書き方や技術選定の相談では発火しないよう、対象外も description に書く
- 手順: 相談の場面を `scenes` で絞り、関係する原則を最大3件引く。原則IDと出典URLを添え、`not_applicable` に当たる場面では使わない。
  一見反対のことを言う原則（P13a・P14a）を引くときは、テーマの「使い分け」の注記に従う
- 読み替えの規則（レビュワーも読む節）
  - 製品・市場寄りの4件（P01a・P07a・P12a・P18a）: 元はゲーム製品と市場の話である。ソフトウェア開発に使うときは、
    「利用者」を、そのソフトウェアを使う人や呼び出す側に置き換え、置き換えたことを明記する
  - 決める人を前提にした原則（P04b・P11a・P15a・P17a）: ユーザーが決める立場か、提案する立場かを先に確かめる。
    決める立場なら原則をそのまま使う。提案する立場なら「決める人が判断しやすい材料になっているか」に置き換える。
    レビューでは、成果物の決定をユーザーが決めた前提で「誰が決めたかが書かれているか」を問う形にする

## 6. フック（`hooks/principle-review.py`）

PreToolUse の `Bash` で動く。

1. コマンドが `git commit` でなければ、何もせずに通す。コミットの判定とコミット先のディレクトリの解決（`cd`・`-C`）は、
   `hooks/guard-dangerous-bash.py` の `is_git_commit` と `git_target_dirs` を再利用する。
   ADR 0025 が挙げたコミットの見分けの取りこぼし（`bash -c` などで包んだ形）は、guard フックと同じ範囲で残る
2. コミット先のディレクトリで、ステージ済みのファイルを `git diff --cached --name-only` で取る。
   コマンドに `-a` か `--all` があれば、変更された追跡ファイル（`git diff --name-only`）も含める
3. 対象の場所に当たるファイルを節目に分ける
   - `spec`: `docs/superpowers/specs/`、`docs/specs/`、`docs/adr/` の下の `.md`
   - `plan`: `docs/superpowers/plans/`、`docs/plans/` の下の `.md`
   - 削除されたファイルは対象にしない
4. 対象が無ければ通す
5. まだ止めていない（セッションID, ファイルのパス）の組があれば、その組を記録して止める（`permissionDecision: deny`）。
   理由には次を書く
   - `principle-reviewer` を起動し、ファイルのパスと節目だけを渡すこと。会話の要約は渡さない
   - 返ってきた問いを要約せずにユーザーへ出すこと
   - レビューが終わったらコミットし直してよいこと
6. すべての組が記録済みなら通す。そのとき、止めた後に `principle-reviewer` が起動したかを会話記録で確かめ、
   起動していなければ `systemMessage` で画面に表示する

「1回だけ」の単位は、セッションとファイルの絶対パスの組にする。内容のハッシュは使わない。
問いを受けて直すたびに再レビューされると、直してもまた止まる繰り返しになるため。
絶対パスで記録するので、リポジトリXで止めた後のリポジトリYのコミットを2回目として通す取り違え（ADR 0025 の背景）は起きない。

ADR 0025 は日本語レビューの時点をコミットからPR作成へ移したが、このフックはコミットに置く。
仕様書はbrainstormingの中でコミットされ、その直後にユーザーが読む。PR作成は実装の後なので、仕様書を読む前のレビューに間に合わない。

状態はセッションごとにファイルへ保存する。置き場所と保持期間は、`hooks/jp-doc-review.py` の作り（7日で消す、セッションIDを安全な名前にする、ロックを取る）に合わせる。

### 6.1 エラー処理

検査できなかったときは、問題ありとして扱う。黙って通さない。

| 起きたこと | 振る舞い |
|---|---|
| 入力のJSONを読めない、`session_id` が無い | 「1回だけ」を記録できないので、止めずに「原則レビューを検査できなかった」と表示して通す。止めると毎回止まり続け、フックごと外される恐れがあるため |
| `git` が失敗した（リポジトリ外を含む） | リポジトリ外なら通す。それ以外の失敗は、1回止めて理由を表示する |
| 原則集のコピーを読めない | 1回止めて「原則集を読めない」と表示する。2回目は表示つきで通す |
| 会話記録を読めない（6の確認） | 通したうえで「レビュワーの起動を確かめられなかった」と表示する |

## 7. レビュワー（`agents/principle-reviewer.md`）

- 使える道具は Read・Grep だけにする。成果物を直さない
- 手順
  1. 原則集のコピーを読み、`checkpoints` に渡された節目を含む原則を選ぶ（現時点で spec 11件、plan 5件）
  2. スキルの「読み替えの規則」の節を読む
  3. 成果物を読み、各原則の `review_question` で照らす。`not_applicable` に当たる場面なら、その原則は使わない
- 返す形
  - 気になった原則ごとに、原則ID、問い、成果物の該当箇所（見出しか行）、気になった理由を1文。最大5件で、重い順に並べる
  - 問いの前に「会話で決着済みなら、成果物に経緯を足すだけで済む」と1行添える
  - 気になる点が無かったときも「問題なし」だけで終えない。照らし合わせた原則のIDを並べる

## 8. テスト

- 書き出し（`sakurai-transcripts`、TDD）: candidate と rejected を落とす。`basis` などの公開しない欄を落とす。
  テーマ名と使い分けの注記が付く。同じ入力から同じ出力を出す。`--check` が差を検出する。`--dest` が無いと失敗する
- フック（このリポジトリの `tests/`、TDD）: 対象の場所の判定（spec・plan・対象外・削除）、`-a` の扱い、
  （セッション, パス）の組で1回だけ止めること、止めるときの理由の中身、6.1の各行、2回目の通過とレビュワー未起動の表示
- 原則集のコピー（このリポジトリの `tests/`）: 必須の欄がそろっている。公開しない欄が無い。`review_question` が spec・plan の原則にある。
  `sakurai-transcripts` が無い環境でも走る
- スキルとレビュワー: 単体テストにできないので、`superpowers:writing-skills` の手順で実際のプロンプトを使って確かめる。
  助言は、発火すべき相談2つ、発火すべきでない技術相談1つで確かめる。レビューは、この仕様書自体を節目の対象にして、問いが出ることを確かめる
