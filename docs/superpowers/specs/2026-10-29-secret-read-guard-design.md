# secret を含むファイルの読み取りを止める

## 背景

2026-10-29の失敗調査で、AIが secret を2回出力していたと分かった。`~/.codex/config.toml` と `~/.zshrc.local` を読んだときで、
どちらも値を伏せる正規表現が一致せず、値がそのまま出た。effort を high にした後の出来事なので、考える深さでは防げない。

`~/.claude/settings.json` の `permissions.deny` には、すでに20件の Read 拒否がある（`~/.ssh/**`、`~/.aws/credentials`、
`~/.npmrc`、`.env` 系など。正本は `settings.json.template`）。漏れた2つのファイルは、この一覧に無かった。

調べた結果（中身は表示せず、パス・名前・権限・キー名だけを見た）:

- secret は `~/.config` 配下やホーム直下のドットディレクトリに散らばっている。値だけを書いたファイル
  （`~/.config/cw-workspace-local/asana-access-token` など）もあり、中身のパターンでは検出できない
- `~/.claude/settings.json` の `env` に `ANTHROPIC_AUTH_TOKEN` がある。このファイルは設定作業で頻繁に読む
- 権限が本人だけ（600/400）のファイルには secret が多い。ただし `~/.claude/settings.json`、会話記録（`~/.claude/projects/**/*.jsonl`）、
  `~/.claude/paste-cache/*`、lockファイルなども600である
- `~/.npmrc`、`~/.docker/config.json`、`~/.gitconfig.local` は644で、名前も規則に当たらない

一次ドキュメント（code.claude.com の permissions・sandboxing、2026-10-29取得）で確かめたこと:

- `Read(...)` の deny は、Read ツール、Bash の `cat` `head` `tail` `sed` `tee`、リダイレクトの対象に効く。
  ファイル名を書かずに読む `grep -r pattern .` や、Python などのスクリプトが自分で開く場合には効かない
- パターンは gitignore 形式で、`~/` 起点と `**` が使える
- sandbox は OS のレベルで止められる。ただし SSH での git push、Go 製 CLI の TLS 検証が失敗するなど影響が大きい

## 目的

AIがうっかり secret のファイルを読んで値を出力する事故を、置き場所が増えても一覧の追加なしで止める。
目的3（構造を見る）と目的4（fail-close）が衝突したときは、目的4を優先する。

1. AIのツール呼び出し（Read ツールと Bash）で、secret を含むファイルの中身が出力に出る経路を止める
2. secret の置き場所が増えても、規約どおりの名前・権限なら、一覧を足さずに対象に入る
3. 作業で中身の構造が要るファイルは、値を出さずに構造だけ見られる
4. 判定できないときは止める側に倒す（fail-close）

## やらないこと

- 出力側の伏せ字。値の形で検出する方式は、外れると値がそのまま出る（今回の漏えいの型）。1〜3の後でも漏れる経路が見つかったら検討する
- sandbox の有効化
- secret をファイルから別の保管先（Keychain など）へ移すこと
- 悪意のあるエージェントへの防御。対象は、うっかり読んで出力してしまう事故である。`python3 -c "open(...)"` のように
  意図して回り込む経路は、完全には塞がない（下の「既知の穴」に書く）
- Codex CLI。利用者は今Codexを使っていない（2026-10-29）。`guard-dangerous-bash.py` はCodexとも共有しているので、
  層2をそこに足す場合も、Codexでの振る舞いは変えない。Codexへ広げる件はbacklogに積む
- AIに secret のファイルを編集させる経路。必要なときは利用者が手で直すか、その場だけ許可する

## 構成

### 層1: 既存の `permissions.deny` を広げる（`settings.json.template`）

標準の仕組みで止められるものは、自作のフックより先にここで止める。

- 漏れていた場所を足す: `~/.zshrc.local`、`~/.codex/` と `~/.codex-personal/` の `config.toml`・`auth.json`・
  バックアップ（`config.toml.*`、`*.bak`）・`history.jsonl`、`~/.config/cw-workspace-local/**`、
  `~/.config/github-copilot/**`、`~/.gnupg/**`、`~/.gitconfig.local`、`~/.claude/.credentials.json`、
  `~/.claude/settings.json`、`~/.claude/settings.*.json`
- 名前の規則で書いたパターンを足す: `*token*`、`*secret*`、`*credential*`、`*.pem`、`*.key`、`auth.json` など。
  適用範囲は `~/.config/**` とホーム直下のドットディレクトリに限る。リポジトリ配下のソースコード（`token.go` など）を止めないため

### 層2: フックで標準の隙間を埋める（`hooks/` に新設）

`guard-dangerous-bash.py` には足さず、別のフックにする。登録するのは `settings.json.template` だけで、`codex/hooks.json` には登録しない。
こうすると、Codexでの振る舞いが変わらないことを配線で保証できる。

PreToolUse で Read・Grep・Bash を検査する（AIが提案し、利用者が2026-10-29に承認: Grep ツールの content モードも中身を出すため）。
判定の前に、パスを symlink の実体へ解決する。`~/.claude/rules` や `~/.claude/skills` はこのリポジトリへの symlink なので、
解決すると対象範囲から外れ、設定作業の Grep や Read は止まらない。

- 対象範囲: `~/.config/**` とホーム直下のドットディレクトリ（`~/.*` とその配下）。層1と同じ範囲にそろえる
  （AIが提案し、利用者が2026-10-29に承認: ホーム全体にすると、学習store などリポジトリ配下の600ファイル（`~/garage` 配下に169件）が止まる）
- Read・Grep ツール: 対象が対象範囲の通常ファイルで、グループと他者の権限が無い（`mode & 0o077 == 0`）なら止める。
  Grep はディレクトリを指定されたとき、対象範囲に向いていれば止める
- Bash: 引数に現れるパスを同じ基準で判定する。`grep -r` などの再帰走査が `~/.config`、ホーム直下のドットディレクトリ、
  ホームそのものに向くときも止める
- Bash で、引数が対象範囲を指すときだけ判定する。そのうち中身を出さないコマンド（`ls`、`stat`、`test`、`[`、`-exec` を伴わない `find`）は通す。
  許可リストで書き、載っていないコマンドは、引数が対象範囲を指す場合に止める
  （AIが提案し、利用者が2026-10-29に承認: 存在や権限の確認は作業で頻繁に要り、中身は出ない）
- `cp`・`mv`・`rsync`・`ln` の複製元が判定に当たるときも止める（AIが提案し、利用者が2026-10-29に承認: 対象範囲の外へ複製してから読む経路を塞ぐ）
- 判定できないとき（パスを解決できない、stat が失敗する）は、対象が対象範囲に見える場合に止める
- 例外: 会話記録・`paste-cache`・`plans` など Claude Code 自身が作る600のファイルのうち、作業で読むもの。
  例外は場所で書く（権限で例外を作ると、例外が広がる）

### 層3: 値を出さずに構造を見る読み口（`bin/` に新設）

- 対象: `~/.claude/settings.json`、`~/.codex*/config.toml`、`~/.claude.json` など、作業で構造が要るファイル
- 出すもの: キーの階層と型。値は、許可したキー（`model`、`theme`、`permissions` など、値の種類が決まっていて secret を書く場所ではないもの）
  だけを出す。それ以外の値はすべて伏せる。伏せ方は値の形を見ない（許可したキー以外は全部伏せる）
- `hooks` は許可しない。コマンド文字列にトークンを直書きする書き方がありうるため。フックの中身は、リポジトリの `settings.json.template` で読む
- スクリプトとして動くので、層1の deny は効かない。層2のフックはこの読み口を通す

## 既知の穴（この設計では塞がない）

- 名前も権限も規約から外れたファイル（644で名前が普通のもの）。見つけたら層1の一覧に足す
- スクリプトが自分でファイルを開く経路（`python3 -c`、`node -e` など）。層2で、引数に secret の置き場所が現れたら止めるが、
  変数や生成したパスを使われると見えない
- MCPサーバのファイル読み取りツール（serena など）。層2の対象に入れない（AIが提案し、利用者が2026-10-29に承認: ツールごとに入力の形が違う。今は serena の接続が失敗している）
- 一度出力された値は、会話記録に残る。過去に出た2件の値をローテーションするかは、利用者が判断する

## 検証

- 層1: Read ツールと `cat` で、足した場所が拒否されることを実機で確かめる
- 層2: フックの判定を単体テストで固定する（600のファイル、644のファイル、例外の場所、解決できないパス、`grep -r ~/.config`）
- 層3: 許可していないキーの値が出ないことをテストで固定する。値の形に関係なく伏せることを、
  secret らしくない値（普通の文字列）でも確かめる
- security boundary（secrets）に当たるので、完了前に security-reviewer の意味レビューを受ける

## 作り手に任せること

- 層1の具体的なパターンの書き方と、ホーム直下のドットディレクトリの表し方
- Bash の引数の解析に、`guard-dangerous-bash.py` の既存の実装を流用するか（流用するなら共通モジュールへ切り出す）
- 層3のコマンド名、出力形式、許可するキーの初期一覧
