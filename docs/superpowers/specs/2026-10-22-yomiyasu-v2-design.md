# yomiyasu v2への更新と、日本語レビューの報告の見直し

## 目的

主目的は、yomiyasuのsubmoduleを v1.0.1+1（`b14ee43`）から v2.1.2（`9fabae2`）へ上げ、日本語文書レビュー
（ADR 0024・0025・0032）を壊さずに使い続けることである。上げないと困ることは無いが、最新に追従したほうが推敲の質が
上がっているはず、とユーザーが判断した（2026-10-22、submoduleなどの更新の洗い出しから始まった）。

v2に破壊的変更があり、レビュワーの手順と報告を直すことになった。そこで、レビューで直した内容をユーザーが少ない手間で
確かめられるようにすることも、目的に加えた。

日本語レビューは、楽に伝わる文章にするための道具で、ユーザーの作業の本質ではない（ユーザーの言葉）。
確かめる手間が増える変更は、目的に反する。

## 背景

### v2で壊れること

上流はv2でリポジトリの構成を変えた。

- ルートの `SKILL.md` が無くなり、スキル本体は `skills/yomiyasu/` の下（`SKILL.md`、`references/`、`scripts/`）だけになった
- `references/` の必読資料（`gemini-syntax.md`、`slop-catalog.md`、`domains/*.md`）は、`skills/yomiyasu/references/` にもある

今の配布は `setup.sh` が `skills/yomiyasu`（submoduleのルート）を `~/.claude/skills/yomiyasu` と
`~/.agents/skills/yomiyasu` にリンクしている。このままv2へ上げると、次が起きる。

- `hooks/jp-doc-review.py` は `~/.claude/skills/yomiyasu/SKILL.md` が無いとレビューを**省略して先へ進む**（同ファイル651行付近）
- `hooks/jp-doc-lint.py` は同じ `SKILL.md` を起点にリンターを探す
- `agents/jp-doc-reviewer.md` は `~/.claude/skills/yomiyasu/` の `SKILL.md` と `references/` を読む

### 直した内容が見にくい

`agents/jp-doc-reviewer.md` の「報告」節は、メインのエージェントへ返すものを「変えた点（短く）」に限り、
書き直した本文を返さないと決めている。ユーザーが見ているのは、エージェントがこのセッションに書いた文字だけである
（ユーザーの言葉）。元の文と直した文を並べる材料が無いので、何をどう直したかが追いにくかった。

### スキル一覧の重複（backlog P3）

v1のsubmoduleには、ルートの `SKILL.md` と、複製の `skills/yomiyasu/SKILL.md` がある。
スキル一覧に `yomiyasu` と `yomiyasu:yomiyasu` が両方出ている。入れ子の `SKILL.md` が名前空間付きで
読み込まれているためだと推測しているが、確かめていない。

## 目標

1. v2.1.2で、Claude Codeの日本語レビュー（コミット時・PR作成時・Confluence投稿時）が今と同じように動く
2. レビュー後の報告に、**意味が変わりやすい直しなど、重要なものだけ**を `元の表現 → 直した表現` の対で出す。
   選ぶのはレビュー全体（複数ファイルにまたがっても）からで、件数の上限は設けない（ユーザーの判断）。
   今後どれだけ直しが出るかは予想できないので、上限を決めずに始め、「1回の報告で対が10組を超えたら上限を決め直す」
   という条件をbacklogに残す（ユーザーの判断）。「重要なものだけを選ぶ」ことで、確かめる手間を抑える。
   重要な直しが無ければ、そう1行で書く。メインのエージェントは、対を要約せずにユーザーへ見せる
3. 直した理由は、短く添えられるなら添える（ユーザーの言葉では「付けばうれしいが必須ではない」）
4. スキル一覧の `yomiyasu` が1つになる
5. Codex側（`~/.agents/skills/yomiyasu`）でも、スキルとして読める状態を保つ

## やらないこと

- 直した箇所をすべて並べること。件数が多いと確かめる手間が増える（ユーザーの言葉）
- Codexで日本語レビューのフックを動かすこと（backlog P2のまま）
- yomiyasuの任意のフック `scripts/yomiyasu_hook.py` を登録すること。このリポジトリのフックと役割が重なる
- 仕事の原則のレビュー（principle-reviewer）の報告の見直し。別件としてbacklogに積む

## 失敗とみなすこと

- レビューが黙って省略される状態が残る（動いているように見えて動いていない）
- 確かめる手間や、レビュー1回の待ち時間が目に見えて増える（推測。ユーザーの「楽に」から）
- レビュワーが実行できるコマンドの範囲が、必要以上に広がる（ADR 0024の決定9）

## 決まっていること

- 報告の対の形は、v2の出力フォーマットの「変えたところ」欄（`元の表現 → 書き直し後の表現（変更理由）`）に合わせる。
  ただし、v2の「最大5点」は使わず、上の目標2のとおり上限を設けない
- このリポジトリでの作業場所は本体（`skills/yomiyasu`、`hooks/`、`agents/` は動作中の設定に効くパス）
- このリポジトリを入れているPCはほかにもあるが、長く更新していないので、移行の手順はこのMacの分だけ用意する（ユーザーの判断）。
  ほかのPCが後で追いつくときのために、READMEに移行の手順を1か所書いておく
- メインの会話で名前を出さずにyomiyasuを自動で動かす使い方はしていない（ユーザーの言葉。フックかスキルから呼んでいる）。
  v2.0.2の「名前を出して頼んだときだけ動く」変更への対応は、範囲の外とする

### 配布の形（B案。ユーザーの判断）

スキル本体が入れ子の `skills/yomiyasu/skills/yomiyasu/` になったので、`~/.claude/skills/yomiyasu` がそこを指すようにする。
agent-toolkit-for-aws と同じ形（ADR 0035）にする。submoduleを `skills/` の外へ移し（例: `vendor/yomiyasu`）、
`skills/yomiyasu` を入れ子のディレクトリへのsymlinkにする。`setup.sh` と `manifests/skills.json` は変えずに済む見込み。

却下したA案は、`setup.sh` でyomiyasuだけリンク元を入れ子のディレクトリに変える形。submoduleを動かさずに済むが、
`skills/yomiyasu` の中身と実際に配る中身が食い違ったまま残り、`setup.sh` のClaude側とCodex側の両方に例外が入る。
上流がまた構成を変えたときも、B案ならsymlinkを張り替えるだけで済む。

本体で移すので、移している間は、動いているセッションから一瞬スキルが見えなくなる。

`manifests/skill-required-reads.json` の `root` と `alternateRoots`、`hooks/jp-doc-lint.py` の
`LINTER_RELATIVE_PATHS`、READMEの更新手順を、新しい形に合わせる。上流v2のルートにも `scripts/yomiyasu_lint.py` と
`references/` が残っているので、古い候補のパスでもリンターが見つかってしまう。スキル本体とは別の版を黙って使わないよう、
不要になった候補は消す。リンク先が入れ子の1つだけになれば、
重複（目標4）も消える見込みである。消えなければ原因を調べ、上流に報告するかを決めてbacklogに残す。

### v2の検査スクリプトを、記録を残さずに使う（ユーザーの判断）

v2は、書き直した最終稿を別のファイルに保存し、`scripts/yomiyasu_check.py run --source 原文 --final 最終稿` で
lintと原文・最終稿の差分検査をまとめて実行し、`verify` で提出物を照合する流れになっている。

レビュワーは `run` を `--no-record` 付きで使う。差分の検査で、意味がずれた直し（文の種類、許可・能力・保証の言い方、
足した語・消えた語）を機械が候補として挙げ、報告の対を選ぶ根拠にする。

- `--no-record` なので、作業repoの `.yomiyasu/` に原文と最終稿の全文の写しは残らない。業務repoに全文の写しを溜めたくない（ユーザーの判断）
- `verify` は使わない。`verify` は、提出物が `run` で検査した最終稿と1文字も違わないかを、記録のハッシュで照合するだけで、
  意味が保たれているかは見ない。記録が無いと動かない。代わりに、レビュワーの手順を「検査を最後にして、その後はEditしない」にする。
  v2の `SKILL.md` にも、`--no-record` で実行したら `verify` は実行せず、実行しなかった検査として報告すると書いてある
- レビュワーのBashの許可は、リンターに加えて、`yomiyasu_check.py run --no-record` の決まった引数の形だけに広げる。
  `verify` などほかのサブコマンドは許可しない（ADR 0024の決定9）

却下した案:
- 作業repoに記録を残す: 業務repoのディスクに全文の写しが溜まる
- 記録を作業repoの外の一時フォルダに残し、レビューの終わりにフックで消す: `verify` は使えるが、守れるものが小さい割にフックの手間が増える
- 検査スクリプトを使わず、リンターだけを呼ぶ: 意味がずれた直しを機械で拾えない

レビュワーは元のファイルをその場で直すので、`--source` に渡す原文の写しが要る。写しの作り方と置き場（例: 依頼の時点でフックが
一時フォルダに写し、レビューが終わったら消す）は作り手が決める。業務repoの中には置かない。

決めた理由と却下した案は、ADRに書く。

## 作り手に任せること

### レビュワーの手順

`agents/jp-doc-reviewer.md` と、Codex用に同じ手順を写した `codex/agents/jp-doc-reviewer.toml` の手順と報告を、
v2の `SKILL.md` に合わせて直す。少なくとも次を確かめる。

- 必読資料のパスがv2でも同じか（`references/gemini-syntax.md` などは残っている。v2で増えた `references/doc-types/`、
  `review-points.md` などを必読にするかは、作り手が決める）
- v2の「対話リライト時の出力フォーマット」はユーザー向けで、全文を返す。レビュワーはファイルをその場で直すので、
  本文は返さず、「変えたところ」の形だけを使う
- v2.0.2で「名前を出して頼んだときだけ動く」ようになった。レビュワーは `SKILL.md` を明示的に読むので影響は無いはずだが、確かめる

### メインのエージェントへの指示

レビュワーの報告を受け取ったメインのエージェントが、対をそのままユーザーに見せるようにする。
フックが止めるときの理由（`hooks/jp-doc-review.py` の文言）に書くか、レビュワーの報告の冒頭に書くかは作り手が決める。

## 確かめ方

待ち時間の判断（設計者の判断）: v1のうちに、同じ日本語の文書でレビューを1回起こし、所要時間を記録しておく。
v2で同じ文書をもう1回レビューして比べる。2倍を超えたら「目に見えて増えた」とみなし、検査スクリプトや必読資料の足し方を見直す。
1回ずつの比較なのでばらつきは消せない。目安として扱う。

- 既存のテスト（`tests/test_jp_doc_review_hook.py`、`test_jp_doc_lint.py`、`test_jp_doc_review_wiring.py`、`test_setup_*.py`）が通る
- `~/.claude/skills/yomiyasu/SKILL.md` がv2の本体を指し、`jp-doc-lint.py` がv2のリンターで検査できる
- 実機で1回、日本語の文書をコミットしてレビューを起こし、報告に `元 → 後` の対が出ることを見る
- そのレビューの後、作業repoに `.yomiyasu/` も原文の写しも残っていない
- 新しいセッションのスキル一覧で、`yomiyasu` が1つだけになっている
- `~/.agents/skills/yomiyasu/SKILL.md` が読める
