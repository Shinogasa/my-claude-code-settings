# mainに誤って積まれたコミットの回収判断

保護ブランチ (main) への直接コミットをブロックするフックに、ヒアドキュメントの
ネストと行継続 (`\` + 改行) でトークン化が壊れ検査全体が素通りするバグがあった。
修正の過程で、フック自身のバグにより main へ直接コミットが2回素通りしてしまった。

### 判断点: 誤って積まれた2コミットをどう回収するか

- A) 新規ブランチへ全コミットを逃がし、ローカル main を origin/main へ巻き戻す
- B) 3コミットとも main に残し、追加修正だけ別ブランチで作業する

**予測:** A を選ぶ。理由は、main と origin の乖離を放置すると、次に main で
作業するときに事故の痕跡が紛れ込む・見落とすリスクがあるため。

**実際:** A を選んで実行したところ、ブランチへ切り出した後に想定外の作業が
発生した。回収対象のコミット履歴の中に、フックのブロックに阻まれて実際には
実行されなかった「検証用の空コミット」が1件混ざっていた
(`git reset --hard` を試みてブロックされ、その後 `--allow-empty` の
再現テストもブロックされた一方で、その前に作った無意味な検証コミット自体は
既にリポジトリに残っていた)。この不要なコミットを取り除くため、
`git rebase --onto` (非対話的 rebase) を追加で行う必要が生じた。

### 欠けた軸: 前提の検証

方針 A は「回収対象のブランチに積まれているのは全部正当なコミットである」
という前提の上に成り立っていた。この前提を、選択の時点で `git log` で
実コミット一覧を確認して検証してはいなかった。結果的に致命的な問題には
ならなかった (rebase で解決できる範囲だった) が、対象を確認せずに
「移す」という操作を選んだ点は変わらない。

**次に同種の判断で確認する問い**: 複数コミットをブランチへ回収する・
移す判断をするときは、対象コミットの一覧を選択肢提示の前に出す。
「何を移すか」を確認してから「どう移すか」を選ぶ順序にする。
