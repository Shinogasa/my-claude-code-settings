# 影響範囲を数えずに適用を決める

## 判断点

設定配布スクリプトの方式変更を、実環境へいつ適用するか。
作業中ブランチにはレビュー未完了の変更が残っている。

- A) 今、このブランチのまま両ホストへ適用する
- B) マージしてから適用する
- C) 片方のホストだけ先に適用し、もう片方は後にする

## 予測

A) 今、このブランチのまま両ホストへ適用

**判断基準（原文）**: 影響小さいなら問題ないと思った

## 実際

適用に到達する前に、見積もり外の経路で障害が起きた。

配布スクリプトが管理する対象を数えていなかった。認証情報が5箇所に複製されており、
スクリプトが触れるのはそのうち2箇所だけだった。残り3箇所は手で保守する領域にあり、
「スクリプトを通せば揃う」という前提が成立していなかった。

## 差分

部分一致。結論そのものは成立しうるが、前提が未検証だった。

「スクリプトで上書きすればよい」と述べたが、問題の設定ファイルは
スクリプトの管理対象外だった。管理対象は8項目に限定されており、
対象一覧を読めば実行前に分かる情報だった。

## 評価: 前提の検証

「影響小さいなら」と条件節を置いたのは、前提の自覚としては正しい。
ただし条件を確認せずに実行の判断へ渡した時点で、その条件は
「そうであってほしい」に変わっている。

**条件節は、検証を省く言い回しとしても機能してしまう。**
「〜なら問題ない」は、前提を明示しているように見えて、
その前提を確かめる責任を先送りする形にもなる。

## 過去の判断原則との接続

同日の1件目（`2026-08-26-配布先の所有権を実体一致で判定してよいか.md`）の末尾:

> 「現状で問題ない」と言う前に、「この判断が誤りだと後で分かるのは、
> どんな出来事が起きたときか」を1つ挙げる。

同一セッション内で、30分後の判断に呼び出せていない。
原則が文脈をまたがない現象が、日をまたがずに再現した。

## 概念

**爆発半径（blast radius）** — 変更が失敗したときに影響が及ぶ範囲。
適用前に数え上げて確定させる対象であって、「小さいと思う」は範囲ではなく感想。
数えられないなら「未確認」と言う方が、小さいと言うより情報量が多い。

## 定石

**設定値が複数箇所に複製されている系では、変更前に「同じ値が何箇所にあるか」を数える。**

```bash
# 値そのものを出さずに、複製箇所だけを数える
python3 -c "
import hashlib
def fp(s): return hashlib.sha256(s.encode()).hexdigest()[:8]
# 各設定ファイルから該当値を読み、指紋で突き合わせる
"
```

数えずに1箇所だけ直すと、残りが古いまま部分的に動く状態になり、
全断より切り分けが難しい形で壊れる。

## 学習領域

前提の検証が抜けていた → 「影響小さい」の対象を数えていなかった。
実際には設定ファイルが管理対象外で、同じ値が5箇所に散っていた。

**次に同種の判断で確認する問い**: 「影響が小さい」と言うときは、
小さいと言える対象を数え上げてから言う。数えられないなら「未確認」と言う。

## 付随して得た教訓（測定の判別可能性）

同一性の照合をハッシュ比較で行ったが、この測定は
「別の有効な値」と「壊れた値」を区別できなかった。両者とも「不一致」を出す。

実際には片方が他方の部分文字列（末尾1文字が欠落）だった。
検出できたのは、別目的で入れた「置換先の値が既に出現していないか」という
安全装置が部分文字列マッチだったためで、設計の結果ではない。

**照合は一致/不一致の2値で終えず、不一致の内訳（部分文字列・長さ差）まで見る。**
