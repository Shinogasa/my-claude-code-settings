# コンテナ初期化の順序をどこで直すか

### 判断点: 起動時に張られるはずの symlink が張られていない。どこで直すか

開発コンテナで、設定ディレクトリを指す環境変数がホスト形式の絶対パスへ向けられており、
そのパスを実在させる symlink を起動フックが張る構成になっていた。
symlink が張られず、CLI が同じパスを**実ディレクトリとして新規作成**していたため、
本来読むはずの設定ファイル（認証情報を含む）が一切読まれない状態になっていた。

選択肢は3つ。

- A) 起動フックが既存の実ディレクトリを退けて張り直す
- B) ローカルフックをベース entrypoint より先に実行する
- C) イメージのビルド時に symlink を焼き込む

**予測:** B。

> 他の問だと実態をコンテナの中に入れたりするので変更に追従が遅くなる。
> 順番を変えるだけで解決するならコストが低そう

**実際:** レイヤーの選択は正しい。ただし「フックを先に実行する」を額面通り実装すると、
5本あるフックのうち4本が壊れる。実測した依存は次の通り。

- ファイアウォール追加設定 … ベース側が作る ipset の存在が前提
- SSH agent リレー … 同じくチェーン作成後が前提
- MCP 登録 … CLI を叩くので、まさに設定ディレクトリを作ってしまう側
- 警告メッセージの追記先 … ベース側が直後にシェル設定ファイルを `cat >` で作り直すため消える

正しい形は「フック単位の順序入れ替え」ではなく「1本のフックを工程で分割」すること。
symlink 作成だけを前へ、検証と警告追記は後ろに残す。

**差分（部分一致）:** 選んだ層は当たり。粒度が「フック単位」ではなく
「フック内の工程単位」だった。

### 欠けた軸: 失敗モード

「順番を変えるだけ」を選ぶとき、**その順番に依存している側がどう壊れるか**を
言えていない。しかも上記4本はいずれも失敗を `|| true` で握り潰す作りだったため、
壊れても出力に何も出ない。順序変更の副作用が、そのまま無音の欠落になる。

**次に同種の判断で確認する問い**: 実行順を前倒しする案を選ぶときは、
**「今の順序に依存しているものを1つ挙げる」を選択の前に済ませる。**
挙げられないなら、それは順序が偶然成立しているだけで、依存が見えていない。

### 概念

**暗黙の順序依存（implicit ordering dependency）** — 実行順に依存しているのに、
その依存がコード上に宣言されていない状態。順序を変えた瞬間に壊れるが、
依存が書かれていないため変更前には見えない。

### 付随して学んだこと: 「開けるか」は検査になっていない

このフックには検証が付いていて、`[ -d ] && [ -r ]` で「設定ディレクトリが開けるか」を
確かめ、通れば `ok` を出していた。だが CLI が作った空ディレクトリも `-d` かつ `-r` を
満たすため、**壊れている状態でも `ok` が出る**。仮説が真のときと偽のときで
同じ出力になる以上、これは測定ではない。

`readlink -f` の解決先が期待する実体と一致するかまで見て、初めて判別可能になる。
