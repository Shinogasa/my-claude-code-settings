# 応答途中で接続が切れる事象の切り分け方針

コンテナ内で作業していると、LLM クライアントが「応答途中で接続が失われた」と表示して
止まる。リトライのバックオフ待ちが入り作業が中断する。頻度が上がってきた、という報告。

環境: コンテナは iptables policy DROP + ipset 許可リスト方式のファイアウォールを持つ。
クライアントは設定ファイル経由で、直接のベンダー API ではなく**中間の LLM プロキシ**
（OpenAI/Anthropic 互換ゲートウェイ）を向いていた。

### 判断点: どの証拠を重く見て切り分けを始めるか

集まった証拠は互いに別のレイヤーを指していた。

- 短時間の接続確立はコンテナ・ホストともに 30/30 成功
- ファイアウォールは**起動時に一度だけ** DNS 解決して IP を許可リスト登録する方式（動的更新なし）
- conntrack 使用率・MTU・established timeout はいずれも正常範囲
- 過去ログにエラーが断続的に存在。発生日が直近に偏っている
- クライアントのバージョンはコンテナ・ホストで同一

**予測:** 「接続確立は成功しているのに応答中に切れる」という症状の性質を最優先する。
レイヤーを決め打ちせず、まず「誰が切っているのか」を特定してから対象を決める。
遠回りに見えるが誤爆が少ない、という判断基準。

**実際:** この方針が有効だった。既存ログから**切断までの経過時間の分布**を取ると、
23件が 180.0〜183.2 秒に集中していた。ばらつき3秒。
パケットロスや MTU 不整合ならこの集中は起こらないため、
**固定タイムアウト値を持つ中間装置**が切っていると特定できた。

さらに切断時の入力コンテキスト規模を見ると、全23件が 118k トークン以上（中央値 315k）。
小さなリクエストでは一度も起きていない。
「大きなコンテキストのリクエストが処理時間 180 秒を超え、プロキシ経路の固定タイムアウトに
達して切られる」という因果が閉じた。

対照的に、先にレイヤーを決め打ちしていた仮説（ファイアウォールの IP ローテーション漏れ）は
実測で否定された。宛先は固定 IP で許可リストにも入っていた。
方針を決め打ちしていれば、ここで時間を失っていた。

**差分（一致）:** 結論は予測どおり。ただし予測に含まれていなかった観点が1つある。

**対照群を取ること。** 失敗側だけを見ると「180 秒付近に集中している」までしか言えない。
「180 秒を超えたら必ず失敗する」を言うには、成功側の分布が必要だった。
成功 775 件の最大が 68.9 秒で、180 秒を超えて成功した例が 0 件——
この対照があって初めて「壁」の存在が証明できる。

しかも成功側は最初、測り方が汚染されていた。素朴に「直前のログ行との時間差」で測ると
人間の入力待ちやツール実行時間が混ざり、「180 秒超の成功が24件ある」という
偽の反証が出た。計測対象を「ツール結果を返した直後の呼び出し」に限定して初めて 0 件になった。
**対照群は、取るだけでなく交絡を除かないと結論を逆向きに壊す。**

### 欠けた軸: 失敗モード

選んだ方針が**どう壊れるか**が言語化されていなかった。

「症状の性質から入る」は、**症状に規則性があること**を暗黙の前提にしている。
今回は 180 秒という規則性が出たので機能した。もし分布がばらけていたら
（真のパケットロスや経路品質の劣化なら実際にばらける）、この方針は手がかりゼロで空振りし、
結局レイヤーごとの計測に戻る必要があった。空振りしたと判断する基準も決めていなかった。

**次に同種の判断で確認する問い**: 切り分け方針を選ぶときは、
「この方針が空振りするのはどんなデータが出たときか」を、着手前に1つ具体的に言う。
言えないなら、その方針は検証可能な形になっていない。
