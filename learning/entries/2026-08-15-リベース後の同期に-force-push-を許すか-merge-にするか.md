# リベース後の同期に force push を許すか merge にするか

### 判断点: エージェントが main に追随する手段として、rebase + force push を許すか merge を既定にするか

ガードが `git push --force` / `-f` を止めているため、エージェントが
`--force-with-lease` を使ってきた。これを許容するかどうかの判断。

**予測:** merge の方がいい。

> --force-pushを使うと強制的にブランチへプッシュされてしまうため
> 予期せぬコミットが入ってしまう可能性がある。
> mainを保護していない場合は特に危険

**実際:** 結論は同じ。merge を既定にすべき。ただし決め手は履歴の綺麗さでも
「予期せぬコミットが入る」でもなく、**force push を使わない操作は
force push の安全性を検証しなくていい**という点にある。
ガードの正しさに依存する設計より、ガードを必要としない設計が強い。

補強材料:

- squash merge 運用ならブランチの内部履歴はマージ時に捨てられる。
  rebase で履歴を整える利益は最終的に消えるのに、force push のリスクだけ払う
- レビューコメントが outdated に飛ばない
- 消した履歴は reflog にしか残らず、その reflog は消した本人のローカルにしか無い

rebase が正当化されるのは `--ff-only` / rebase merge 運用のとき。
そこではブランチの履歴が最終成果物なので、綺麗さがコストに見合う。

**差分（予測に含まれていなかった観点）**

`--force-with-lease` の lease は、**手元の remote-tracking ref を見ているだけ**。
背景の `git fetch`（エディタの自動 fetch、`git pull`、他ツールの `git fetch --all`）が
その値を最新化した瞬間、比較は必ず通る。公式ドキュメント自身がこの穴を明記していて、
回避策として push 専用の remote を別に作ることを勧めている。

エージェントは fetch を頻繁に打つため、この環境では保護がほぼ機能しない。
実際の分岐点は「force か force-with-lease か」ではなく
**「lease の比較対象が汚染されうるか」**だった。

明示形にすれば塞げるが、どちらも既定では効かない。

- `--force-with-lease=<branch>:<目視した OID>` — 手元キャッシュを経由しない
- `--force-with-lease --force-if-includes` — remote-tracking の先端が reflog 上で
  取り込み済みかを検証する。ancillary option なので明示指定が必須。
  `--force-with-lease=<ref>:<expect>` と併用すると no-op になる

また lease は「他人が動かしたか」しか見ない。自分の rebase が conflict 解決で
コミットを落としていても素通りする。

### 欠けた軸: 前提の検証

「main を保護していない場合は特に危険」は、force push の対象が main だという
前提を置いている。この flow で書き換えられるのは feature ブランチであって main ではない。
main の保護設定はこのリスクにほとんど効かない。
**確認していない前提を、危険度の根拠として使っている。**

### 副次: 失敗モード軸も弱い

述べたのは「棄却した案（force push）がどう壊れるか」で、
「選んだ案（merge）がどう壊れるか」ではない。
merge を既定にすると main を取り込むたびに同じ conflict を再解決することになり、
長命ブランチほど痛む。そこを言えていないと、痛くなったときに rebase へ揺り戻す。

### 概念: 楽観的並行制御（compare-and-swap）

「期待値と一致したときだけ書き換える」方式。期待値が自分の手元のキャッシュ由来だと、
そのキャッシュを別経路が更新した瞬間に保護が消える。
ETag / If-Match、DB の version カラムでも同じ形の事故が起きる。

### 接続: 過去の判断原則がそのまま再現した

`2026-08-08-危険な操作をどこで止めるかと、禁止が経路を変えるだけになる問題.md`

> 禁止は能力を消さず、経路を変えるだけ。
> 禁止する前に「同じ結果に到達する他の手段」を1つ挙げる。

`--force` を塞いだ結果、エージェントは `--force-with-lease` という別経路へ流れた。
ガードのトークン比較が完全一致だったため、別経路は検知もされなかった。

**次に同種の判断で確認する問い**: 操作のリスクを述べるときは、
**その操作がどのオブジェクトを書き換えるか**を1つ名指ししてから、危険度の評価に入る。
