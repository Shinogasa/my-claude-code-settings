## 判断点

構造体の状態を変更するメソッドを、レシーバをポインタにして呼び出し元を直接書き換える形にするか、
値レシーバのまま新しい値を返す形にするか。プロジェクトにはイミュータブル方針が文書化されていた。

## 予測

ポインタレシーバ。

**判断基準（原文）**: 「もともとの値を続けて使ったほうがTodoの値の管理の仕方として正しいとおもったから」

## 実際

値レシーバ + 新しい値を返す。

## 差分

### 反例: 「もともとの値を続けて使う」が成立していない

```go
func (u *Usecase) Complete(ctx context.Context, e *Entity) error {
	e.MarkDone()                                   // 元の状態を上書き
	if err := u.publisher.Publish(ctx, e); err != nil {
		// 元に戻したいが、変更前の状態はもう存在しない
		return err
	}
	return nil
}
```

ポインタレシーバが実現するのは「**同じ実体を指し続けること**」であって、
「変更前の値が残ること」ではない。上書きした瞬間に元の値は失われる。

判断基準の中で、2つの別々のものが1つの言葉に畳まれていた。

| | 何を保つか | 実現する方式 |
|---|---|---|
| 同一性の継続 | 同じ実体を指し続ける | ポインタレシーバ |
| 値の保存 | 変更前の値が失われない | 新しい値を返す |

欲しかったのは後者だが、選んだのは前者を実現する方式だった。
**言葉が指す対象が2つあるとき、どちらを意図しているかを言えないまま選ぶと、
選んだ方式が意図と逆の性質を持っていても気づけない。**

## 評価: 前提の検証軸

確認できる取り決めが2つとも手元にあった。

- コーディング規約に「既存オブジェクトを変更せず、新しいオブジェクトを作る」と明記されていた
- 該当箇所のコメントが「イミュータブル方針に沿うのはどちらか」と論点を名指ししていた

「正しいと思った」は推測である。参照可能な文書が存在し、しかもコメントがその所在を
指していたにもかかわらず、参照せずに直感で決めている。
推測と確認済みの事実が区別されていない。

## 過去の判断原則との接続

前提の検証軸が欠けた回はこれで9件目。過去の記録には同じ形が繰り返し現れている。

- 「導入する」を選ぶ前に、配布の有無を1つ確認してから決める
- 分類の基準を決めたら、その基準が成立する条件を1つ言う
- 誤作動リスクを理由に防御を弱めるときは、選ぶ前に頻度を1つ数字で置く

共通しているのは「**選ぶ前に、確認できる事実を1つ確認する**」。今回もそこが抜けた。

慢性的に同じ軸が欠けているということは、個別の知識不足ではなく
**判断の手順に確認ステップが組み込まれていない**ことを示す。

## 概念

**エイリアシング（aliasing）** — 複数の変数やスライス要素が同じ実体を指している状態。
片方を通じた変更が、それを知らない他方から見えてしまう。

## 学習領域

前提の検証軸が抜けていた → 今回、イミュータブル方針という文書化された制約が存在し、
コメントもその所在を名指ししていたのに参照しなかった。

**次に同種の判断で確認する問い**: 選択肢を選ぶ**前に**、
「この判断を縛る既存の取り決めが文書にあるか」を1回確認する。
「無い」と判断する場合も、どこを見て無いと言えるのかを言えるようにする。
