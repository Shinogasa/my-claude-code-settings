# 防御機構を PR に分ける判断と、シンボリックリンク経由の設定が持つ動的性


### 判断点: 実装済みの機能を既存 PR に統合するか、独立させるか

**予測:** 追跡性を優先し、既存 PR のタイトルとスコープを変更した上で統合する

**実際:** 同じ判断。統合する側の PR が扱う主題と中身が乖離すると、
後から「いつその防御を入れたか」を履歴から引けなくなる。改題が統合の前提条件になる。

**差分（予測に含まれていなかった観点）**

この種のフックは、設定ディレクトリから作業ツリーへの**シンボリックリンク**で動いている。
つまり**チェックアウト中のブランチが、今この瞬間のフックの中身を決めている**。

同じセッション中に実際に観測した。別の作業でブランチが切り替わった瞬間、
実装したはずの判定が手元から消えた。**マージされるまで、その防御は
「特定のブランチにいるときだけ有効」**という状態だった。

一般化: **設定の配線（静的）と、配線先の中身（git 管理下＝動的）は別物。**
「機構を入れた」と「機構が効いている」の間に、チェックアウト状態という
可変要素が挟まっている構成がある。

### 欠けた軸: 前提の検証

「フックは配線済みだから有効」という前提が、実は条件付きだった。
配線ファイル（settings 相当）は静的なので確認すれば済むが、
リンク先の実体は git の状態で変わるため、確認のタイミングごとに答えが違う。

**次に同種の判断で確認する問い**: 「入れたから安全」と言う前に、
**「今この瞬間、その実体は何を指しているか」を1回確認する。**
特にリンク・シンボリックリンク・キャッシュ・生成物を挟む構成では、
定義の存在を機能の有効性の証拠にしない。

### 副産物: 自分の防御に自分が守られなかった経路

この防御は「作業前にブランチを切り忘れる」ことを止めるために作った。
だが実装が未マージの間は、まさにその防御が必要な場面
（別ブランチで作業を始めるとき）で無効になっている。

一般化: **防御機構を導入する期間そのものが、その防御の空白期間になる。**
守る対象と、守る手段の配布経路が同じリポジトリにあるとき、この重なりが起きる。
導入中に事故らない保証は、機構ではなく運用側にしかない。
