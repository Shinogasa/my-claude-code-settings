# テストの網羅性を評価する基準の選び方

関連: [[2026-08-10-AI-が生成したテストケースを人間がレビューする位置]]

### 判断点: AI が生成したテスト群に「何が足りないか」を探すとき、何を基準に欠落を列挙するか

対象は、外部 API のレスポンスを型フィールドで分岐させるカスタムデシリアライザ。
実装の分岐は `if (type == "volume") A else B` の2本。
テストは3件（`volume` / 別の既知値 / フィールド欠落）。

**予測:** 「入力データの境界を基準にする」。
null・空文字・型違い・不正な識別子など、入力値そのものの異常パターンを列挙して探す。

**実際:** その基準で実際に欠落が出た。

- 型フィールドが object や配列だった場合 → プリミティブ取得で例外。未テスト
- 分岐先の必須フィールドが欠落した場合 → デシリアライズ例外。未テスト

しかも実装のコメントは「不明な値はフォールバックする」と後方互換を意図しているのに、
型が違う場合だけ例外で落ちる。**意図と挙動がずれている可能性**が浮上した。

対照的に、AI 側が推奨として提示した「実装の分岐を基準にする」は、
**このケースでは欠落をゼロ件と判定して終わる**。if も else も既にテストされており、
分岐カバレッジが 100% だったため。選択肢の推奨の置き方が誤っていた。

**差分（一致）:** 予測に含まれていなかった観点は「その基準はいつ探索を終えるのか」。

### 欠けた軸: トレードオフ

入力境界を基準に選んだとき、分岐基準が持っていた
**「分岐を尽くしたら終わり」という停止条件**を捨てている。
境界の列挙は原理的に無限で、型違い・必須フィールド欠落・不正な識別子・巨大文字列と
際限なく出せる。止め方を決めないと、次のどちらかになる。

- テストが肥大化し、メンテコストで TDD 自体が嫌われる
- 恣意的に打ち切り、「網羅した」という主張が根拠を失う

**次に同種の判断で確認する問い**:
網羅性の基準を選んだ直後に「この基準で探索が終わる条件」を1行で書く。
書けないなら、停止条件を持つ基準（分岐カバレッジ等）と併用し、
境界基準は「分岐では踏めない経路」に絞る。
