# 学習用Webアプリ: 並行処理の題材選定と、実装差し替え時の故障点

`#設計判断` `#レビュー力` `#並行処理` `#レイヤードアーキテクチャ`

### 判断点1: 素朴なCRUDアプリで並行処理を学ぶ題材をどう仕込むか

**予測:** 集約API（1リクエストで複数の集計を並行取得する）。

**実際:** 同じ。ただし単独では不十分と判断し、常駐ワーカーを扱う段を追加して2段構えにした。

**差分（予測に含まれていなかった観点）: リクエストスコープの並行処理では、並行処理のライフサイクル管理を学べない**

`errgroup` 系の並行処理は、リクエスト終了時に context キャンセルで必ず回収される。つまり**リーク**という実務で最も事故る現象を、構造上体験できない。停止しない定期実行、書き手のいないチャネルでブロックし続けるワーカー、シャットダウン時に処理途中で殺されるジョブ——これらは常駐型でしか再現しない。

一般化するとこうなる。**「その機構で起きうる失敗を、その題材で再現できるか」を学習設計の選定基準に置く。** 安全に成功する題材は、失敗の形を教えない。題材選定では「何が学べるか」だけでなく「何が学べないか」を明示的に潰す。

### 判断点2: 永続化層の実装を差し替えたとき、設計がまずいと最も危険な壊れ方をするのはどこか

**予測:** テストコード全体。モックの型や前提が崩れて大量に落ちる。

**実際:** 上位層（HTTPハンドラ）のエラー分岐。

#### 反例: テストが全て緑のまま、本番だけが壊れる

テストが大量に落ちるのは「壊れた」のではなく「安全網が作動した」状態である。CIが赤くなればマージされない。実は最も安全な失敗モードだった。

反例はこうなる。ハンドラが低レベルドライバ固有の「該当行なし」エラーで分岐していたとする。ORM実装に差し替えると、実際に返るのは別の型のエラーになる。ところが上位層のユニットテストは永続化層をモックしており、そのモックは**ドメイン層のエラーを返すよう書かれている**ため、テストは全て通る。

結果、コンパイル成功・テスト全緑・しかし「存在しないリソースの取得」が404ではなく500を返す。

対照的に、interface にドライバ固有のトランザクション型が漏れていた場合はコンパイルすら通らない。うるさく壊れるものは怖くない。

一般化: **危険さは被害の大きさではなく、気づけなさで決まる。** 故障モードを列挙するときは「何が壊れるか」ではなく「壊れたときに気づけるか」で優先順位をつける。

#### 予測が滑った経路: 「影響範囲の広さ」を危険度と取り違えた

「テストコード全体」という予測は、影響を受ける行数で危険度を測っている。だが行数は検知可能性と無関係であり、むしろ**広く壊れるほど気づきやすい**。危険度の評価軸は影響範囲ではなく、検知までの時間である。

この取り違えは実務のリスク評価でも起きる。「広範囲に影響する変更」を慎重に扱うのは正しいが、それは検知しやすい方であって、本当に警戒すべきは**局所的で静かに振る舞いだけが変わる変更**の側にある。
