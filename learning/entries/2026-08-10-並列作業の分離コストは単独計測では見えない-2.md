# 並列エージェントの分離機構をどの基準で選ぶか

複数のコーディングエージェントを同一リポジトリで並列に走らせるとブランチが衝突する。
git worktree で分離したいが、その機構を何に載せるか（規約 / 手順書 / フック）を決める場面。

### 判断点: 検出が原理的に不完全な状況で、何を優先して機構を決めるか

提示した選択肢は「検出に頼らない」「防止の確実性」「中断コスト」の3つ。

**予測:** 「検出に頼らない」に傾きつつ、いずれも選ばなかった。理由は
「些細な作業でも worktree を切ることになって開始までの時間が延びそう。そのリードタイムは
どの程度か。また worktree を切るとテスト実行やアプリ起動ができなくならないか」。
つまり **分離コストを実測してから基準を決める** という判断。

**実際:** 分離コストは2層に割れていた。

- worktree の作成自体は 0.05 秒未満。オブジェクトはコピーされず、追跡ファイルの展開だけなので
  リポジトリの履歴サイズにほぼ依存しない
- 重いのは追跡外の資産の再構築。サブモジュール、環境変数ファイル、依存パッケージ、
  ビルドキャッシュはいずれも新しい作業ツリーに来ない
- さらに再構築では直らない層がある。ポート、ローカルDB、コンテナ名といった
  **リポジトリ外の共有資源は worktree を切っても分離されない**

**差分（一致）:** 方向は妥当だった。予測に含まれていなかった観点は
**worktree はファイルシステムの分離であって実行環境の分離ではない** という境界。
「起動できなくなる」の主因は後者側にあり、これは worktree の採否と独立に
並列作業へ付いてくる制約である。

### 欠けた軸: なし（3軸とも充足）

- トレードオフ: 捨てるもの（開始までの時間）を明示している
- 失敗モード: 壊れ方（テスト実行・起動が通らない）を挙げている
- 前提の検証: 推測で確定させず、実測を要求している

**この判断基準が通用しなくなる条件**: 「測ってから決める」はコストが単独で測れることを
前提にしている。worktree の本命コストである実行環境の衝突は、2つ同時に動かした時にしか
現れない。単独計測では常に 0 と出るため、測ったこと自体が誤った安心になる。

**次に同種の判断で確認する問い**: コストを実測して判断するとき、
「その計測は、問題が起きる条件を再現できているか」を1つ確認する。
並列で起きる問題を単独で測っていないか。
