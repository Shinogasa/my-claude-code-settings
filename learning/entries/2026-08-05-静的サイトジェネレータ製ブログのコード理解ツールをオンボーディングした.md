# 静的サイトジェネレータ製ブログのコード理解ツールをオンボーディングした


### ★ Predict / ★ Delta

**問い**: このリポジトリを clone して開発サーバを起動したとき、最初に壊れるのはどこか。

**予測**: テーマが存在せずレイアウト解決が失敗する（テーマが git submodule のため）。→ **一致**

**実際**: 一致。submodule は未初期化で、テーマディレクトリは空だった。

**予測に含まれていなかった観点**: **ツールチェーン自体の不在**。
そのビルダのバイナリが PATH に無く、submodule より手前で落ちる状態だった。

### 一般化

「最初に壊れるのはどこか」を考えるとき、**リポジトリ内部の不整合を探しに行く癖**がある。
だが破綻の順序は実行の順序に従う。

```
実行系の到達順:
  [1] バイナリの存在        ← リポジトリの外
  [2] 外部から取得する依存   ← リポジトリが参照するだけで中身を持たない
  [3] リポジトリ内部の設定   ← ここばかり見てしまう
  [4] 実行時の外部通信       ← ビルドは通るが表示だけ壊れる
```

[1] と [2] は**リポジトリを読んでも見つからない**。ファイルの有無ではなく
「そのファイルが実在するか」を実行環境に問い合わせないと分からない層である。
リポジトリを丁寧に読む行為は [3] の解像度だけを上げ、[1] の盲点は埋めない。

### 副産物: 「ビルドは通るが表示が壊れる」層の存在

上図 [4] にあたるもの。外部リソースをビルド時に取得する仕組みが、
取得失敗時にエラーではなく**フォールバック文言を出力して正常終了**していた。
CI も終了コードも緑になる。この層は自動検証で捕まらないため、
「目視確認が必要な箇所」としてドキュメント化するしかない。

一般化: **フォールバックを持つ処理は、失敗を成功に変換する。**
可用性のための設計だが、同時に検証可能性を奪う。フォールバックを入れるときは
「失敗したことが後から分かるか」を併せて設計しないと、静かに壊れ続ける。
