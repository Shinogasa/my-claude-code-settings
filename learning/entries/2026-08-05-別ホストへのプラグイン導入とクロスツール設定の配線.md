# 別ホストへのプラグイン導入とクロスツール設定の配線


### 判断点: 拡張機構を持つツールに、hook を持たない拡張を入れたとき最初に壊れるのはどこか

**予測:** 既存のスキル群と名前が衝突する。

**実際:** 衝突は起きない。そして「起きない」ことの理由が問題の本体だった。

**差分（予測が破綻する反例）**

衝突が成立するには「両方が候補として比較される」前段が要る。その前段が無かった。

拡張が提供するスキルも、既存のスキルも、エージェントが自発的に一覧を参照して初めて
選択の土俵に上がる。参照を強制する仕組み（セッション開始時の自動注入）を持つホストと
持たないホストがあり、後者では**どちらも土俵に上がらない**。競合しないのは設計が
良いからではなく、どちらも呼ばれないからだった。

一般化: **「衝突しない」と「衝突できない」は観測結果が同じで、意味が正反対。**
前者は共存の成功、後者は機能の不在。名前空間の設計を検討する前に、
「そもそも両方が評価される経路があるか」を先に確認する。

### 実装中に自分で作り込んだ誤り: 「キーが無い」を「機構が無い」と読み替えた

設計時、拡張の manifest に hook 相当のキーが無いことを確認し、
「このホストには hook 機構が無い」と結論した。**誤り。**
機構は存在し、manifest のキーではなく**同階層の別ファイル**で定義する形式だった。
他の拡張が実際にその形式で hook を使っていた。

結論（配線が必要）は変わらなかったが、理由が過度に一般化されていた。

**なぜ起きたか**: `ls` と `grep` は「自分の探し方の範囲内に無い」ことしか証明しない。
それを「存在しない」に変えるには、探索空間そのものが正しいという別の根拠が要る。
私は探索空間の前提（hook は manifest のキーで定義される）を検証しないまま、
その内側だけを丁寧に走査して「無い」と結論した。

**防げたか**: 防げた。公式リポジトリの README の3段落目に、必須の manifest と並ぶ
optional な構成要素として当該ファイル名が明記されていた。しかも調査の過程で
そのリポジトリのファイル一覧は取得しており、README がそこにあることを見ていながら
開かずにファイル走査へ進んだ。既存ルール（Research & Reuse の
「GitHub code search first, library docs second」）の順序を守っていれば通らない経路だった。

一般化: **不在の主張には、探索空間の正しさの根拠を添える。**
根拠として最も安いのが一次ドキュメントで、走査より先に読むべきもの。
走査を丁寧にやるほど「調べ尽くした」感覚だけが強まり、前提の誤りが隠れる。
丁寧さは正しさの証明にならない。
