# force push の例外をどの属性で切るか

### 判断点: force 系を一律ブロックしたフックに、正当な用途（未マージ PR の自ブランチを amend して上書き）の逃がし方をどう作るか

**予測:** 保護ブランチ以外が対象なら通す。

> 保護ブランチいがいならロールバックがきいてあんぜんだから

**実際:** 同じ結論。対象 ref を解決し、`main` / `master` のときだけ止める形に変えた。

**差分（予測に含まれていなかった観点）**

「ロールバックがきく」が成立するのは、上書き前のコミットがどこかに残っている場合だけ。
残る場所は**上書きした本人のローカル reflog** であって、リモートには残らない
（unreachable になり、いずれ GC される）。

つまり効いているのは「保護ブランチか否か」ではなく
**「そのブランチに自分以外がコミットしていないか」**。
非保護でも、共同作業ブランチ・別マシンの自分・並列で動く別セッションが
push していれば、復旧経路は同じく無い。
保護状態は所有関係を保証しないので、**代理として不完全**。

もう1つ、判定が二値で終わらなかった。**対象 ref を特定できない形**が第三の状態として出た。

- refspec 省略（宛先が現在のブランチ依存。detached HEAD や git 管理外では解決できない）
- `--all` / `--mirror`（対象を1つに絞れない）

これを「非保護だから通す」に畳むと素通しになるため、ブロック側へ倒した。
`rules/proving-absence.md` の「検査できなかった を 問題なし に畳まない」がそのまま出た。

### 副産物: フラグを見ている限り経路は残る

実装中に `git push origin +main` が素通りすることを実測で確認した。
refspec 先頭の `+` は force update だが、フラグを一切使わないため
接頭辞判定（`--force*` / `-*f*`）を通り抜ける。

対象 ref を解決する設計に変えると、`+main` `refs/heads/main` `HEAD:main` 省略形が
すべて同じブランチ名へ畳まれるため、この穴は判定の副作用として閉じた。
**綴りの列挙をやめて、操作対象を正規化してから見る形にすると、綴りの分岐が消える。**

### 欠けた軸: 前提の検証

「ロールバックがきく」を根拠に据えたが、**復旧に使う保存先を確認していない**。
確認していれば「本人の手元にしか無い」＝他人が触ったブランチでは効かない、
という限界まで届いていた。

これで `axis: "前提の検証"` は3連続。同じ形で外している
（危険度・安全性を、確認していない性質を根拠に述べる）。

### 副次: 失敗モード軸

「安全だから通す」と述べたが、通した結果どう壊れるかが無い。
今回の実装で言えば、共同作業ブランチが対象のとき、フックは何も言わずに通す。

### 概念: 代理指標（プロキシ変数）

測りたい性質（復旧可能性）を直接測れないとき、観測しやすい別の属性
（ブランチが保護対象か）で代用すること。代理は本体とズレる条件を必ず持つので、
**「代理が外れるのはどんなときか」を1つ言えないうちは、代理を根拠にできない**。

### 接続: 過去の判断原則

`2026-08-15-リベース後の同期に-force-push-を許すか-merge-にするか.md`

> 操作のリスクを述べるときは、その操作がどのオブジェクトを書き換えるかを
> 1つ名指ししてから、危険度の評価に入る。

今回は「どの ref を書き換えるか」までは届いた（保護ブランチかどうかを見た）。
届かなかったのは**書き換えられた側がどこに退避されるか**。
オブジェクトの名指しは1歩前進していて、欠けたのはその次の段。

**次に同種の判断で確認する問い**: 「復旧できるから安全」と言うときは、
**復旧に使う保存先を1つ名指しし、それが自分の手元以外にも存在するか**を先に確認する。
