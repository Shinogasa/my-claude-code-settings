## 判断点

整数ベースの列挙型に文字列変換メソッドを生やしたとき、
どのケースにも当てはまらない値が来た場合に何を返すか。
コンパイラが「戻り値の無い経路がある」と指摘したため、埋める必要があった。

永続化層では既定値が定義済みで、新規作成時は未完了状態が入る。

## 予測

既定値（未完了状態）を返す。

**判断基準（原文）**: 「todoを新規作成したときって基本的に終わっていないタスク。
なのでデフォはpendingでいいと判断」

## 実際

この分岐は新規作成とは無関係。列挙値のどれにも一致しなかったときだけ通る経路であり、
到達した時点で既に何かが壊れている。

## 差分

### 反例: 列挙値を1つ足したとき

```
const (
    Pending Status = iota
    Done
    Archived        // ← 後から追加
)
```

変換メソッドに `Archived` のケースを足し忘れると、フォールバックが拾って
未完了状態の文字列を返す。アーカイブ済みのレコードが未完了として永続化される。

- コンパイラは何も言わない（フォールバックがあるので戻り値は必ずある）
- 静的解析も通る（実際に確認した）
- 新しい列挙値を通さないテストは緑のまま

「テストが緑で、本番だけ静かに壊れる」形になる。フォールバックを置いた瞬間、
ケース追加漏れを検出する最後の機会が消える。

## 評価: 前提の検証軸

「デフォルト」という1つの語が、2つの別々のものを指している。

| 語の意味 | 何を決めるか |
|---|---|
| 既定値 | 値を省略して作成したときに入る初期値 |
| フォールバック分岐 | どの分岐にも当てはまらない値が来たときの動作 |

前者についての判断は正しい。しかし今書いているのは後者である。
どちらを意図しているかを確認せずに、語感の一致だけで結論を移送している。

## 過去の判断原則との接続

同じ構造が値レシーバの回に記録されていた。

> 言葉が指す対象が2つあるとき、どちらを意図しているかを言えないまま選ぶと、
> 選んだ方式が意図と逆の性質を持っていても気づけない。

前回は「同一性の継続」と「値の保存」が1語に畳まれていた。今回は
「初期値」と「フォールバック」。**語が同じで指す対象が違う**という形が反復している。

前提の検証軸が欠けたのは16件目。

## 概念

**網羅性検査（exhaustiveness checking）** — 列挙型に対する分岐が、
取りうる値をすべて覆っているかを機械的に検査すること。
言語やツールがこれを持たない環境では、フォールバック分岐を置くと
「覆えていない」状態が正常系に見えるため、検査の余地そのものが無くなる。

## 学習領域

前提の検証軸が抜けていた → 今回「デフォルト」の語感で判断し、
その分岐に実際に入るのがどんな値かを確認していない。

**次に同種の判断で確認する問い**: 分岐のフォールバックを書くときは、
**「この分岐に入るのは、どんな値が来たときか」を1つ具体的に挙げてから中身を書く。**
挙げられないなら、その分岐が何のためにあるのか分かっていない。
