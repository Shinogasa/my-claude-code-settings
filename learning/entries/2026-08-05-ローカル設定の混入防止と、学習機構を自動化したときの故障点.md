# ローカル設定の混入防止と、学習機構を自動化したときの故障点


`#レビュー力` `#故障モード` `#防御の層` `#可観測性`

### 判断点1: ローカル設定ファイルの持ち込みを、コミット時のパターン検査は止められるか

**予測:** 絶対パスを含むファイルは止まるが、もう一方（構造的パターンに該当しないファイル）は素通しする。

**実際:** 同じ。絶対パスの規則1本で13件検出しブロック、もう一方は検出0件だった。

**差分（予測に含まれていなかった観点）: 止まった理由は「秘匿すべきファイルだから」ではなく「たまたま絶対パスが含まれていたから」**

検査は中身の文字列の形だけを見ている。もしそのツールがパスを `~/` 表記で書いていたら、ローカルプロキシの接続先ごと素通りしていた。ループバックアドレスは、プライベートIP範囲を狙った既存パターンに含まれていない。

つまりこの防御は**内容の危険さを判定していない**。危険なファイルが止まったのは副作用であって、設計された挙動ではなかった。

一般化: **防御は層で分ける。ファイル単位で「持ち込ませない」のは無視リスト（gitignore）の仕事、中身の混入を拾うのがパターン検査の仕事。**片方で両方を賄おうとすると、通ったときに「検査を通過した」という誤った安心が残る。

今回の実例では、無視リストが完全一致指定だったため、**ツールが退避目的でリネームしたファイル**（先頭にアンダースコアを付けて無効化するパターン）を捕まえられていなかった。glob に変えて塞いだ。

### 判断点2: 学習ログを機械的に読んで再出題する機構は、最初にどこが壊れるか

**予測:** ログのパースが壊れる。しかも失敗してもセッションは正常に始まるため、出題されないことに誰も気づかない。

**実際:** 同じ。手書き Markdown を機械可読の前提に置くのが最も脆い。

**差分（予測に含まれていなかった観点）: その故障は将来の話ではなく、機構を作る前にすでに2回起きていた**

エントリ件数を見出しの grep で数えていたが、その正規表現が**コードブロック内に置いた記録フォーマットの例**まで拾っていた。結果、実際は19件のところを20件と報告した（その前の回は19件を18件と記載していた）。

再出題の hook が同じ正規表現を使えば、日付プレースホルダのままのテンプレート行を**実問題として出題する**。パースの脆弱性は hook を書いて初めて現れるのではなく、目視カウントという最も単純な利用ですでに露呈していた。

一般化: **自動化を検討している対象は、自動化する前に人間が同じ操作で失敗していないかを見る。**手作業で数え間違えるデータ構造は、機械が読んでも同じ場所で間違える。前兆は機構を作る前から出ている。

さらに、この機構が特に静かに壊れる理由は**動作を確認する動機を持つ観測者がいない**ことにある。出題されなくてもユーザーは「今回は出題がなかった」としか思わない。学習支援の機構は「サボっても誰も困らない」という性質を構造的に持つため、他の機構以上に**動いていることの可視化**を先に設計する必要がある。
