# 回避策として入れた設定を維持するか外すか

### 判断点: 過去に回避策として入れた無効化フラグを、性能向上のために外すか

LLM ゲートウェイ経由で使う環境で、実験的機能を一律無効化するフラグが
設定に焼き込まれていた。「最高の性能を引き出す」という目的と正面から
衝突しうる唯一の設定だった。

**予測:** 業務継続性を優先し現状維持。加えて「推測ではなく、
ゲートウェイ側の一次情報を当たるべき」と指摘した。

**実際:** 現状維持で妥当。一次情報を確認したところ、次が判明した。

- この問題は**上流が本家 API 直呼びの場合には発生しない**。
  別プロバイダへルーティングする構成でのみ起きる
- 恒久対応は**プロキシ側**の設定整備とバージョン更新であり、
  クライアント側の無効化は回避策でしかない
- そのフラグはクライアントの公式ドキュメントに記載が無い

**差分（一致）**

現状維持の判断は妥当。ただし予測に含まれていなかった観点が1つある。
**提示された選択肢が3つとも「クライアント側で完結する対処」だった。**
上流の別プロダクトに答えが書いてある可能性が候補に無く、
それを補ったのは予測した側だった。選択肢を作る側の設計が狭かった事例。

もう1点。「現状維持」を選んだ時点では、**この判断がいつ見直されるかの条件が
決まっていない**。作業内容だけを記録して着手条件を書かない項目は放置される。

### 欠けた軸: トレードオフ

現状維持で何を捨てているかが言語化されていない。
このフラグを維持する限り、実験配信される機能は受け取れないが、
それが具体的に何なのかは不明のまま維持を選んでいる。

**次に同種の判断で確認する問い**: 「現状維持」を選ぶときは、
**捨てているものを1つ名指しする**。名指しできないなら、
それは現状維持ではなく判断の先送りだと自覚する。
