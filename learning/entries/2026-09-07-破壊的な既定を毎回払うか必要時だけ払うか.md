# 破壊的な既定を毎回払うか、必要時だけ払うか

## 判断点

コンテナの起動コマンドが、無条件に「強制再作成」オプションを付けていた。
再作成は実行中のシェルセッションを終了させる。

当初「不要なオプションでは」と疑い、まず測定した。結果、設定を焼き込んだ
イメージが変わればオーケストレータは自動で作り直すため、
その用途には確かに不要だった。ここで「片方が明確に劣る」と判断しかけた。

しかし設計文書に、見落としていた理由が書かれていた。
「秘密情報ファイルの内容変更を確実に新しいマウントへ反映するため」。
これを測ると、記述より悪い挙動が出た。

| 操作 | コンテナから見える秘密情報 |
|---|---|
| 同一 inode で上書き | 新しい値が即座に見える |
| 別 inode へ置き換え（多くのエディタの保存） | **ファイルごと消える** |
| 置き換え後に通常の起動コマンド | **直らない**（何もしないと報告される） |
| 強制再作成つきの起動 | 直る |

「古い値が残る」ではなく読めなくなる。しかも素直な対処である再起動では直らない。
実在するトレードオフだった。**「片方が明確に劣る」という当初の判断は誤りだった。**

選択肢:

- A) 無条件に付ける（現状の実装）
- B) 付けない。必要なときだけ利用者が渡す
- C) 秘密情報ファイルの inode / mtime を記録し、変化したときだけ付ける

選んだ結論: **A**

判断基準（原文）:

> セッションが終わっても再度起動したら問題なさそうだと判断した

## 実際

結論は一致。C の複雑さ（状態ファイルの追加）に見合う便益は薄く、A が妥当。

ただし「再度起動したら問題ない」は半分だけ正しい。何が残り何が消えるかを分けると:

| | 再作成後 |
|---|---|
| 会話履歴・永続メモリ | **残る**（named volume 内） |
| 認証・ツール登録の設定ファイル | **残る**（named volume 内） |
| 作業ツリーの未コミット変更 | **残る**（host bind） |
| 起動中のプロセス（開発サーバ、実行中のテスト、依存インストール） | **消える** |
| シェルの cwd・履歴・環境変数 | **消える** |

状態は残るが、進行中の作業は消える。

## 差分

一致。予測に含まれていなかった観点は
「**コストを払う人が、操作した人と一致しないことがある**」。

起動コマンドを叩いた本人はセッションが落ちることを知っている。
だがコンテナは並列セッション間で共有される（同リポジトリの規約が
「開発サーバのポート・ローカルDB・コンテナ名は作業ツリーを分離しても
衝突し続ける」と明記している）。別ターミナルで動いていたセッションは
何の前触れもなく落ちる。その人は A を選んでいない。

## 評価

- **前提の検証** — 「問題なさそう」が推測のまま結論の土台になっている。
  「再作成で消えるもの」は確認できる事実であり、確認前に判断が確定していた。
  今回は上の表のうち「起動中のプロセスが消える」が抜けた。
- **失敗モード** — A の壊れ方を言えていない。具体的には
  「自分が叩いた起動コマンドが、別ターミナルの実行中セッションを無告知で落とす」。
  自分のセッションだけを想定していた。

## 過去の判断原則との接続

`2026-08-16-force-push-の例外をどの属性で切るか.md` に同じ型の原則が既にあった。

> 「復旧できるから安全」と言うときは、**復旧に使う保存先を1つ名指しし、
> それが自分の手元以外にも存在するか**を先に確認する。

「再度起動したら問題なさそう」は「復旧できるから安全」と同じ形。
復旧元を名指ししていない。同じ軸が同じ型の判断で繰り返している。

## 概念

**blast radius（影響半径）** — 操作が壊す範囲。自分が払うコストと
他人が払うコストは別に数える必要がある。
「自分は納得している」は影響半径の外側には効かない。

## 定石

破壊的な副作用は、**副作用が実際に発生する条件が成立しているときだけ**
事前告知する。無条件に警告すると読まれなくなり、条件付きなら情報として残る。
今回なら「コンテナが既に起動している起動コマンド」でだけ告知する。

## 次の問い

**次に同種の判断で確認する問い**: 「再実行すれば戻る」を根拠にするときは、
**戻らないものを1つ挙げる**。挙げられないなら、それは戻ると確認したのではなく、
壊れるものを列挙していない。

## 副産物: 削除しかけた理由

このオプションを削除しかけたのは、**なぜ付いているのかがコードにも ADR にも
書かれていなかった**ため。理由が設計文書の本文にしかなく、実装から辿れなかった。
「無条件に付ける」判断を維持するなら、削除を試みる次の人が同じ測定を
やり直さずに済むよう、理由を実装のそばに残す必要がある。
