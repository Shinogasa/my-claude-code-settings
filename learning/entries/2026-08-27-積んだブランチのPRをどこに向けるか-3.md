# 積んだブランチのPRをどこに向けるか

### 判断点: 未マージのブランチの上に積んだ作業を、どこへ向けて PR にするか

作業ブランチが、まだ OPEN な別 PR のブランチの上に積まれていた。
`main` からの差分に、下位 PR のコミットが1つ含まれている状態。

選択肢は3つ。

- A) `main` を base にして PR を作る（下位 PR のコミットも差分に含まれる）
- B) 下位 PR のブランチを base にして積む（下位がマージされるまでマージできない）
- C) 下位 PR を先にマージしてから `main` へ rebase する

**予測:** C。

> 7マージしたので3
>
> さきにいれておいたほうがいいものだったkら

**実際:** 結論は一致。rebase は衝突なく通り、下位 PR のコミットは自動的に
スキップされて、上位の作業だけが差分に残った。

ただし**通った理由は、下位 PR が merge commit 方式でマージされたこと**にある。
元のコミットが同一 SHA のまま `main` に入ったため、rebase が
「もう含まれている」と判定できた。

```
git merge-base --is-ancestor <下位PRのコミット> origin/main  → 含まれる（同一SHA）
```

**差分（一致）:** 予測に含まれていなかった観点は**下位 PR のマージ戦略**。
squash merge / rebase merge で入っていた場合、元のコミットは `main` で別 SHA になる。
rebase は「まだ入っていない」と判断して再適用を試み、
同じ内容が両側にあるため衝突するか、重複コミットが残る。
「先に入れる」を選んだ時点で、どちらで入るかは確認していなかった。

### 欠けた軸: 失敗モード

同じセッションで**2回連続**この軸が空いた。
1回目は「実行順を前倒ししたとき、その順序に依存している側がどう壊れるか」、
2回目は「先に入れたものが、どういう形で入るか」。
いずれも**選んだ案が通らない世界を見に行っていない**。

選択肢が3つとも成立しうるとき、勝敗を分けるのは「どれが良いか」ではなく
「どれが壊れにくいか」であることが多い。良さの比較だけで選ぶと、
通ったときに「正しかった」と学習してしまい、通った理由が
外部条件だったことに気づけない。

**次に同種の判断で確認する問い**: スタックしたブランチを rebase する前に、
**下位ブランチがどのマージ方式で取り込まれたかを1つ確認する。**
merge commit なら素通りする。squash / rebase merge なら手当てが要る。

### 概念

**stacked PR（スタックPR）** — 依存関係のある PR を積み重ねる運用。
下位 PR のマージ戦略が上位ブランチの rebase コストを決める。
squash / rebase merge は元と別の SHA を作るため、
上位から見ると「まだ入っていない」ことになり、重複コミットや衝突が出る。
