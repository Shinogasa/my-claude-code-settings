# コード学習の記録（pilot）

`skills/code-learning/SKILL.md` の演習で、ユーザーが**実際に示した能力**を振り返るための記録。
設計判断の ★ Predict / ★ Delta は `learning/entries/` に置き、ここへ混ぜない。
このschemaと既習閾値は ADR 0012 の確定値ではなく、pilot用の初期案である。

## 保存する条件

- ユーザーがコードを書いた・変更した・レビューで指摘した実行動を観測したときだけ記録する。
  理由説明と転移回答は、そのイベントに付随する証拠とする。説明・転移回答だけ、
  AIによる解説だけ、スキップ、未回答は保存しない。
- `★ Code Delta` と同じ一つの能力について、観測した行動、検証結果、未確認事項を分ける。
  コンパイルやテストの成功だけを「理解した」と言い換えない。
- **このリポジトリは PUBLIC。** 社名、組織・顧客名、リポジトリ名、内部URL・パス、
  非公開の型・データ名、業務コードを保存しない。技術的本質を最小再現形へ一般化する。
  **抽象化できない場合は保存しない。** 不明なら記録を作らず、session内のfeedbackで終える。

## ファイルと形式

1イベントにつき `learning/code/entries/YYYY-MM-DD-<能力のスラッグ>.md` を1ファイル作る。
同名なら末尾へ `-2`、`-3` を付ける。架空のユーザー回答や模範コードを埋めたサンプルエントリは作らない。

```markdown
---
date: YYYY-MM-DD
title: "抽象化した能力名"
mode: review      # write / modify / review のいずれか
transfer: passed # passed / failed / not_tested のいずれか
---

# 抽象化した能力名

## 能力

どの挙動・失敗経路・依存・変更影響を扱ったか。一つに絞る。

## 形式

Write / Modify / Review のどれを行ったか。Explainだけなら記録しない。

## ユーザーが実証

実際に書いた・直した・指摘した内容と理由。公開可能な最小再現形で表す。
観測していない推測は書かない。

## 検証方法

test・compiler・benchmark・公式資料・repository契約のどれで何を確かめたか。
未実施ならその旨を書く。検査の成功と仕様の充足を区別する。

## ★ Code Delta

一致点、重要な差分、事故になる条件、再利用できる確認問いを一つずつ。
verified_fact / repo_convention / engineering_judgment / unverified を混同しない。

## 転移結果

変えた条件、ユーザーの回答、検証結果。未実施なら not_tested と理由を書く。

## 未解消のgap

次の実作業で確認すべき一点。無ければ「観測範囲ではなし」とし、
長期保持まで証明したように書かない。
```

## 既習判定と再出題

pilotでは、同じ能力を**別文脈で2回**正しく示し、2回目は**実質ヒントなし**で
理由と変更・レビュー内容を説明し、検査可能な転移にも成功したときに限り、
「既習候補」として同程度の課題を控える。単一タスク内の言い換え2回は数えない。
この閾値は長期保持の証明ではない。後続の実作業で失敗が見えたら再び候補にする。
記録が無いことは未習得の証拠でもない。

反復するgapが体系的な学習missionに向く場合だけ `teach` の候補をユーザーへ提案する。
記録をteachへ**自動同期しない**。導入・転記にはユーザーの明示的な判断を要する。
