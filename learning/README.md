# Learning

★ Predict（予測）と ★ Delta（差分）の記録。仕様は `rules/learning-mode.md` を参照。

> **⚠ このリポジトリは PUBLIC**
> 社名・組織名・プロジェクト名・リポジトリ名・内部ホスト名・内部URL・
> テーブル名・内部パス・業務コードを書かないこと。
> 技術的本質のみを一般化して記録する。判断に迷ったら書かない。
> 詳細は `rules/learning-mode.md` の「抽象化ルール」を参照。

## 構成

```
learning/
├── README.md          運用ルール・集計方法・検証チェックポイント（このファイル）
└── entries/           1エントリ1ファイル
    └── YYYY-MM-DD-<タイトルのスラッグ>.md
```

同じ日に複数書く場合はファイル名末尾に `-2` `-3` を付ける。

## エントリの形式

```markdown
---
date: 2026-08-21
title: "タスク概要"
result: hit
axis: "失敗モード"
---

# タスク概要

## 判断点

何を判断する場面だったか。競合した選択肢を並べる。

## 予測

選んだ結論。

**判断基準（原文）**: ユーザーが自分の言葉で書いた理由（**原文のまま。要約しない**）

## 実際

実際の判断・原因・リスク。

## 差分

結論に対する差分。一致なら「予測に含まれていなかった観点」を1つ。

## 評価: 失敗モード

欠けた軸だけを名指しする。3軸すべて埋まっていた回は
`## 基準が破れる条件` を置く（→「`全軸充足` は自己申告なので、本文で検査する」）。

## 過去の判断原則との接続

同型の判断原則が過去エントリにあれば引く。無ければ節ごと省く。

## 概念

**概念名（英語名）** — 1文の説明。判断の一般名。

## 定石

**こう書く** — そうしないと何が起きるか。コードレベルの書き方。
コードを伴わない判断（運用手順、設定配置、ドキュメント構成）では節ごと省く。

## 次の問い

**次に同種の判断で確認する問い**: ...
```

`## 次の問い` は 2026-08-31 まで `## 学習領域` という名前で、
軸名と「今回何が抜けたか」を再掲していた。評価パートとの重複を解消するため、
**次回の行動だけ**を書く節に縮約した（→ ADR 0007 D4）。
`**次に同種の判断で確認する問い**:` の文字列は grep キーのため**変えていない**。
**このテンプレートは 2026-08-21 以降の形。** それ以前のエントリは見出しの階層と名前が
揃っていない（`### 判断点` は76件中31件）。過去エントリの一括統一は未着手のため、
**全件を対象にした見出し grep は現時点では母数が信頼できない**。

`## 概念` は 2026-08-14 の D6 導入時に、`## 定石` は 2026-08-21 に追加した。
仕様は `rules/learning-mode.md` の「概念名の供給」「定石の供給」を参照。

### frontmatter

| フィールド | 値 | 意味 |
|---|---|---|
| `date` | `YYYY-MM-DD` | 記録日 |
| `title` | 文字列 | 本文の H1 と一致させる |
| `result` | `hit` / `miss` | 予測が当たったか。**成績ではない**（外した回にも学習効果がある） |
| `axis` | 軸名 / `"全軸充足"` / `"未記録"` / `null` | 欠けた軸。下記参照 |

**`axis` の値は必ずクォートで囲む。** `axis: 未記録` と `axis: "未記録"` が混在すると
下の集計スクリプトが別の値として数える（2026-08-14 に4件の混在を検出し正規化した）。

### `axis` の4つの値を混ぜないこと

| 値 | 意味 | 集計での扱い |
|---|---|---|
| `"トレードオフ"` / `"失敗モード"` / `"前提の検証"` | 欠けた軸 | 母数に入れる |
| `"全軸充足"` | 3軸すべて埋まっていた。**名指しする軸が無いことを積極的に主張する値** | 母数に入れる（欠落0件として） |
| `"未記録"` | 軸評価の導入後だが記載が無い。**記載漏れ** | 母数から除外 |
| `null` | 2026-08-08 の軸評価の導入前。軸という概念自体が無かった | 母数から除外 |

**`未記録` と `null` を同じ「空」として扱うと、傾向ではなく「記録がいつ始まったか」を測ることになる。**
軸名は `rules/learning-mode.md` の3軸から動かさない。言い換えると集計が壊れる。

#### `全軸充足` は自己申告なので、本文で検査する

`全軸充足` を書くのは評価する側（AI）であり、**「本当に3軸埋まっていた」と
「評価を飛ばした」を、値そのものからは区別できない**。放置すると、
サボった回が「最も良く書けた回」として集計に入り、上達を過大評価する方向へ偏る。

そこで `rules/learning-mode.md` が全軸充足の場合に義務付けている
「その判断基準が破れる条件を1つ示す」を、**検査可能な見出しに固定する**。

- `axis: "全軸充足"` のエントリは、本文に `### 基準が破れる条件` を必ず置く
- 見出しが無ければ**記載漏れとして扱う**（`未記録` と同じ側に倒す）

```bash
# 全軸充足なのに破れる条件が書かれていないエントリ（記載漏れの疑い）
grep -l '^axis: "全軸充足"$' learning/entries/*.md | xargs grep -L '^### 基準が破れる条件'
```

**これは「書いたかどうか」しか検査しない。** 書かれた内容が妥当かは検査できないため、
この grep が空なことを「評価が適切だった」の証拠にしてはいけない。

## 集計のしかた

```bash
# 総数
ls learning/entries/*.md | wc -l

# 外した回の一覧（再出題用ではない。→ ADR 0001 の A5）
grep -l '^result: miss$' learning/entries/*.md

# 軸ごとの件数（未記録・null は自動的に別集計される）
grep -h '^axis: ' learning/entries/*.md | sort | uniq -c | sort -rn

# 特定の軸のエントリ
grep -l '^axis: "失敗モード"$' learning/entries/*.md
```

### 集計する前に確認すること

**母数が足りているか。** 2026-08-09 時点で軸が付いているのは34件中8件、しかも全て
2026-08-08 以降。この状態で軸別集計をすると、傾向ではなく直近数日の内訳が出る。
`null` が24件ある限り、「どの軸が慢性的に弱いか」は言えない。

**軸の分布は出題形式に依存する。** 2026-08-14 の測定で、
「トレードオフ」軸の欠落が2件しか無いのは得意だからではなく、
**当時の選択肢が判断基準をラベルに書き込んでいたため構造的に検出できなかった**ことが
判明した（→ `docs/adr/0001-learning-mode-prediction-format.md`）。
**同日より前と後のエントリを同じ母数で集計してはいけない。**

**`result` の分布は「成績」ではない。** 2026-08-14 時点で hit 80%（直近20件で90%）。
事前テストは外した回にも効果があるため、**hit 率が高いのは出題が易しすぎる兆候**として読む。
